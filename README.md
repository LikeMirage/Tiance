# 天策 Tiance - 一个看得见运行过程的 Agent 工作平台

**用标准工具调用做事，用文件夹项目组织内容，用会话保留工作过程。**

在 Windows 上管理项目和文件，让一个或多个 AI 工作。工具调用、多 AI 协作、长期记忆、记忆压缩，以及每次实际发给模型 API 的内容，都能找到对应的过程和记录。

## 为什么做天策

我给客户讲 AI，从来不愿意先讲一堆名词。很多概念拆开以后很简单，有些甚至只是给已有做法换了个包装。围着词语解释词语，很容易把理解 AI 变成背概念，最后陷入文字游戏。

我想直接让客户看：模型怎样调用工具，几个 AI 怎样协作，长期记忆从哪里来，历史太长时怎样压缩。再往里看，每次请求究竟给 API 发了哪些消息、提示词、工具说明和参数？

但我一直没找到一款软件，能按我希望的方式，把这些过程直观、连贯地摆在同一个地方。只有输入框和结果，很难拿来解释中间究竟发生了什么。

于是我做了天策。能力通过工具调用，内容放在真实目录里，AI 的工作留在能打开的会话里。同类事情共用同一套结构，少发明几种特殊形式。

我想让初次接触的人也能看懂所谓 Agent 的运行逻辑。先把事情看明白，至于要给它起什么名字，可以往后放。

## 我更相信模型的能力，也愿意认真打磨工具

我用过几乎所有主流 AI 工具。从早期的 Cline 插件，到 Cursor、Augment、Windsurf、Kiro、Google Antigravity、Claude Code、Codex，一路都在实际工作中使用。

下面是我的个人体验，不是对这些产品做的统一评测。

以前模型能力普遍还不够强的时候，厚重的框架和大量系统提示词，也许能帮它多走几步。但用到现在，我越来越觉得：**模型本身的能力才是最重要的。**

一套框架可能让某一类任务做得更好，尤其是编程。但把这套习惯带到其他工作里，也可能多出无关步骤、错误假设和 Token 浪费。我没有体验到哪套框架，能在使用同一个模型时，稳定地让各种工作都明显高出一截。相反，有些工具不知道在系统提示词里塞了什么，原本机灵的模型也变得束手束脚，做什么都带着同一套模板味。

我的习惯是：把需求和材料交代清楚，给模型几个基础、好用的工具，先让它做。遇到真实问题，再改工具、补说明。模型本身做不到的事，我不会指望靠一层层堆提示词，把它硬哄成能做到；在我遇到的任务里，这样往往只是让错误绕得更远、花得更多。

天策仍然需要任务说明、工具参数和必要的执行规则。自动命名要知道自己是在命名，记忆整理要知道哪些信息值得保留。**我希望每条规则都能说清楚它解决了什么问题。**

相比不断给主模型加一套“应该怎样思考”的剧本，我更愿意把具体能力做成独立工具，反复打磨输入、执行和结果。需要的人启用，需要修改的人直接改。

## 一次请求，到底发生了什么

假设你让 AI：“分析这个销售表，画几张图，再写一份 Word 报告。”

一次可能的过程是：

1. 程序把你的要求、相关历史和可用工具说明发给模型。
2. 模型提出读取表格的工具调用，程序执行，把结果交回模型。
3. 模型根据结果继续调用工具，运行分析、保存图表、写报告。
4. 调用文档转换工具生成 Word，最后告诉你结果在哪里。

**模型提出调用，程序执行，结果交回模型，再决定下一步。** 常见 Agent 的工作过程，可以从这个循环看起。

在天策里，工具调用能展开看参数、结果和错误。请求记录还能让你核对实际发给 API 的消息、系统提示词、工具定义和生成参数，以及供应商的响应；敏感凭据会脱敏。你不必只靠聊天窗口里显示的几句话，猜测模型究竟看到了什么。

长对话加入了哪些摘要？一段记忆是否进入了请求？动态工具有没有带上完整参数？这些都应该有记录可以核对。

## 多 AI 协作、自动命名和记忆，都有过程可查

AI 协同系列工具沿用人操作会话的同一套能力。模型通过标准工具调用创建普通子会话，选择模型、角色与工具，发送任务，等待或读取结果。

子会话会出现在会话树里。用户随时可以打开，查看材料、工具调用和回复，按会话状态补充要求或停止任务。子 AI 还可以继续创建自己的子会话，不同会话可以使用不同供应商和模型。

![项目中的多级会话树与工具调用记录](assets/screenshots/session-tree.png)

图中左侧是项目，中间展开的是会话与子会话，右侧是当前会话的回复和工具调用。这些会话都可以进入查看和交互。

自动命名、记忆压缩和长期记忆管理也沿用这种形式：

| 功能 | 实际怎么做 |
| --- | --- |
| 自动命名 | 达到触发条件后创建命名会话，由 AI 根据材料生成标题，通过会话管理工具提交。 |
| 记忆压缩 | 创建压缩会话，让 AI 整理累计摘要，通过压缩提交工具保存；后续请求使用已提交摘要和需要保留的原始消息。 |
| 长期记忆 | 创建项目或全局记忆管理会话，让 AI 先读取已有记忆，再通过记忆工具增删改；后续请求按规则带上相关记忆。 |

平台负责何时触发、提供哪些材料、允许哪些工具，以及怎样校验、保存和反馈结果。后台做的事情能进入会话查看；摘要和记忆也能找到来源。压缩改变后续请求携带的历史，不删除原始聊天记录。

这种统一也有实际好处：用户会用普通会话，就能继续理解子任务和记忆任务；程序可以复用会话、工具和记录机制，不必每多一个功能就另建一套。

## 各类内容，共用文件夹项目结构

**普通项目、工具、角色、主题、供应商等内容，都按有真实目录的项目来管理。** 共用的项目结构负责组织内容，各自的文件和界面负责表达用途。

| 项目类型 | 里面有什么 |
| --- | --- |
| 普通项目 | 资料、源码、生成文件，以及项目内的会话数据 |
| 工具 | 用途和参数说明、执行程序、资源、依赖等文件 |
| 角色 | 角色提示词与相关配置 |
| 主题 | 主题配置、图片等资源 |
| 供应商 | 协议、模型与适配配置 |
| 知识和经验项目 | 按项目组织的资料与会话；专用功能仍待开发 |

它们共用文件浏览、分类、会话等能力，各自的看板负责把常用配置摆出来。工具也是可以打开、对话和修改的项目，个性化需求可以直接在工具自己的文件里实现。

普通项目既可以使用天策创建的目录，也可以使用已有工作文件夹。正文、源码、附件和交付文件保留为真实文件；会话等内部状态集中保存在项目的 `.Tiance/tiance.db`。

## 几个我反复打磨过的工具

软件里的部分办公工具，最初就是朋友提出需求后做的。已有项目能解决的部分就复用，实际使用中发现不足，再把缺的能力补上。下面这些例子，也能说明为什么我愿意把精力放在工具上。

### Markdown 转 Word：把 AI 的输出变成能继续编辑的文档

AI 很擅长输出 Markdown，但正式交付经常需要 Word。做 `md2docx` 时，我关心的是公式能否继续编辑、表格是否好读、已有文档的排版能否沿用。

公式转换复用了成熟解析器，以及 Microsoft 的 `MML2OMML.XSL` 公式转换规则，把 Markdown 中的 LaTeX 公式转换为 Word 原生数学对象，再检查和修复必要的结构。普通公式可以在 Word 里继续编辑；难以可靠表达的内容会转成图片或保留源码，并返回提示。

它还可以从现有 Word 样本提取模板，沿用纸张、页边距、标题、正文、页眉页脚等设置；表格分列会考虑实际字体和内容宽度。具体实现见[Markdown 转 Word 工具设计](docs/02_Markdown转Word工具设计.md)。

### Word 编辑：把用户选中的位置传清楚

用户在 Word 预览中选中内容并引用到对话，程序会携带文字位置、表格行列、段落和文档版本等信息。即使选中的是表格里的原生公式，工具也能结合这些信息定位、核验对应对象，减少让 AI 重读整份文档再猜位置的工作。

修改内容可以继续用 AI 熟悉的 Markdown 和公式表达。工具先预检定位与修改，再提交写入；文件变了或无法唯一定位时，会明确报错。这里打磨的是引用、定位、内容转换和写入之间的配合。

### MinerU 解析：保留原图，再补上图里的信息

我很喜欢 MinerU 的文档解析服务。但在自己的使用中，有些插图、流程图、截图里的信息，解析结果没有充分表达出来。

于是我在 MinerU 结果上增加了视觉模型补充：分析需要处理的插图，把识别出的内容以“视觉解析”标注插在结果文档的原图下方。原图保留，模型补充有明确标记，读者可以对照检查。

解析服务继续做它擅长的部分，视觉模型补充图中的信息，这些步骤放在一个独立工具里。补充失败也会留下说明，不把缺失内容当作已经成功还原。

### GUI 系列：从看见位置，到执行动作

GUI 工具让 AI 查看和操作桌面。它可以把截图划成网格，逐级查看局部区域，再用格内比例坐标指定位置，最终映射到屏幕像素。这样可以在同一个坐标体系里从整屏逐步定位到小目标。

真正需要打磨的是状态继承：截图、局部视图、网格和坐标要对应同一份画面；操作后的新截图、窗口身份变化、旧引用失效，也要交代清楚。坐标能够映射到像素，不代表模型每次都能正确识别目标，因此仍需要观察和结果确认。

鼠标、键盘、批量动作和标注沿用这些状态。对能提供控件信息的 Windows 界面，还可以通过控件工具读取和操作按钮、输入框等元素。执行动作和确认业务成功分别记录，避免截图失败后把已经点过的按钮再点一遍。

### 动态工具：需要时再读说明，通过标准调用执行

工具多了，每次把所有完整参数说明都塞进请求，会占掉很多上下文。设为动态加载的工具先提供名称、摘要等目录信息，AI 需要时再读取完整参数和案例。示例是否额外注入由配置决定，节省多少也取决于实际工具和配置。

只告诉模型一个名字，还不足以让它通过标准工具协议直接调用未声明的目标。天策把 `load_tool_info` 和 `execute_dynamic_tool` 作为正式工具提供给模型：前者读取说明，后者接收目标工具名与参数，再执行真正的工具。

这样，外层仍是标准工具调用，目标工具也保持自己的结构。参数、启用状态和权限照常检查；外层执行工具与目标工具的权限从严合并：**禁止优先于询问，询问优先于允许。** 套一层执行入口不会获得更大的权限。

## 不同位置的能力，怎样保持同一套工具结构

多数普通工具用 Python 就能完成工作。但有些事情需要访问当前界面状态，有些需要复用模型集中保存的供应商配置。让每个工具自己猜前端状态、读数据库、取密钥，会把工具和主程序绑得越来越紧。

我的折中办法是保留统一的工具配置、参数和结果形式，再为确实需要跨越的位置提供明确接口。这就是天策里“能力桥”这个名字对应的实际用途：

| 执行或连接方式 | 解决什么问题 | 相关工具 |
| --- | --- | --- |
| Python 工具运行入口 | 接收参数，启动独立进程执行，收回结果；依赖与资源由工具管理 | 文档转换、MinerU、GUI 等普通工具 |
| 前端能力桥 | 使用已经登记的界面能力和实时状态，再把结果交回工具调用 | AI 会话协同、编辑器标签页管理、新建空白工具 |
| 后端供应商能力桥 | 在后端使用已保存的供应商配置与凭据，执行明确授权的能力 | 模型内置网络搜索、DeepSeek 官方网络搜索的凭据复用路径 |

例如，标签页工具可以打开刚生成的文件供用户查看；模型内置网络搜索工具复用当前会话供应商的原生搜索；DeepSeek 官方网络搜索使用独立 Search/Fetch 接口，工具没有配置自己的 Key 时，可以通过后端桥复用模型集的 DeepSeek 配置，桥不会把 Key 交给工具。

这几种能力不必伪装成同一种执行环境，但对 AI 仍然是标准工具调用，对用户仍然是同一套工具项目。工具自己的业务留在工具里，共用能力留在对应接口里。需要一种尚未开放的界面或供应商能力时，就扩展对应接口，不在通用聊天流程里为某个工具到处加特殊判断。

## 你也可以做自己的工具

“新建空白工具”本身也是一个工具。AI 调用它，就能在指定分类下创建工具项目，配齐配置、程序入口、测试示例和完整制作资料。

```text
工具项目/
  .tool/                  名称、参数、返回格式和权限等配置
  program/
    main.py               执行程序
    requirements.txt      Python 依赖声明
  assets/                 按需放置资料与资源
  tests/                  测试示例
  docs/tool-development/  创建时附带的制作说明
```

你可以让 AI 先读随附文档，再把你的办公习惯、固定处理步骤或其他需求做成工具，反复修改到好用为止。新工具默认关闭，完成并验证后，由你决定是否启用。详细接入方式见[工具制作文档](docs/29_工具制作与空白模板.md)。

现成的工具、角色、主题和供应商项目也可以从在线市场获取，安装后仍保留可查看、修改的本地内容。

![项目总览与当前会话](assets/screenshots/project-overview.png)

项目总览把各项目的会话和状态放在一起；进入项目后，可以继续浏览文件、编辑和预览文档。文件、文件夹和其他项目都可以引用到对话。

## 权限与隔离：这是我的使用取舍

我自己使用 Agent 的习惯偏向“疑人不用，用人不疑”：决定让它接手一件事，就愿意给它充分的操作权限。我更关心它做了什么、出了问题能否查清，也不会仅因为产品带一个“沙箱”标签，就认为可以放心交出设备。

**天策目前没有通用的操作系统级沙箱。** Python 工具在独立进程里运行，仍可能访问当前进程权限允许访问的文件、网络和程序。当前 Windows 启动器要求管理员授权，工具进程也会沿启动链继承权限。

程序有工具启用、参数校验、权限策略和执行确认。这些机制控制哪些调用允许执行，不构成对恶意工具代码的系统隔离。我的充分授权习惯不代表程序默认放行所有操作，用户仍可以设置自己的权限策略。

如果需要把 AI 的操作与日常设备隔开，可以使用专用电脑或虚拟机，例如 VMware；隔离效果仍取决于共享目录、网络和凭据如何配置。不要把我的使用习惯当成适合所有人的安全保证。

项目与会话数据保存在本地；使用在线模型、MinerU、网络搜索等服务时，相应内容仍会发送给所选服务。本地保存与离线运行是两回事。

## 开始使用

目前提供 Windows 发布包，已经包含 Python、后端依赖和构建好的前端，无需另外安装 Python 或 Node.js。

1. [下载最新 Windows 版](https://github.com/LikeMirage/Tiance/releases/latest/download/Tiance.zip)，解压并保留完整目录结构。
2. 双击根目录的 `Tiance.exe`，确认 Windows 管理员授权后启动。
3. 在模型集中配置自己的供应商与 API Key。
4. 创建项目或打开已有工作文件夹，新建会话，选择模型和需要的工具，开始工作。

使用前请阅读上面的[权限与隔离说明](#权限与隔离这是我的使用取舍)，了解工具在本机执行的范围。

软件支持通过 GitHub Releases 更新，更新包保留用户项目和配置。使用 Git 克隆源码的目录应继续通过 Git 更新。
