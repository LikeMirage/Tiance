# 05 验证、启用、排错与发布

## 最小验证流程

1. 读取五份 JSON，核对调用名唯一、执行类型、明确的并发/动态/超时、程序入口和文件引用。参数、程序和案例一致。
2. 从工具根执行 `python -m unittest discover -s tests -v`。模板测试证明“尚未实现不能声称成功”，实现业务后须替换为业务成功、失败、参数和副作用测试，不能拿模板测试证明业务已可用。
3. 直接测试 stdin/stdout。宿主启动会提供 tiance_runtime；手动启动需要把当前应用的 `1_PythonServer` 加入 PYTHONPATH，或用平台执行器。不要从 pip 安装同名包。
4. 通过当前后端的 `ToolProjectConfigStorage.normalize_standard_file_content` 检查标准文件，再用 `tool_metadata.load_tool` 验证可加载；通过参数校验器验证合法与非法调用。不要在工具日常程序里导入后端服务来执行这些测试。
5. 在隔离临时工作区验证路径、覆盖、依赖、超时、权限拒绝与取消。真实业务确需联网或真实副作用时，按用户授权范围验证，报告未验证的项目。
6. 根据用户意愿决定是否启用，再测试平台真实调用与结果展示。没有启用授权时可以完成离线测试，保持 false 并明确说明。

PowerShell 手动协议测试示意（把应用根替换成实际位置）：

```powershell
$env:PYTHONPATH = 'C:\实际应用目录\1_PythonServer'
'{}' | & 'C:\实际应用目录\runtime\python\py313\python.exe' '.\program\main.py'
```

使用 PowerShell 单引号保护 JSON，不能把模型或用户输入拼成未经转义的 shell 命令。新模板此时应返回未实现错误，退出码非零，这是正确行为。

## 如何开启

配置位置是本项目 `.tool/tool.json`，把 `state.enabled` 设置为 true。工具制作完成不意味着用户希望立即开放；明确的启用指示才执行。修改清单后确认注册成功；目标会话的工具总开关与选择列表也必须允许该工具。不要未经指示批量改所有会话或角色模板。

开关关闭不代表清单可以缺字段。注册表仍会读取关闭工具的配置。不要删除 input/output/examples 后继续写 tool.json。新工具初始装配应先写其他文件，最后写清单；已有工具的多文件修改要控制一致性并及时校验。

## 常见问题

| 现象 | 先检查什么 |
| --- | --- |
| 项目能打开，但工具列表没有 | 是否有完整 .tool；是否全局启用；是否注册失败；会话是否选择它 |
| 文件修改后仍是旧说明或旧状态 | 注册表刷新是否报错；失败会保留旧索引；不要用重复开关掩盖根因 |
| 参数不允许/缺少必填 | AI 实际 arguments 与 input.schema.json 的位置、类型、额外字段和分支条件 |
| 前端能力不可用 | 能力名称/版本是否登记、前端是否重建、是否保持连接、是否重启了旧后端 |
| 缺少 tool_project_id | 使用了未更新的后端请求合同，不能回退到调用方 project_id |
| 宿主能力无授权 | 调用名白名单、短期凭据、过期/撤销、能力类型、所需模型/登录是否存在 |
| stdout 不是 JSON | 初始化输出、第三方日志、BOM、额外 print、多个对象或进程崩溃 |
| 找不到 tiance_runtime/依赖 | 手动启动的 PYTHONPATH、工具私有依赖环境、实际解释器版本 |
| 创建失败但分类里已有项目 | 读取 returned project/root_path，检查 written_files/attempted_file，继续修复，不重复创建 |
| 图片只有路径文字 | 标准 resource_link、工作区相对路径、格式、权限和模型 image 模态 |

## 市场发布

本地新模板不自带根 manifest.json，以免把模板版本误当成新工具的市场身份。准备发布时根据当前 `docs/16_在线工具市场发布与更新流程.md` 和工具市场源码构建器生成正式包。稳定市场 ID 与工具调用名承担不同职责；更名、安装时调用名冲突和更新身份必须分别处理。

根 manifest.json 的当前形状：schemaVersion=1、kind=tiance-tool-package、id、version、author、license、compatibility（minTianceVersion、platforms）。不要未经授权替用户选择许可证或声明作者。最低应用版本应依据实际能力兼容；仅有相同版本号也不能证明本机有尚未正式发布的前端能力。

包包含五份 .tool 合同、实际程序与资源及依赖声明；排除 .Tiance、已安装 dependencies、缓存、测试临时产物和个人凭据。config.json 只保留可发布的空密钥模板和业务默认值。全量发行包的工具允许列表/清单也需要核对，新增目录不保证会被发布脚本自动收录。

市场仓库构建器负责 index.json、安装包、大小与 SHA-256，应用源码仓库并不包含同一份市场构建入口；不要随意发明脚本路径。当前在线市场更新保留本地调用名、state、loading、权限、config、依赖和 .Tiance；并发开关和案例选择尚没有单独保留规则，发布更新前应明确这一现状。本文不把它描述成已经修复。

测试报告应区分：静态检查、隔离测试、真实运行、界面验证、联网验证。源码改动不自动代表用户当前运行的进程已经加载新版。发布到 GitHub 或市场属于单独动作，须有用户指示。
