# 上游响应异常重试与会话运行结算机制

更新时间：2026-08-19
流式解析保护补充：2026-10-29（BE-068）

## 一、目标

本机制解决模型上游请求在发送后出现连接失败、协议解析失败、流式响应意外中断等问题，并保证：

- 普通会话和功能会话使用同一套重试机制。
- 重试同一个完整逻辑请求，不重复写入用户消息，不重复创建会话。
- 未完成响应不会混入后续模型上下文。
- 已经完整完成并持久化的工具轮次不会因后续请求失败而丢失。
- 最终失败可以在界面中看到，但不伪装成模型正式回复。
- 每一次真实 HTTP 请求和响应都可审计。
- 用户主动取消永远不会触发自动重试。
- 不根据供应商名称、模型名称或零散错误文案写特殊分支。

## 二、关键概念

### 1. 会话运行

一次用户消息触发一条会话运行。运行使用稳定的 `run_id`，并关联：

- `session_id`
- `user_message_id`
- 开始时间
- 最终状态
- 最终错误码和错误信息
- 最后一轮上游请求实际尝试次数

一次运行可能包含多轮模型请求。例如模型先调用工具，工具返回后再请求模型生成最终回答。

### 2. 模型轮次

从一份完整模型请求状态开始，到模型正常完成、返回工具调用、失败或取消为止，称为一个模型轮次。

自动重试的边界是当前模型轮次。重试时重新发送该轮次相同的完整逻辑请求状态。

### 3. 物理请求尝试

模型轮次第一次请求和每一次重试，都是一次独立的物理 HTTP 请求。每次尝试都有：

- `attempt_index`
- `attempt_count`
- 完整脱敏请求
- 完整响应或已接收的响应片段
- HTTP 状态
- 传输错误
- 尝试结果事件

### 4. 正式消息、运行结果和审计记录

三者职责严格分开：

- 正式消息：用户消息、模型完整回复、已提交的工具调用和工具结果。它们可进入后续模型上下文。
- 运行结果：记录运行最终成功、失败或取消。失败结果用于界面错误卡片，不进入模型上下文。
- 审计记录：保存每次物理请求的原始脱敏请求与响应、事件和哈希，用于排查，不进入模型上下文。

禁止把运行错误卡片或 HTTP 审计记录拼进正式消息，禁止模型上下文依赖界面展示数据。

## 三、配置

会话设置增加 `upstream_retry_count`：

- 含义：首次请求失败后，最多额外重试多少次。
- 默认值：`1`，即最多发送两次物理请求。
- `0`：不自动重试。
- 该值是显式会话配置，不存在代码内部的隐藏重试次数。
- 角色配置包含同一字段。
- 子会话和功能会话按现有会话配置继承规则获得该值。

功能模型设置不再有独立的“失败重试次数”。记忆压缩、项目记忆管理、全局记忆管理等功能会话不再维护第二套重试循环。

## 四、统一重试流程

### 1. 非流式请求

处理顺序：

1. 构造当前模型轮次的完整逻辑请求。
2. 写入本次尝试编号。
3. 发送物理请求。
4. 保存 HTTP 请求和响应审计。
5. 如果请求抛出异常或返回空结果，记录本次尝试失败。
6. 如果仍有重试次数，使用同一完整逻辑请求状态再次发送。
7. 正常获得完整结果后记录本次尝试成功并返回。
8. 次数耗尽后向会话运行层报告最终失败。

### 2. 流式请求

处理顺序：

1. 构造当前模型轮次的完整逻辑请求。
2. 接收并暂存正文、思考、工具调用、协议续接状态和用量。
3. 只有收到协议适配器确认的完成事件，该尝试才算完整成功。
4. 出现异常、明确错误事件，或连接结束但没有完成事件时，该尝试失败。
5. 如果仍可重试，发送 `retry_reset` 内部流事件。
6. 会话层和前端收到 `retry_reset` 后，只撤销当前未提交模型片段。
7. 已经完成并持久化的更早工具轮次保留。
8. 使用同一完整逻辑请求状态重新发送当前模型轮次。
9. 最后一次仍失败时，才向用户显示最终错误。

“连接正常关闭”不等于“模型回复完整”。没有完成事件的流必须按异常流处理，不能把最后收到的一段正文当作完整回答。

### 3. 共用流式解析与异常累积保护

OpenAI 兼容、Responses、Anthropic 和 Gemini 统一使用 `app/infra/llm/chat_adapters/sse.py`。网络数据块不等于 SSE 事件，也不等于整篇回复：一条事件可跨多个数据块，一个数据块也可包含多条事件。

- 以最多 64 KiB 的工作块扫描新字节，未完成行及多行事件使用可增长字节缓冲；不重新扫描旧字节，不逐行复制数据块的剩余正文。
- 累计处理 256 KiB、256 行或 256 个数据块时主动让出事件循环，给其他请求及取消处理执行机会。此处使用 `asyncio.sleep(0)`，没有人为等待时长，也不是业务超时或数据条数上限。
- 支持 UTF-8 跨块、流首 BOM、LF/CRLF/CR 行结束、多行 `data`、注释及 `[DONE]`。保留既有的 EOF 尾事件兼容；是否完整成功仍由各协议的结束标记判断。
- 后端配置 `LLM_SSE_MAX_EVENT_BYTES` 默认 **67,108,864 字节（64 MiB）**，必须为正整数；可通过环境变量或后端 `.env` 调高，重启后生效。
- 该值分别保护**单行字节数（含 `data:` 等行内字段，不含行结束符）**及**单条事件的数据字节数（含多个 `data` 值之间拼入的换行）**。两处各自计数，事件结束后清零；不限制整个 HTTP 响应、整篇回复、工具调用循环或会话的总长度，也不代表进程总内存上限。
- 超限抛出 `UpstreamProviderError`，错误码为 `upstream_stream_event_too_large`，包含实际检测大小、配置上限和调整方式；不截断后当作成功，不尝试拼接后续事件来掩盖异常。沿现有尝试失败/重试机制结算。
- 解析失败、超限、取消或下游提前关闭时，立即关闭上游生成器及 HTTP 响应，沿现有原始交换流程保存**停止前已接收到的字节**；不会继续下载尚未收到的剩余响应。无效 JSON 按协议错误处理，不静默跳过。

这与原始响应审计的 8 MiB 内存转临时文件阈值相互独立。合法的大事件可包含完整响应或工具参数，不按供应商名称特殊处理。完整事件的 JSON 解码仍是一次同步操作；调高单事件保护值会增加其内存和单次解析开销，不能把分块调度误称为大型 JSON 解析的完全隔离。

回归入口：`1_PythonServer/tests/test_sse_parser.py`，并联合协议适配器、原始响应审计及会话重试/取消测试验收。

## 五、不做供应商特殊分类

程序不通过供应商名称、模型名称、HTTP 状态码表或错误文案决定是否重试。

统一边界是：

- 请求没有形成一个协议上完整、可提交的模型结果：按上游请求失败处理，可重试。
- 请求形成了协议上完整的模型结果：按成功处理，不重试。
- 用户主动取消：按取消处理，不重试。

因此：

- HTTP 401、403、408、429、500 等错误都会经过相同次数的重试，不写供应商专用判断。
- 余额不足、限流、模型不存在等若由上游以错误响应返回，也按统一失败边界处理。
- 内容安全或模型拒绝若以正常完成的模型回复返回，属于有效回复，不重试。
- 内容安全若由协议适配器报告为请求错误，则按统一失败边界处理。

这样不会因供应商错误格式变化而不断添加特殊补丁。

## 六、同一个完整逻辑请求是什么意思

重试不会只发送“最后一条文本”，也不会重复创建用户消息。

重试使用当前模型轮次已经构造好的完整请求状态，包括：

- 系统提示词
- 需要返回的正式历史消息
- 当前用户消息
- 已经提交的工具调用和工具结果
- 当前工具定义
- 生成参数
- 协议需要的续接信息

OpenAI Responses、Anthropic、Gemini 等协议的具体传输形式由各自协议适配器负责。统一重试层只保证逻辑请求状态不变，不越过协议适配边界自行拼装供应商字段。

## 七、流中断时的数据处理

### 1. 当前模型轮次尚未提交

本轮收到的正文、思考、未完整工具调用和协议续接片段全部视为临时数据。

发生重试时：

- 后端清空本轮临时累积。
- 前端回退到最近一次已提交工具结果后的显示状态。
- 临时正文不写正式消息。
- 临时工具调用不执行。
- 临时协议续接信息不进入下一次请求。

### 2. 更早工具轮次已经提交

如果此前模型工具调用已经完整、工具已经执行、调用和结果已经写入正式消息：

- 这些事实不会被回滚。
- 当前失败轮次从包含这些正式工具事实的请求状态重新发送。
- 不会再次执行已经完成的工具。

## 八、工具指令异常与上游异常分离

工具指令错误不是上游传输失败，不能和 HTTP 自动重试混为一体。

### 1. 参数不是合法 JSON

处理方式：

1. 不执行该工具。
2. 持久化一条结构化工具失败结果，错误码为 `INVALID_TOOL_ARGUMENTS`。
3. 为保证下一轮协议结构合法，回放给模型的工具调用参数使用 `{}`。
4. 工具失败结果中保留原始错误参数和明确提示。
5. “修复错误工具指令”开启时，把合法化后的调用和失败结果返回模型，让模型自行重新输出工具调用。
6. 关闭时，不继续自动请求模型修正。

### 2. 参数是合法 JSON，但不符合工具 Schema

这是正常工具参数校验失败：

- 工具执行层返回结构化错误。
- 不触发上游 HTTP 重试。
- 是否继续生成由正常工具循环决定。

### 3. 流式工具调用尚未完整时连接中断

这是上游流不完整：

- 工具调用不执行。
- 不写入正式工具调用消息。
- 当前模型轮次整体按上游失败重试。

## 九、最终失败的持久化和展示

重试次数耗尽后：

1. 用户消息只保留一份。
2. 不创建伪造的 `assistant/error` 正式消息。
3. 每次物理尝试的失败事实写入 `conversation_journal`，并关联该次 HTTP 交换工件。
4. 有供应商 HTTP 响应时，错误内容使用原始响应正文；没有响应时使用本地捕获到的原始异常；协议检测失败使用检测器实际产生的信息。
5. `conversation_runs` 只保存整轮状态、尝试次数和结算时间，不再复制尝试错误正文。
6. 如果请求在首次物理尝试前就因本地配置校验失败，`conversation_runs` 保留该本地错误作为唯一失败记录。
7. 会话消息接口按用户消息返回相应尝试事件和整轮状态。
8. 前端按事件顺序显示每次失败，刷新或重新进入会话后仍可恢复。
9. 后续模型请求只读取正式消息，因此不会收到错误卡片。

运行使用稳定 `run_id`。重复提交同一运行时，已结算结果会直接复用，不会再次调用上游。运行状态只允许从 `running` 结算一次，后到的终态不能覆盖先到的终态。

## 十、用户主动取消

用户取消和上游失败是不同终态：

- 收到本地取消后立即停止当前请求。
- 不执行自动重试。
- 运行结算为 `cancelled`。
- 取消发生在上游响应前时，不写空白的取消助手消息。
- 取消发生在正文生成过程中时，已经收到的部分内容可以保存为 `cancelled` 助手消息。
- 已经提交的工具调用和工具结果始终作为事实保留，不因展示设置关闭而删除。

用户停止只终止当前执行，不撤销已经保存的上下文。取消回复中的正文和思考、对应的用户消息，以及已经提交的工具调用和结果，始终保留在后续模型上下文中。空白消息仍会过滤，工具调用与结果仍须保持协议配对完整。

原“返回截断消息／取消后继续使用已生成内容”和“返回截断前用户消息／取消后继续使用本轮用户消息”两个设置已移除。旧会话、旧角色包中的这两个字段只作兼容读取并忽略，不再允许关闭返回；新保存的配置不再写入这些字段。需要撤回或更正用户输入时，使用编辑历史用户消息创建分支的功能。

这项规则不改变上游异常的重试方法；输出上限截断的特殊恢复另行设计。

## 十一、功能会话统一

自动命名、记忆压缩、项目记忆管理和全局记忆管理仍是普通会话运行。它们的区别来自提示词、角色配置和所调用的工具，不来自另一套会话执行器。

本次统一内容包括：

- 删除功能模型独立失败重试配置。
- 删除功能任务外层自动重建会话的重试循环。
- 删除压缩记录中的失效 `attempt_index` 和 `retry_of` 字段及对应看板展示。
- 功能会话继承统一 `upstream_retry_count`。
- 一次功能任务只创建一个功能会话。
- 上游失败由该会话内部的统一模型请求层重试。
- 最终失败后立即结束本次功能任务，不继续生成新的功能会话。

`function_type` 等临时功能标记仍只用于当前角色集尚未完成时防止功能递归，不用于建立第二套上游重试机制。

## 十二、审计与原始数据

每一次物理 HTTP 尝试都会保存独立审计工件，内容包括：

- 脱敏后的请求 URL 和请求头
- 脱敏后的完整请求体
- 响应状态和响应头
- 已收到的完整响应字节；流中断时保存中断前已经收到的字节
- 传输异常类型和安全处理后的异常信息
- 尝试编号和总尝试数
- 原始内容大小、压缩后大小、SHA-256 和完成状态

原始交换内容以 `audit-manifest-v2` 写入项目会话数据库：工件保存版本引用，版本链保存结构增量及有界检查点，大段正文和工具定义以 gzip 内容块共享。还原后的完整内容必须通过大小与 SHA-256 校验。每次物理尝试仍有独立工件和尝试编号，不合并重试记录。审计读取只接受这一种增量格式，具体存储规则见《项目、会话与存储》的“审计快照的增量存储”。`conversation_journal` 同时记录：

- `model.http_exchange.completed`
- `model.http_exchange.failed`
- `model.request_attempt.completed`
- `model.request_attempt.failed`
- `model.request_attempt.cancelled`

错误内容不进行跨供应商业务归一化，不根据 HTTP 状态码推断余额、配额、权限或限流原因。HTTP 响应正文、本地网络异常和本地协议检测信息分别按其原始来源保存。尝试事件通过 `artifact_id` 关联对应 HTTP 交换，整轮运行通过 `run_id` 关联全部尝试事件。

聊天错误卡片读取尝试事件和运行结算记录；实时卡片读取原有流事件。审计正文改用增量格式不改变这些入口，不改变重试、取消和最终结算时机。HTTP 审计正文写入失败时，尝试错误事件仍须独立保存。

审计失败只记录日志，不反向改变已经完成的模型请求结果；模型调用与审计存储保持职责分离。

## 十三、明确禁止的隐藏行为

本机制不包含：

- 按供应商或模型名称自动改变重试策略。
- 按 HTTP 状态码写隐藏重试次数。
- 无限重试。
- 功能会话自己的第二套重试。
- 自动重写正式历史消息。
- 把失败卡片注入模型上下文。
- 把不完整正文当成完整回答。
- 执行未完整接收的工具调用。
- 失败时重复写用户消息。
- 自动清理或截断原始请求响应审计。
- 用归一化文案、翻译文案或状态码业务推断替换原始错误内容。

## 十四、已验证场景

后端测试覆盖：

- 非流式传输异常后使用同一消息请求重试。
- 非流式空结果进入同一重试路径。
- 流式响应没有完成事件时重试。
- 流式重试次数耗尽后只暴露最终错误。
- 用户取消不重试。
- 最终失败只保留用户正式消息，并生成可恢复运行错误。
- 同一运行只能首次结算成功。
- 会话运行写入正确项目数据库，不生成嵌套错误数据库。
- 功能会话只创建一次并继承统一重试次数。
- 取消前、取消中、工具调用中取消的消息和上下文边界。

前端测试覆盖：

- 重试回滚未提交片段。
- 已完成工具轮次在重试后继续保留。
- 会话流恢复、分页和取消状态不受影响。
- 角色和会话设置契约可通过类型检查与生产构建。

本次实现完成时的验证结果：

- 后端完整测试：1002 项通过。
- 前端会话状态测试：175 项通过。
- 前端 TypeScript 检查通过。
- 前端生产构建通过。
