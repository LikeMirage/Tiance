# 隐式截断与隐藏默认值专项问题分析

> 记录日期：2026-08-18
> 目的：记录已经真实出现的隐蔽问题、形成原因、当前修复和后续专项审查方法。

## 一、真实出现过的问题

### 1. 前端只读取最近 100 条历史消息

早期实现把一次接口分页大小误当成会话总量上限。界面短期看起来正常，模型请求上下文却可能缺失更早消息，继而影响前缀缓存、记忆压缩和长会话一致性。

问题危险之处不在“100 是否够大”，而在没有任何地方告诉用户和调用方：返回的是不完整历史。

当前规则：

- 接口按游标分页，不设置隐式总条数上限；
- 需要完整上下文的调用方必须逐页读取到结束；
- 页面只展示一页不等于数据层只保留一页；
- 分页游标重复、页面重复或身份不一致时明确失败，不能静默提前结束。

### 2. Python 工具输出超过 8 MB 后被直接丢弃

旧执行器为 stdout 和 stderr 各设置固定捕获上限，超过后停止保留后续字节。普通工具很难触发，因此长期不易发现；一旦用于代码扫描、日志分析或大文档提取，模型拿到的却是不完整结果。

当前规则：

- 工具进程输出先进入可滚动到磁盘的临时文件，不再以 8 MB 为事实边界；
- 工具成功、失败、超时和取消都保留已经产生的完整输出；
- 内存中的流缓冲、界面事件队列仍可有容量控制，但那是传输与显示背压，不能改写持久化事实；
- 大结果是否进一步生成工件引用，应由正式工具合同决定，不能靠执行器偷偷截断。

### 3. 原始模型请求和响应缺少统一、完整、可核对的记录

会话消息能说明用户和模型最终看到了什么，却不能单独证明供应商实际收到的 HTTP 请求体、返回的原始流、状态码和响应头。数据分散后，协议适配、思考内容续接和供应商错误很难复盘。

当前增加两层记录：

1. `conversation_journal` 是项目内统一事件总账，按项目 event_id、会话、运行、轮次和工具调用建立关联；
2. 大体积原始交换保存为会话工件，数据库只保存路径、大小、SHA-256 和完成状态。

每次模型 HTTP 交换保存经过密钥脱敏的请求地址、请求头、请求体、原始响应字节、响应状态、响应头、错误类型和时间。流式响应使用磁盘滚动缓冲完整汇总，不把内存阈值变成截断阈值。

`conversation_messages` 仍是正式消息事实来源；事件总账用于审计和定位，不重复承担消息仓库职责。

### 4. 看起来安全的隐藏时间和回退策略

同一时期还发现过：工具超时缺失时自动补 60 秒、个体工具从总超时固定减 5 秒、项目身份缺失时回退到当前界面项目、聊天流按具体工具名称解释结果等问题。

这些代码往往出于“先让它能跑”或“避免出错”，但都在合同外改变了真实语义。当前对应改为显式清单字段、严格能力合同、明确失败、结构化资源失效和项目身份透传。

## 二、AI 编程为什么容易写出这类问题

1. **把局部性能措施当成全局业务边界。** 为一个列表减少渲染量时，AI容易直接在读取层切片；为防内存增长时，容易直接停止保存输出。
2. **只验证短样例。** 十几条消息、几 KB 输出和单窗口工具调用都正常，长期数据、并发和失败路径没有进入测试。
3. **偏爱“看起来安全”的默认值。** 60 秒、100 条、8 MB、固定重试次数都容易被当作常识写入，但产品没有授权这些语义。
4. **混淆展示、传输和事实。** 页面可以分页、网络可以背压、内存可以滚动到磁盘；这些限制不能反向删改数据库和原始工件。
5. **为了补当前错误增加特殊分支。** 按供应商、工具名或页面状态打补丁，短期有效，却把边界知识散落到不负责该业务的层。
6. **测试只证明成功，不证明完整。** “返回了结果”不等于“结果完整”；“列表能打开”不等于“历史未截断”。
7. **代码审查只看改动文件。** 隐式上限常在调用链另一端，必须沿“写入—持久化—读取—组装—展示”完整追踪。

## 三、开发中必须遵守的避免方法

### 1. 先写不可破坏的不变量

- 持久化事实不得被界面分页截断；
- 模型上下文不得因前端展示策略缺失历史；
- 工具返回不得无提示丢字节；
- 原始请求、响应和消息必须能按 run_id、turn_id、tool_call_id 关联；
- 缺少身份、能力或必要配置时明确失败，不猜测；
- 任何上限都必须说明作用层、超限行为和是否影响完整性。

### 2. 区分四种容量控制

| 位置 | 可以做什么 | 不能做什么 |
| --- | --- | --- |
| 界面展示 | 分页、虚拟列表、折叠 | 删除或少读模型事实 |
| 实时传输 | 背压、重连、要求重新同步 | 把溢出当作正常结束 |
| 内存 | 滚动到磁盘、释放已持久化副本 | 静默丢弃未持久化内容 |
| 永久存储 | 明确保留策略、用户可见清理 | 用硬编码常量偷偷截断 |

### 3. 所有限制必须形成显式合同

代码中出现 `limit`、`max`、切片、固定超时、固定重试和固定字节数时，必须回答：

1. 谁决定这个值；
2. 作用于展示、传输、内存还是事实；
3. 超限后是分页、落盘、报错还是丢弃；
4. 用户和调用方如何知道结果是否完整；
5. 是否有跨边界测试证明没有改变业务语义。

回答不清楚时，不得把该常量作为正式默认行为。

## 四、用 AI 做专项审查的方法

让 AI 审查时不要只问“有没有性能问题”，应要求它沿完整数据链给证据：

```text
审查本功能是否存在隐式截断、隐藏默认值或完整性丢失。

必须沿写入、持久化、分页读取、上下文组装、实时传输、界面展示和导出逐层检查。
搜索固定条数、固定字节、切片、超时、重试、队列上限、LRU 和 fallback。
对每一处说明：作用层、超限行为、是否影响正式事实、是否向调用方暴露 incomplete 状态。
重点验证长会话、大工具输出、流式错误、取消、重连、两个窗口和并发子会话。
没有代码证据时不得推测；不要为了显得全面制造不存在的问题。
输出必须包含文件位置、真实影响、复现条件和最小正确修复方向。
```

专项测试至少包含：

- 超过旧上限一倍以上的数据；
- 恰好跨分页边界的完整轮次；
- 单条超大事件与大量小事件；
- 流式错误发生在已经产生大量内容之后；
- 取消与超时后核对已产生内容；
- 多窗口领取同一前端工具请求；
- 原始工件大小和 SHA-256 与实际内容一致；
- 密钥、Authorization 和敏感查询参数未进入审计工件。

## 五、本次修复的验收基线

1. 超过 8 MB 的工具输出完整返回；
2. 一万条工具消息的精确轮次读取不形成总量截断；
3. 会话事件总账支持分页读取，而不是一次全扫或固定截断；
4. 原始模型流保存完整字节并附带大小与哈希；
5. 前端工具跨窗口只能领取一次；
6. 停止调用会话会释放前端等待，同时不谎称副作用已经回滚；
7. 所有工具清单明确声明运行类型、超时和是否允许并发；
8. 发布前执行工具市场构建、全量测试和密钥扫描。

这份记录不要求以后取消所有限制。正确目标是：限制放在正确层，行为可见、可验证，且绝不能静默改写正式事实。
