# 隐式截断、隐藏默认值与特殊化耦合专项问题分析

> 记录日期：2026-08-18
> 目的：记录天策已经真实出现的隐蔽问题，提炼共同根因，并形成后续开发、重构、测试和 AI 审查必须遵守的设计原则。

## 一、这类问题真正危险在哪里

这类问题通常不会立即报错：

- 代码可以编译；
- 页面可以打开；
- 普通样例可以通过；
- 短会话和小文件看起来正常；
- 新增测试甚至可能全部通过。

真正的问题是：程序在没有明确合同、没有用户确认、没有显式错误的情况下，悄悄改变了正式业务事实、通用数据结构或模块依赖方向。

它们表面上可能分别表现为“少了几条消息”“工具结果不完整”“来源 ID 看不见”“等待提前结束”，但根因高度一致：

```text
局部实现需要
    ↓
被错误提升为通用层规则
    ↓
通用事实、数据合同或执行语义被静默改变
    ↓
短测试正常，长期使用产生严重偏差
```

用户看到的异常只是结果。真正需要审查的是：某一层是否理解了本不属于它的业务概念，或者用自己的局部限制改写了更底层的正式事实。

## 二、已经真实发生的案例

### 1. 前端硬编码只读取最近 100 条历史消息

早期实现把一次接口分页大小误当成会话总量上限。界面短期看起来正常，模型请求上下文却可能缺失更早消息，继而影响前缀缓存、记忆压缩和长会话一致性。

这不是简单的“100 条够不够”问题，而是展示层的局部加载策略越界改变了模型事实：

```text
正确边界：
界面可以分页显示
模型上下文仍从完整持久化历史组装

错误边界：
界面只加载 100 条
模型也只能得到这 100 条
```

当前规则：

- 接口按游标分页，不设置隐式总条数上限；
- 需要完整上下文的调用方必须逐页读取到结束；
- 页面只展示一页不等于数据层只保留或只提供一页；
- 分页游标重复、页面重复或身份不一致时明确失败，不能静默提前结束；
- 必须使用超过旧上限一倍以上的数据验证完整性。

### 2. Python 工具输出超过 8 MB 后被直接丢弃

旧执行器为 stdout 和 stderr 各设置固定捕获上限，超过后停止保留后续字节。普通工具很难触发，因此长期不易发现；一旦用于代码扫描、日志分析或大文档提取，模型拿到的却是不完整结果。

这里不是“内存是否需要限制”的问题，而是内存层的容量控制越界改写了工具正式结果：

```text
正确边界：
内存有界
超出部分滚动到磁盘
正式结果保持完整

错误边界：
内存最多保留 8 MB
正式工具结果也只剩 8 MB
```

当前规则：

- 工具进程输出先进入可滚动到磁盘的临时文件；
- 工具成功、失败、超时和取消都保留已经产生的完整输出；
- 内存流缓冲和界面事件队列可以有容量控制，但不能改写持久化事实；
- 大结果是否生成工件引用由正式工具合同决定，不能靠执行器偷偷截断。

### 3. 原始模型请求和响应缺少统一、完整、可核对的记录

会话消息能说明用户和模型最终看到了什么，却不能单独证明供应商实际收到的 HTTP 请求体、返回的原始流、状态码和响应头。数据分散后，协议适配、思考内容续接和供应商错误难以复盘。

当前采用两层记录：

1. `conversation_journal` 是项目内统一事件总账，按项目事件、会话、运行、轮次和工具调用建立关联；
2. 大体积原始交换保存为会话工件，数据库只保存路径、大小、SHA-256 和完成状态。

每次模型 HTTP 交换保存经过密钥脱敏的请求地址、请求头、请求体、原始响应字节、响应状态、响应头、错误类型和时间。流式响应使用磁盘滚动缓冲完整汇总，不把内存阈值变成事实截断阈值。

`conversation_messages` 仍是正式消息事实来源；事件总账用于审计和定位，不重复承担消息仓库职责。

### 4. 工具超时和等待时间存在隐藏默认值

已经出现过以下行为：

- 工具没有配置超时时，执行层自动补 60 秒；
- 个体工具等待时从总超时固定减去 5 秒；
- 尚未达到真实终态时提前返回 `still_running`。

这些数值看起来是在“提高安全性”，实际上没有产品合同授权。执行层用自己的隐藏时间改变了工具“何时完成”和“调用方得到什么结果”的语义。

当前原则：

- 工具超时属于明确工具执行合同；
- 缺少必要配置时明确失败，不猜测一个默认值；
- 等待、后台继续和真实终态必须使用明确状态表达；
- 不能为了给另一层“预留几秒”而悄悄缩短用户配置的时间。

### 5. 项目身份缺失时回退到当前界面项目

某些前端工具曾在请求缺少 `project_id` 时，回退使用用户当前打开的项目。

这看似方便，却把界面瞬时状态变成了工具调用身份：项目切换、事件重放或旧请求恢复时，工具可能操作错误项目。

当前原则：

- 项目、会话和请求身份必须由调用合同明确传递；
- 身份缺失时明确失败；
- 当前界面打开什么不能替代工具调用属于什么；
- 前端状态只能用于展示和交互，不能猜测正式归属关系。

### 6. 聊天流按具体工具名称解释业务结果

聊天流或前端刷新逻辑曾按具体工具名称判断是否刷新主题等资源。

这会导致通用聊天层认识某个具体工具：工具重命名、替换、从市场安装另一实现或增加同类工具时，隐藏分支立即失效。

正确方向是：

- 资源自身产生稳定变更事件；或者
- 工具返回通用、受约束的资源失效通知。

通用层只理解“主题资源已变化”，不能理解“某个叫 `theme_designer` 的工具执行完了，所以刷新主题”。

### 7. AI 会话交互工具被耦合进通用会话数据结构

原始设计非常直接：`interact_ai_conversation` 在工具内部把来源会话名称和 ID 追加到任务正文末尾，然后把完整字符串作为普通 `user` 消息发送。

```text
任务正文

本条消息来源会话名称：...
本条消息来源会话 ID：...
```

通用会话系统只处理普通消息，不需要知道这条消息来自用户输入框还是另一个 AI。

#### 错误改造

在 v0.3.19 的一次改造中，来源后缀被替换成专用 `source_context`：

- 通用 `ChatMessageRequest` 增加 `source_context`；
- 项目会话领域消息增加 `source_context`；
- 数据库序列化开始保存该字段；
- 消息持久化和重复请求判断开始比较该字段；
- 模型请求组装把它转换为 `<conversation_source>`；
- 前端会话工具改为向通用链路传递 `sourceContext`。

错误依赖方向变成：

```text
interact_ai_conversation
        ↓ source_context
通用消息 Schema
        ↓
通用会话领域模型
        ↓
数据库持久化
        ↓
请求去重与模型上下文组装
```

这不是“来源信息是否显示”的问题。显示异常只是结果。真正的问题是：单个工具要求通用会话系统理解自己的专属语义，为 AI 向 AI 发送消息开了一条特殊数据通道。

它直接违反：

- AI 会话与普通会话使用同一结构；
- AI 发消息与用户发消息使用同一通路；
- 工具只能调用通用能力，不能反向要求平台底层适配自己；
- 工具可以独立安装、替换和删除；
- 通用数据库不能成为所有工具专属字段的集合。

如果接受这种做法，后续很容易继续出现：

```text
source_context
document_edit_context
memory_task_context
search_context
theme_context
```

最终会话系统将退化为各类工具的特殊适配层。

#### 为什么测试没有阻止错误

原测试明确验证消息末尾包含来源会话名称和 ID。错误改造时，这条测试被改成验证 `sourceContext` 对象存在。

这不是正常的测试同步，而是用新实现覆盖了旧产品合同：

```text
原行为发生变化
    ↓
修改原测试预期
    ↓
新实现测试通过
    ↓
行为退化被伪装成重构成功
```

正确规则是：已有回归测试保护的外部行为不得自行改变。若测试预期必须改变，首先要证明产品合同已经由用户明确修改，而不是因为新代码需要不同预期。

#### 当前修复

- 删除通用消息 Schema、领域模型、数据库序列化、持久化和请求组装中的 `source_context`；
- 删除专用来源消息服务；
- 恢复工具内部追加来源后缀；
- 拼接后的内容重新作为普通 `user` 消息发送；
- 回归测试重新验证完整普通消息正文。

当前依赖方向恢复为：

```text
interact_ai_conversation
├─ 组装任务正文
├─ 追加来源名称和 ID
└─ 调用普通会话发送能力
                    ↓
通用会话系统只认识普通 user 消息
```

## 三、所有案例的共同根因

| 案例 | 越界的局部规则 | 被静默改变的通用事实 |
| --- | --- | --- |
| 最近 100 条消息 | 前端分页大小 | 模型完整历史 |
| 8 MB 工具输出 | 内存捕获上限 | 工具正式结果 |
| 原始交换缺失 | 消息展示数据 | 供应商真实请求与响应证据 |
| 自动补 60 秒、固定减 5 秒 | 执行器便利策略 | 工具完成语义 |
| 缺少项目时回退当前项目 | 界面当前状态 | 工具正式身份 |
| 按工具名刷新主题 | 某工具实现名称 | 通用资源变化合同 |
| `source_context` | 会话交互工具语义 | 通用消息与数据库合同 |

共同错误不是某个数字、字段或函数写错，而是依赖方向反了：

```text
正确：具体功能依赖通用能力
错误：通用能力为具体功能增加特殊认识
```

## 四、天策必须坚持的设计原则

### 1. 通用事实只有一个来源

- 会话消息由统一消息仓库保存；
- 工具结果由统一工具执行合同返回；
- 模型原始交换由统一审计工件记录；
- 运行状态由统一会话运行系统维护。

不能为了某个页面、工具或供应商建立第二套事实。

### 2. 具体功能只能依赖通用能力

允许：

```text
工具 → 普通文件能力
工具 → 普通会话能力
工具 → 通用资源变更合同
供应商适配器 → 通用模型协议接口
```

禁止：

```text
通用会话层 → 判断具体工具名称
通用消息 Schema → 保存某个工具专属字段
通用执行器 → 猜测某个工具需要的超时
通用前端状态 → 猜测请求属于哪个项目
```

### 3. 不给任何工具、模型、供应商或功能会话开小灶

同一种能力必须走同一条正式通路。差异只能存在于负责该差异的适配器或工具内部，不能扩散到无关通用层。

- AI 发消息就是普通消息；
- AI 会话就是普通会话；
- 功能会话仍使用统一运行结构；
- 供应商协议差异留在协议适配器；
- 工具专属格式留在工具内部；
- 主题变化通过通用资源事件表达。

### 4. 展示、传输、内存和事实严格分层

| 位置 | 可以做什么 | 不能做什么 |
| --- | --- | --- |
| 界面展示 | 分页、虚拟列表、折叠 | 删除或少读模型事实 |
| 实时传输 | 背压、重连、重新同步 | 把溢出当作正常结束 |
| 内存 | 滚动到磁盘、释放已持久化副本 | 静默丢弃未持久化内容 |
| 永久存储 | 明确保留策略、用户可见清理 | 用硬编码常量偷偷截断 |
| 具体工具 | 组装自己的输入输出语义 | 修改通用消息或数据库合同 |

### 5. 所有默认值、限制和回退都必须形成显式合同

代码中出现 `limit`、`max`、切片、固定超时、固定重试、固定字节数或 fallback 时，必须回答：

1. 谁决定这个值；
2. 它作用于展示、传输、内存还是正式事实；
3. 超限后是分页、落盘、报错还是丢弃；
4. 用户和调用方如何知道结果是否完整；
5. 是否有跨边界测试证明没有改变业务语义。

回答不清楚时，不得把它作为正式默认行为。

### 6. 外部行为优先于实现整洁感

“结构化”“更干净”“更统一”“更安全”都不是改变产品合同的授权。

如果一个重构会改变以下任一项，就不是普通重构：

- 用户看到的正式内容；
- 模型收到的上下文；
- 数据库保存的业务事实；
- 工具输入输出合同；
- 模块依赖方向；
- 错误、等待、取消或完成语义。

必须先明确产品决策，再修改实现和测试。

## 五、修改前必须执行的边界检查

### 1. 先写不可破坏的不变量

每次任务开始前，至少写出与本次改动有关的不变量。例如：

- 工具发送的消息仍是普通 `user` 消息；
- 通用会话层不理解具体工具语义；
- 持久化事实不受界面分页影响；
- 工具返回不因内存限制静默丢字节；
- 项目和会话身份不能由当前页面猜测；
- 已有外部行为不因重构变化。

验证完成时逐条确认，而不是只报告测试通过。

### 2. 使用改动范围作为越界报警器

出现以下情况时必须停止并重新判断：

- 修改一个工具，却同时修改通用消息 Schema；
- 修改一个页面，却同时修改模型上下文组装；
- 修改一个供应商，却同时修改通用会话数据；
- 修改展示性能，却同时修改持久化读取范围；
- 修改工具等待，却同时引入全局固定超时；
- 修改资源工具，却要求聊天层识别具体工具名。

这些不一定永远错误，但属于高风险边界，不能作为顺手改动继续完成。

### 3. 不得用修改旧测试掩盖行为变化

当现有测试与新实现冲突时，先回答：

1. 测试保护的是实现细节还是产品合同；
2. 用户是否明确要求改变该合同；
3. 是否存在不改变合同的实现方式；
4. 为什么新增行为必须进入通用层。

没有明确答案时，保留原测试，修改实现。

### 4. 必须沿完整数据链检查

不能只检查当前文件。至少追踪：

```text
输入
→ 业务组装
→ 通用接口
→ 持久化
→ 分页读取
→ 上下文组装
→ 实时传输
→ 界面展示
→ 导出与审计
```

对每一层确认它是否只承担自己的职责。

## 六、用 AI 做专项审查的方法

### 1. 隐式截断和隐藏默认值审查提示词

```text
审查本功能是否存在隐式截断、隐藏默认值或完整性丢失。

必须沿写入、持久化、分页读取、上下文组装、实时传输、界面展示和导出逐层检查。
搜索固定条数、固定字节、切片、超时、重试、队列上限、LRU 和 fallback。
对每一处说明：作用层、超限行为、是否影响正式事实、是否向调用方暴露 incomplete 状态。
重点验证长会话、大工具输出、流式错误、取消、重连、两个窗口和并发子会话。
没有代码证据时不得推测；不要为了显得全面制造不存在的问题。
输出必须包含文件位置、真实影响、复现条件和最小正确修复方向。
```

### 2. 特殊化耦合审查提示词

```text
审查本次改动是否把具体工具、页面、供应商、模型或功能会话的语义耦合进了通用层。

先列出本次功能原本可以依赖的通用接口，再检查 diff 是否进入通用 Schema、领域模型、数据库、消息持久化、请求组装、聊天流或全局状态。
搜索具体工具名、供应商名、专属字段、隐藏 fallback、按名称判断和特殊分支。
如果一个具体功能的修改需要通用层认识它，必须说明为什么不能在适配器或工具内部完成。
保留所有保护既有外部行为的回归测试，不得通过修改测试预期证明重构正确。
分别核对用户看到的内容、模型收到的内容、数据库事实和模块依赖方向。
没有用户明确批准的数据合同变化，不得建议顺手扩展通用 Schema。
```

## 七、专项测试最低要求

- 超过旧上限一倍以上的数据；
- 恰好跨分页边界的完整轮次；
- 单条超大事件与大量小事件；
- 流式错误发生在已经产生大量内容之后；
- 取消与超时后核对已产生内容；
- 多窗口领取同一前端工具请求；
- 原始工件大小和 SHA-256 与实际内容一致；
- 密钥、Authorization 和敏感查询参数未进入审计工件；
- 工具发送消息仍通过普通消息合同；
- 通用消息 Schema 不包含具体工具专属字段；
- 工具重命名或替换后，通用资源刷新合同仍然有效；
- 身份缺失时明确失败，不回退当前界面状态；
- 原有回归测试未被无授权地改成新的产品预期。

## 八、发布前验收基线

1. 超过 8 MB 的工具输出完整保留；
2. 一万条工具消息的精确轮次读取不形成总量截断；
3. 会话事件总账支持分页读取，而不是一次全扫或固定截断；
4. 原始模型流保存完整字节并附带大小与哈希；
5. 前端工具跨窗口只能领取一次；
6. 停止调用会话会释放前端等待，同时不谎称副作用已经回滚；
7. 所有工具清单明确声明运行类型、超时和是否允许并发；
8. AI 间消息与普通用户消息使用同一通用数据结构；
9. 具体工具语义没有进入通用会话 Schema、数据库和请求组装；
10. 发布前执行工具市场构建、全量测试、密钥扫描和改动范围审查。

## 九、最终判断标准

不要只问“功能是否能用”，必须同时问：

1. 正式事实是否完整；
2. 行为是否由明确合同决定；
3. 具体功能是否只依赖通用能力；
4. 通用层是否被迫认识具体功能；
5. 测试是在保护产品行为，还是在替新实现背书；
6. 长期、并发、失败和恢复场景是否仍保持相同语义。

天策不是通过不断增加特殊处理获得能力，而是让项目、会话、消息、工具、供应商和前端能力都建立在少数稳定通用合同之上。任何局部优化只要反向污染这些合同，即使代码能跑、测试能过，也必须视为架构错误。
