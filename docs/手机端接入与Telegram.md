# 外部消息接入：Telegram、飞书、微信

实现日期：2026-11-11。现提供 Telegram、飞书应用机器人、微信 ClawBot 私聊入口。钉钉暂不实施；关闭天策后的自动唤醒仍为待实现事项。下文保留 Telegram 初版研究记录，当前跨平台合同以末尾“微信与飞书接入”一节为准。

## 使用

1. 在 Telegram 的 `@BotFather` 创建机器人，取得 Bot Token。
2. 天策「设定集 → 访问管理 → Telegram 接入」填写 Token，打开“启用 Telegram 接入”开关，即保存配置并验证连接；没有新输入或已保存的 Token 时提示填写。验证失败保持关闭，保留输入以便修改重试。使用天策已有的网络／代理设置，不要求公网监听。
3. 在手机私聊机器人发送 `/start`，在该设置页“允许访问的用户”区域打开自己账号的授权开关。说明放在此区域；开关只有授权请求成功后才更新。未经允许的用户不能查询项目、下载文件或执行任务。初次来信不会自动成为管理员。
4. 通过按钮选择集、分类、项目、会话；此后直接发送文字。发送 `/new 标题` 创建普通主会话，采用该集已配置的默认角色。

天策后端和一个桌面会话入口需要保持在线，可以最小化到托盘。Token 加密保存在全局数据库，接口只返回「是否已保存」，留空保存会保留原 Token。迁到其他 Windows 账号／电脑后可能需要重新填写 Token。

启用开关直接使用后端确认的状态，没有第二个“保存并连接”按钮。关闭接入时保留凭据与授权记录，使用原连接配置关闭，不需要重新验证 Telegram 网络。修改 Token／Bot API 前先关闭接入，修改后重新开启；已有 Token 不必重复输入。切换机器人连接仍按各自保存的启用和授权状态显示。

### 设置页标签（2026-11-11）

复用 GitHub 登录页的 `SettingsViewTabs` 和 Markdown 帮助展示方式，Telegram 内部提供五个标签：

| 标签 | 内容 |
| --- | --- |
| 连接配置 | Token、启用开关、高级 Bot API 地址、通道状态与用户授权开关 |
| 记录日志 | 当前机器人连接的接入事件，按时间倒序、每页 50 条，手动刷新 |
| 快速开始 | BotFather 创建机器人、填写 Token、允许自己的账号、选择项目和会话、发送第一条消息与文件的具体操作 |
| 指令与文件 | 指令表、切换目标与回复归属、文件暂存与提交方式 |
| 常见问题 | 连接超时、502、Webhook 冲突、文件限制、代理、关闭程序与日志范围 |

切换内部标签保留尚未提交的 Token 和地址输入；只有“连接配置”可见时才每 5 秒读取状态。日志页只在进入、翻页或手动刷新时查询，不新增轮询。帮助内容提供中、英、俄三种内置版本，来源为 `2_ReactWeb/src/features/mobile-access/content/`。

日志使用现有全局数据库 `mobile_records` 的 `activity` 命名空间，按连接隔离；不新增数据库版本。`GET /api/mobile/telegram/logs` 接受可选 `connection_id`、`offset`、`limit`，通过索引分页查询，不先加载全部历史。

每个连接保留最近 **1,000 条**诊断事件，写入时淘汰更早事件。此范围只影响诊断记录，不清理正式会话、收件去重、待发送结果或用户授权。记录启停、配置失败、授权变化、消息/按钮接收、文件收件、任务提交/结算和回复发送失败/成功；连续接收故障只记录首次及恢复，不按每次重试重复写入。不记录 Token、请求 URL、异常原文、聊天正文或文件内容，只保留事件、时间、身份/任务 ID、错误类型及可取得的 HTTP 状态码。日志写入失败不改变消息提交和回传结果。

这些是接入诊断，不是所有外发工具的完整审计，也不会补造升级前的记录。正式消息与工具调用仍到对应会话查看；尚未成功验证机器人的首次配置失败暂存于未绑定连接范围。

自动唤醒当前没有实现，设计和验收边界已写入 [待完善事项](20_待完善.md#手机消息自动唤醒与统一接收入口暂不实施2026-11-11)。

网络使用「系统代理」时，Windows 下自动读取代理软件写入的系统代理地址，无需为 Telegram 单独填写端口；网站分流仍由代理软件的规则决定。系统代理开启、关闭或端口变化会在下一次网络请求时生效，正在进行的请求不会因天策刷新连接池而被强制中断。只开启代理软件而未启用它的系统代理功能，不能保证天策流量进入代理；当前不执行 PAC 自动配置脚本，也不自动探测第三方代理端口。

每条操作回执、正式结果都有项目／会话信息及操作按钮。点击「回复此会话」立即切换手机端选择；在 Telegram 原生回复一条已映射的机器人消息，发出后也会切换到它所属的会话。无法识别旧消息时明确拒绝，不猜测目标。

三种渠道的连接配置页均提供「消息接收提醒」，按当前连接保存，默认开启。关闭后仅省略提交成功时的「已接收，正在提交到会话」回执，错误、权限请求、文件收件结果、最终回复和工具主动发送的消息照常返回。调整此项即时生效，不重连机器人；重新扫码或启停同一连接保留原设置。微信重新绑定后若旧数字菜单已失效，会明确提示并重新显示菜单，不把旧编号解释为新选择或 AI 消息。

| 指令 | 作用 |
| --- | --- |
| `/projects` | 集 → 分类 → 项目 |
| `/sessions` | 当前项目的主会话；选中会话后可进入它的下级分类 |
| `/new [标题]` | 在所选项目创建并选中主会话 |
| `/status` | 当前项目、会话、模型与运行状态 |
| `/stop` | 暂停手机当前选中的会话 |
| `/files` | 当前会话待提交的文件引用 |
| `/clear` | 清除当前会话待提交的引用，保留已下载的工作文件 |
| `/help` 或 `/start` | 操作说明 |

AI 子会话、对话分支、自动命名、记忆压缩、项目记忆管理、全局记忆管理按实际分支数据分别展示，可继续进入任意深度的下级。各集共用项目／会话查询，不对每个集另写运行逻辑。

## 文件与回复

手机文件保存到目标项目的 `远程收件/Telegram/<随机目录>/<原文件名>`，文件名作 Windows 路径字符清理，完整保留文件内容。目录必须实际位于目标工作区之内。

- 普通文件先保存并暂存引用，随后发送处理要求才交给 AI。
- 单个文件带说明文字时，完整下载后把说明和文件一起提交。
- 相册有多条异步消息，第一版只收件，明确提示用户再发一条处理要求，避免第一个图片到达就开始处理。
- 图片通过现有 `image_ref` 输入；其他文件通过现有项目文件引用。录音不会被接入模块私自识别，仍由所选模型和工具处理。
- 文件归属在接收时确定。下载过程中切到 B，A 的文件仍保存、暂存和提交到 A。
- 下载失败时不把缺少文件的要求交给 AI；原文件不修改。

只回传本轮最终正式回复、失败或暂停信息，不发送思考和工具过程。没有正式内容也明确告知。长回复分成多个 Telegram 消息发送，正文不截断；第一版按纯文本发送，不额外转换 Markdown 表格，也不自动上传回复中提到的本地交付文件。

Telegram 官方云端 `getFile` 下载上限是 20 MB。设置页可填写自部署的 Local Bot API 地址；它需要用户另外部署，天策不会自动安装。若 Local Bot API 返回服务端绝对路径，只有 API 在本机时才直接复制该文件。参见 [Telegram Bot API](https://core.telegram.org/bots/api#getfile) 和 [Local Bot API](https://core.telegram.org/bots/api#using-a-local-bot-api-server)。

## 复用边界

代码集中在后端 `app/services/mobile/` 和前端 `features/mobile-access/`：

| 部分 | 职责 |
| --- | --- |
| `context.py` | 通用项目／会话定位、分支分组、普通会话创建、工作区收件路径 |
| `desktop_bridge.py` | 通用手机消息准备、运行身份、前端能力桥事件和结算结果 |
| `mobile_repository.py` | 通用外部身份、选择、收件、任务和回传记录 |
| `telegram_transport.py` | Telegram HTTP、文件下载、平台消息长度、Token 日志脱敏 |
| `navigation.py` / `catalog_navigation.py` | 通用导航、项目与会话操作；平台负责菜单编码，不注入模型上下文 |
| `service.py` | 三平台共用的生命周期、授权、收件、任务与回传协调 |
| `useMobileDesktopBridge.ts` | 调用现有 `buildConversationRunRequest`，使用指定会话配置与现有 client tool 执行器 |

创建会话抽到 `application/conversation_creation.py`，HTTP 手动入口和手机端共用；手机创建传 `created_by=user`、`activate=False`，不成为 AI 子任务，也不修改电脑当前选择。

发送复用普通 `ChatCompletionRequestBody`、`ProjectConversationStreamService`、`ConversationRunManager`，记录仍在项目 `.Tiance` 的正式会话数据中。手机端不直接调用模型供应商，也不依赖独立会话管理工具程序。前端只组装同样的请求和服务已有能力桥，后台实际运行、落盘和重试仍由现有后端管理。

工具审批沿用原会话设置。出现需要询问的工具权限时，Telegram 展示本次权限范围并提交同一个 permission bridge 的一次性决定，没有为了远程使用自动放行工具。

## 必须维持的行为

- 手机选择按机器人、聊天、用户保存，与桌面活动页和输入草稿分离。
- 接收到消息即冻结目标；任务完成只向原聊天回传，不改变后来选择的会话。
- 忙会话拒绝新输入并提示重发；不自动排队、不隐式暂停。准备阶段防重与后端原有运行锁两层共同保护。
- 接收 Telegram 消息不等待模型完成，A 运行中可以切到 B。暂停按钮绑定原任务；后端在运行锁内核对 `expected_run_id`，不会误停后来启动的任务。
- 必须收到整个 run 的结算，不能把一次模型 `done`、工具结束或连接关闭当成整轮成功。
- 接收队列要求重新同步时，只重新订阅同一轮运行；若该轮已经结束则按原用户消息读取落盘结果，不能订阅后来的任务，也不能重新发起模型请求。
- 撤销授权会取消尚未提交的手机消息，并恢复其待发送文件引用；已获准且已经开始的任务不因此被强制取消。
- 桌面请求准备失败、连接消失、文件失败、运行失败都有明确回执。60 秒桌面在线判定只是入口存活检测，不是模型或工具执行超时。
- 关闭程序仍走原退出协调器取消和落盘，手机模块只停止收件并等待同一套运行收尾。重启不擅自重放未确认的手机任务。

## 保存、重试和边界

全局数据库版本 52 使用以下结构，通过现有事务迁移保留 v51 的凭据、授权、选择、暂存文件引用和待回传任务，不重写项目会话历史：

| 表 | 内容与隔离方式 |
| --- | --- |
| `mobile_connections` | 连接 ID、平台、平台端机器人 ID、加密配置；`platform + remote_id` 唯一。换成另一个机器人的 Token 会新增／选择另一连接，不覆盖旧连接身份 |
| `mobile_records` | 授权用户、手机选择、按钮、消息映射、暂存引用、收件箱、活动任务、发件箱等；按 `namespace + connection_id` 索引查询。用户状态的键同时包含连接、聊天和用户身份 |
| `mobile_receipts` | 按连接 ID（历史列名 channel）和平台 update ID 去重，连接之间不共用 offset 或接收回执 |

一个连接可允许多个用户，用户各有聊天与会话选择；不同机器人也可分别启用。在设置页保存不同机器人后，可用连接选择器分别管理。当前仅有 Telegram 适配器，其他平台未实现，不能因为表里能存某个平台就误认为能通信。短事务完成去重及引用移交，不在事务中等待网络或模型。

所有连接共用一个 `MobileDesktopBridge` 和原普通会话运行入口。连接适配器使用自己的 scoped repository、收件循环和发件循环。未来平台需注册接收适配器、实现它自己的身份提取／协议及指令，而不用新建会话运行系统。任务结束只清理活动 job；不会删除用户授权、会话选择或正式历史消息。不另外保存一份全量聊天正文日志。

`update_id` 入库成功后才推进 Telegram offset；重复投递不重复执行。控制操作与文件下载、模型任务独立。进程中断时已开始处理但未确认完成的输入不自动重发，会在恢复时提示检查。

正式结果先入发件箱，发送成功后记录 Telegram message_id 与原会话映射；网络失败只重试回传，不重跑模型。遵守 Telegram `retry_after`，其他连接故障退避重试。Telegram `sendMessage` 没有客户端幂等键：极端情况下，服务端发送成功但响应丢失，重试可能重复显示一条结果；不能承诺网络层「恰好一次」，但不会因此重复执行 AI 任务。

无活动时接收使用 30 秒长轮询，桌面连接使用 20 秒长轮询；内部空队列低频检查，设置页只在“连接配置”标签打开期间每 5 秒更新状态。HTTP 连接等待 10 秒、普通 Bot API 读写等待 30 秒、长轮询等待 40 秒、下载单次无数据等待 60 秒；这些是传输失败判定，不改变角色重试参数或工具 `runtime.timeout_seconds`。

设置页区分状态查询错误、保存／授权操作错误和后端报告的 Telegram 通道错误。状态查询恢复成功后自动清除该查询的旧错误，不清除保存／授权失败，也不掩盖后端仍报告的通道故障；状态查询失败或通道故障期间不显示“已就绪”。这只是设置页显示状态，不停止正在运行的手机会话。回归测试覆盖暂时 502 后恢复、操作错误保留和真实通道错误保留。

已有 Webhook 会明确拒绝连接，不自动删除其他服务的配置。当前只处理私聊，不处理群聊、频道、编辑旧消息或 Telegram 帖子。首次验证采用临时数据库和模拟 Telegram／模型响应；需要用户填入 Token 后再验证实际网络、机器人权限及手机体验。

2026-11-11：手机接入、普通会话创建默认角色、数据库升级、运行管理相关测试共 80 项通过；前端手机请求桥测试和生产构建通过。覆盖接收去重、授权、Webhook 冲突、文件归属与完整下载、原会话配置、暂停身份校验、断线重订阅、最终结果回传失败重试。测试未连接真实机器人，未调用真实模型。

同日补充系统代理修复：代理解析、连接池回收、网络设置、手机接入、请求审计、模型请求头和 GitHub 认证相关测试共 140 项通过。覆盖系统代理开启／关闭／换端口、保存相同配置后刷新，以及旧模型流不中断。使用天策内置 Python、系统代理模式实测 Telegram 公共入口返回 HTTP 200；测试进程故意设置失效的代理环境变量，仍正确采用 Windows 系统代理。未修改用户保存的网络配置，未发送机器人消息，也未调用模型。


## 可见消息来源与文件外发（2026-11-11）

新收到并正式提交的手机用户消息，在正文末尾追加以下普通文本；界面、历史保存和模型请求使用同一正文。图片消息的 text content part 也使用相同文字。旧消息不追溯改写：

```text
[消息来源]
平台：Telegram
连接 ID：telegram:123456
用户 ID：987654321
聊天 ID：987654321
```

用户 ID 与聊天 ID 分开保存。当前只收私聊；保留这些字段不意味着已支持群聊。来源标注让 AI 自行选择目标，不是权限凭据，入站授权仍使用实际平台身份。

独立工具“对外消息发送”（调用名仍为 `external_send_file`，目录 `Data/tools/0efca349-3362-5aa1-8f15-203dab248ea2`）默认启用、动态加载。提供 `list_connections`、`send_text` 和 `send_file`。发送必填连接 ID、聊天 ID；纯文本使用 `text`，文件使用 `file_path` 和可选附言 `caption`。只发送明确指定的目标；不追溯最后一条消息、不要求由手机发起、不区分主／子会话，也不限工作区内文件。用户可以依照普通工具策略控制凭据使用、文件读取、外部修改和网络权限；纯文本不需要文件路径或文件读取权限。

外部用户消息的普通可见来源标注会说明：渠道不展示思考、工具调用与中途文字，只自动回传最终回复或错误。AI 可以按需通过已启用的发送工具主动汇报进度、询问或通知。当前仅单向发送，不新增等待回复、收件订阅、任务暂停或会话切换；必须等用户答复才能继续时，AI 应发送问题后结束本轮，等用户按现有入口发送下一条消息。工具返回 `sent` 只代表平台确认，不表示已读或已答复。

工具只声明 `external_messaging` 后端能力桥，使用标准 SDK。后端读取加密的连接配置并负责 Telegram 上传，密钥不进入工具参数或文件。文件按块上传，不整份转成 Base64 或读回内存。调用所在项目／会话名称会附在文件说明中，过长附言完整拆成后续文字消息。

| status | 含义 |
| --- | --- |
| sent | 全部发送已获平台确认 |
| not_sent | 连接未建立或平台明确拒绝等已知失败 |
| unknown | 发送中断／响应丢失，不能判断是否送达；先检查目标聊天 |
| partial | 部分内容已确认，后续内容未全部确认；查看 message_ids，不能盲目重发整个文件或整段文字 |

该工具不使用最终回答的自动重试发件箱，也不自动重试上传。工具总时限由自身 `runtime.timeout_seconds` 配置，SDK 等待复用它；上传网络空闲超时使用天策网络设置。工具取消或外层超时不能撤回已经送达的文件，也不能据此认定发送失败。官方云端的文件大小限制由 Telegram 返回错误，天策不暗中截断文件或强制压缩。

### 必须区分的配置

1. 机器人接收消息选择 Stream，与卡片回调选择 Stream 是两处配置。创建卡片时要明确 `callbackType: "STREAM"`；仅在应用后台开启机器人 Stream，不能保证收到卡片点击事件。官方百科区分普通版和高级版，普通版文档不提供 Stream 回调，应使用支持它的新卡片 API。[官方卡片回调说明](https://open-dingtalk.github.io/developerpedia/docs/learn/card/intro/#我的应用设置了-stream-模式为什么在-stream-通道上收不到卡片回调)
2. Stream 负责钉钉向应用推送消息/事件，发送或更新卡片仍调用 OpenAPI；不能把它当成任意双向 RPC 通道。[官方 Stream 协议](https://open-dingtalk.github.io/developerpedia/docs/learn/stream/protocol/)
3. 卡片需要可用的模板 ID、对应的应用关系、变量与按钮动作配置。官方示例展示模板和回调，不应笼统写成“所有模板必须发布后才可测试”；具体保存、测试和发布流程按当前模板平台规则验证。[官方卡片回调教程](https://open-dingtalk.github.io/developerpedia/docs/explore/tutorials/stream/bot/go/card-callback/)

### 天策的实现方向（建议，未实施）

- 首版用“应用机器人 + Stream + 互动卡片”，先完成私聊。应用凭据使用 Client ID / Client Secret；Python 接收可参考 [钉钉官方 Stream SDK](https://github.com/open-dingtalk/dingtalk-stream-sdk-python)。卡片模板及应用权限需要真实账号配置后联调，本轮没有实测钉钉发送或点击回调。
- 通用部分复用已有连接/授权、用户的项目和会话选择、文件收件、普通会话创建与请求组装、任务回传及诊断记录。各集查询及递归分支仍复用 `context.py`，不为钉钉另建一套项目管理。
- 平台部分增加 DingTalk 接收适配器、身份与文件标识转换、卡片创建/更新/回调适配器。不能沿用 Telegram 用户 ID、按钮数据格式或消息 ID。
- 项目列表、分页和任意深度子会话导航由天策生成卡片数据；钉钉提供交互载体，不提供天策项目查询。界面不展开整棵树，而是显示当前层、返回上级及分页。
- 每次卡片操作核验连接、用户授权和动作目标；更新/过期卡片不能误切目标，选择别的会话不能改变旧任务回复去向。模型和工具仍走普通会话流程。
- 固定快捷入口可后做；第一版在机器人消息中放导航卡片即可覆盖核心交互。文件大小、回传权限、API 配额、卡片模板可用性及回调重试语义需联调核验，不套用 Telegram 的限制值。

### 手机创建后桌面列表不刷新的修复

### “文件接收失败：接入记录不属于当前连接”的根因

接入适配器使用连接隔离的仓储，全局桌面入口使用全局仓储。纯文字任务提交时，全局入口原本会凭空写入一条空的 `staged` 文件暂存记录，连接归属为空；同一用户/会话随后上传文件时，连接隔离检查拒绝更新该记录。问题不在语音下载 API，也不能通过放宽连接隔离解决。

现在没有待消费引用时不创建暂存行，有引用时消费操作明确沿用发起用户的连接归属，并在同一事务中写入任务。启动时只清理此连接已知用户名下、归属为空且不含任何引用的错误占位行；不接管其他连接、不删除非空引用或工作文件。

另一个问题是已失败的下载任务仍留在后续消息等待列表里。现在只跟踪进行中的下载：已结束的任务立即移出，成功文件仍由持久暂存引用保存。某条要求正在等待的下载失败，只拒绝这一条要求并说明原因，后续文字可以继续；`/clear` 同时解除对旧下载的等待，下载完成也不重新附加已清除的引用。不支持的消息不进入收件和提交状态。

钉钉接入本轮暂缓，待用户进一步了解并确定接入方式后实施；未修改钉钉功能。

### 微信 ClawBot

依据腾讯公开的 [openclaw-weixin](https://github.com/Tencent/openclaw-weixin) 及其 [HTTP 协议说明](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol.md)，可研究直接编写 Python 适配器；没有必要为了接收微信消息引入另一套 Agent 运行系统。公开说明基于插件客户端，不能当作完整、永久稳定的服务端承诺。

- 登录走扫码绑定，必要时输入手机显示的验证码，成功后取得机器人凭据；接收采用 HTTPS 长轮询。不是公众号、企业微信 Webhook 或 Telegram BotFather Token。
- 公开消息模型含文字、图片、语音、文件和视频，未看到 Telegram 式原生按钮回调。因此首版建议采用文字菜单。媒体需要按协议下载/上传和解密/加密；语音可能附带转写，不代表所有语音都一定有。
- 回复应保存并带回来源的 `context_token`。插件在缺失时仍尝试发送，但文档明确说这不能证明服务端会接受，不能据此承诺只填任意用户 ID 就能主动发送。该字段属于通道回复凭据，不是模型上下文。
- 文件大小、回复凭据有效期、账号可用条件和故障恢复需要真实账号验证，本轮不填猜测限制，也不照搬插件内的暂停/重试时长作为天策统一规则。

拟议数字菜单如下（不是当前可用命令）：发送“菜单”后显示“1 选择项目、2 选择会话、3 最近五轮、4 切换模型”。用“选 2”执行对应动作，普通数字仍作为聊天内容；如以后允许纯数字，必须有明确的菜单选择状态及退出方式。每页编号映射到稳定对象 ID，按连接、用户及聊天隔离；翻页、过期或目标被删除时不得按新列表位置误操作。项目/会话选择沿用手机独立选择状态，任务创建后固定目标，不随下一次菜单选择变化。

### 复用边界

现有 `MobileRepository` 已按平台连接保存配置与记录，`manager.py` 和 `messaging.py` 有接收/发送适配器注册点；`context.py`、`catalog.py`、`models.py`、`history.py` 和 `desktop_bridge.py` 可复用项目查询、普通会话创建、配置修改、历史读取及运行入口。

但当前 `MobileService` 本身仍是 Telegram 适配器，管理器的配置/状态接口和部分公开连接字段也使用 Telegram 结构。后续接入时应将这些平台配置、身份、媒体和菜单格式放到各自适配器，提取实际共用的接收去重、目标绑定、文件暂存和任务回传流程；不能直接复制 Telegram 服务或声称现在只填两项凭据就已支持另一平台。

飞书用卡片承载动作，微信用数字菜单承载同一组业务动作。两者继续沿用普通会话、可见来源说明、失败收件不阻断后续文字、完成后只回传最终回复/错误/暂停的规则。设置页沿用连接配置、记录日志、快速开始、使用说明、常见问题等标签，具体授权和创建步骤分别编写。钉钉及关闭程序后的自动唤醒仍保持待实现。


## 多连接账号管理（2026-11-12）

微信再次扫码可能得到另一条独立连接，不会自动替换或关闭原连接。此前配置页只列出当前连接下的用户，导致新账号扫码后旧账号仍在运行、却不在当前列表中；关闭新账号授权也不会关闭旧账号。现场只读核对确认是两条独立连接分别保留授权，不是旧账号绕过授权校验。

三平台现在统一显示本平台全部连接下的用户，每个用户标明所属连接、授权状态和连接是否启用。用户列表显示“已授权人数 / 全部账号数”，不把连接启用数量当成授权状态。连接凭据、“启用当前连接”开关和访问范围仍作用于当前所选连接。修改另一连接的账号授权不会切走当前配置页面，也不会把其范围设置套到别的连接上。

账号列表按不可变标识稳定排序，不能直接沿用通用记录仓库的 `updated_at` 顺序，否则每次修改授权都会把账号移到末尾。此排序只作用于账号展示，不改收发队列的时间顺序。连接选择使用已有 `OptionSelect` 一体式主题下拉框；访问范围恢复单列，账号名称为 ID 时不重复显示一遍 ID。

账号所属连接以数据库 `mobile_records.connection_id` 列为准，平台以对应 `mobile_connections.platform` 为准。全部账号列表和授权、删除操作的连接查找共用这份归属事实，不能依赖 JSON 内容中的重复字段。旧 Telegram 账号的 JSON 没有 `connection_id`，但数据库归属和授权均完整；此前全部账号列表按 JSON 字段过滤，误显示为“暂无接入用户”。现改为按数据库归属关联查询，保留原授权、选择和历史记录，无需重新绑定或补写真实数据。回归覆盖三个渠道的字段缺失、字段冲突及跨平台隔离。

三平台设置页面使用整个看板宽度，不再给内容区和表单分别设置固定最大宽度。宽窗口下用户列表与访问范围按比例分配空间，窄窗口下改为上下排列。访问管理采用固定标题和标签导航、独立滚动内容区，切换渠道不对整页文字做滑动变换。三个渠道统一先显示当前连接、启用开关，再显示各自凭据；连接选择行在首次加载时保留并禁用，状态提示保留一行位置，避免数据返回后插入字段把后续内容推下去。

- **关闭授权**：拒绝该账号后续指令；已接受的操作与授权变更串行，待提交任务继续复用提交前授权检查，不偷偷中断已经启动的普通会话。
- **删除用户**：清除该连接下该用户的授权、选择、菜单、回复凭据、待发送引用及待收发消息，并在同一事务中保留最小的删除标记（`mobile_records/deleted_peers`，仅身份键和布尔值，不保留用户资料）。后续来信、`/start` 和旧按钮回调直接忽略，不再建立待授权记录或发送授权提示；重启、关闭再开启连接、普通保存连接配置不会清除此决定。尚未分发的收件在统一入口检查标记后消费，不提交模型任务或下载附件。此规则由三个渠道共用。
- **重新接入已删除用户**：微信由用户重新获取二维码并扫码确认，才清除确认本人在对应连接下的删除标记并建立新授权；不会恢复旧菜单、会话选择或其他已删除用户。Telegram、飞书需要在电脑端删除并重新添加所属机器人连接，再由用户发送 `/start`、在电脑端授权；重建连接也会清掉该连接其他用户的设置。仅临时停止访问应使用授权开关。用户删除和扫码确认与消息分发串行，避免新消息登记覆盖删除决定。
- **删除连接**：先停止该连接的接收和发送循环，再在事务内删除凭据和该连接的接入记录；其他连接继续运行。删除当前连接后切到剩余连接；删除最后一条后显示未连接状态。
- 两种删除都不删除项目文件、已落盘附件或项目中的正式会话。平台消息去重凭据保留，避免重新绑定后重放已经处理过的消息。
- 若仍有待提交/运行中的手机任务或正在处理的文件，删除会明确拒绝，提示先暂停或等待处理结束；可先关闭授权。不能通过删除接入身份悄悄丢弃运行中的任务及其结果。

账号删除和授权共用运行层的派发锁与桌面提交锁；连接删除还停止对应适配器。列表刷新与配置修改由管理器串行，防止删除中途的状态查询重新装载已删除的连接。前端对删除使用确认弹窗，失败保留原列表与错误提示；迟到的轮询不能覆盖刚完成的操作。

回归覆盖双账号显示与隔离、关闭后新指令拒绝、重启后授权持久化、删除后重新来信待授权、跨平台删除拒绝、活动任务删除保护、停止接收、删除最后一条连接，以及三平台前端的确认/取消、删除失败和迟到响应。测试使用隔离数据库和模拟传输；未修改用户真实授权，也未向手机发送测试消息。

三渠道专项复核：账号管理的上述后端场景分别使用微信、Telegram、飞书适配器执行。另用 Telegram 原生消息/按钮回调和飞书原生消息/卡片回调验证：关闭连接或撤销账号授权后，已有按钮和新指令均不能执行；删除账号后再次来信不会重新登记，重新接入也不会恢复已删除的旧按钮。同一用户连接两个机器人时，授权、删除、重启恢复互不影响；同一全局数据库中的其他平台账号不受删除影响。删除失败时用户数据和删除标记一起回滚；已接收但未分发的事件、重启后事件、重新启用连接均不能重建已删除用户。微信重新扫码只恢复本次明确确认的本人。前端三渠道均检查全部账号展示、修改旧连接账号时保持当前配置选中项，以及删除确认与失败恢复。此复核是隔离数据与模拟平台事件的回归测试，不代替真实平台端到端收发验收。

## 微信与飞书接入（v0.3.43，2026-11-11）

### 统一合同

外部平台只是普通会话的另一输入输出入口。连接、用户授权、手机选择、菜单、去重、文件暂存、提交任务、待回传结果全部使用全局库的 `MobileRepository`，按连接和用户隔离。正式消息、工具调用、模型请求与审计仍属于原项目会话。不同平台不会各自维护一套模型运行系统，不以电脑当前页面判断消息归属。

`manager.py` 注册三个适配器；`service.py` 共用收件、授权、文件落盘及最终回复流程；`navigation.py`、`catalog_navigation.py` 共用项目分类、项目、主/子会话、模型选择、最近五轮历史和关系图操作。`desktop_bridge.py` 与前端 `useMobileDesktopBridge.ts` 继续调用手动操作使用的会话创建及消息提交流程。

飞书使用应用机器人长连接，卡片按钮通过 `card.action.trigger` 进入上述导航。传输实现位于 `feishu_transport.py`、`feishu_events.py`、`feishu_frames.py`；仅实现所需协议字段，不引入完整飞书 SDK。App Secret 加密保存；首次发送者需在天策允许。事件持久化后才确认接收，消息 ID 去重。发送使用稳定 UUID；长连接断开后重连。

2026-11-12：飞书新连接改用二维码创建。`feishu_login.py` 对接飞书官方 `https://accounts.feishu.cn/oauth/v1/app/registration` 的 PersonalAgent begin/poll 流程，遵循接口返回的轮询间隔、有效期及 slow_down；取消、过期和异常明确反馈。临时 device_code 和创建得到的密钥不返回前端。获得凭据后复用 `manager.configure_platform` 的身份验证、加密保存和接收器，不另建会话/权限流程。二维码有效期只约束授权等待，不中断后续验证或写库；验证保存期间禁止重复创建。失败不覆盖已有连接，既有控制台连接仍可启停、删除和管理。

扫码成功创建应用不等于机器人接口可用。实际测试曾遇到 tenant token 接口返回 21001（平台策略限制），此时不得显示接入成功或保存为可用连接。不能由此断言手机号或豆包登录账号必然不支持；控制台创建与 PersonalAgent 创建属于不同入口。页面保留完整错误与换账号/联系平台的指引。首次私聊仍需天策本机授权。扫码创建入口可能显示 OpenClaw 来源确认，不需要安装 OpenClaw，也不改变天策的运行机制。

微信使用腾讯公开的 iLink/ClawBot 协议，扫码凭据与本人授权确认完成后才报告连接成功。`wechat_login.py` 处理二维码和验证码；`wechat_transport.py` 处理收发；`wechat_media.py` 按协议分块解密/加密媒体。凭据失效明确提示重新扫码。不是个人微信客户端自动点击，不接入群聊。

`wechat_navigation.py` 保存每个用户的选择模式和菜单栈。菜单模式数字选项只操作菜单；进入会话后，完整文字消息 `5` 查看前5轮对话，`00` 暂停当前任务，`0` 返回上一级，`menu` 直接回集选择，其余普通数字发送给 AI。`05`、`000` 和包含这些词的长文字仍是普通消息；文件附带的 `5`、`00` 或 `menu` 说明不会作为快捷指令吞掉文件。菜单中的 `5` 仍选第5项，`00` 不会暂停任务；创建项目或分类时的名称 `5`、`00` 仍是名称。暂停复用共享 `stop` 动作，固定到接收指令时选中的会话，不退出会话、不改变待发送附件，等待原任务保存后回报结果。`/new` 在分类、项目、会话列表按当前层级创建，在会话内明确拒绝。选择「新建主会话」或在会话列表发送 `/new` 时，直接复用普通会话创建流程，以默认标题和该集默认角色创建并进入会话，不等待下一条消息起名；`/new 名称` 仍可指定标题。只有新建项目、分类未提供名称时才进入名称输入状态。异步 AI 回复不能覆盖当前菜单和编号；失败的选择或创建会恢复原菜单，不能把用户带入不存在的会话。工具审批以单独的 `/action <编号>` 执行，不覆盖菜单状态。

### 文件与发送工具

手机原文件保存到 `远程收件/<平台>/<随机目录>/<原文件名>`，目标在接收时固定。共用的 `context.incoming_path` 先确认项目存在、校验路径位于工作区内，再创建收件目录；各渠道下载器负责写入临时文件、下载完成后更名，成功后才添加待发送引用。不能依赖某个平台下载器自行建目录，否则微信文件、语音和飞书文件首次收件会因目录缺失报错。普通文件等待下一条要求；带说明的文件下载后一起提交。微信语音保留原始编码（例如 SILK、Speex），不在接入层自动转写。失败文件当次报告，不遗留阻塞后续普通文字的标记；没有选会话时不会下载到任意工作区。回归测试覆盖共用收件流程到实际渠道下载器的写入和解密，使用隔离工作区及模拟网络响应，不只在预先存在的目录中测试下载器。

独立工具“对外消息发送”通过唯一 `external_messaging` 能力桥复用三平台连接。`platform`、`connection_id`、`chat_id` 明确指定，不追溯上条用户消息决定接收者。纯文本和文件发送共用连接凭据及目标解析，微信两种发送都需要该 ID 的有效回复凭据，凭据仅在已指定连接内查找，不能擅自换接收者。长文本完整分段，返回已确认的消息 ID、字符数；中途失败保留已确认部分，不自动重发。平台不支持或上游拒绝时返回实际失败；不会偷偷降级成成功或截断内容。

文件与附言可能为多条消息，发送中断时返回“未确认”并提示先核对，不能认定未送达后盲目重发。Telegram 无幂等发送接口、微信未承诺 client_id 的服务端去重，因此网络中断后结果回传可能重复显示，但不会重跑 AI 任务。

### 配置与验证边界

微信与飞书均提供连接配置、记录日志、快速开始、指令与文件、常见问题标签。钉钉占位页替换为飞书。连接配置仅可见时轮询；操作失败保留，后续成功的状态查询不能擦除它。飞书权限/事件设置、微信扫码步骤见界面内快速开始。

微信和飞书传输复用天策网络设置；飞书 WebSocket 同样采用系统/自定义/直连代理策略。不额外开放本机公网端口。仍需天策后端及桌面入口在线，最小化可运行；未实现自动唤醒。

协议依据：[腾讯 iLink 协议](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol.md)、[飞书官方 Python SDK 长连接实现](https://github.com/larksuite/oapi-sdk-python/blob/v2_main/lark_oapi/ws/client.py)。离线回归覆盖协议帧、事件归一、持久化后 ACK、媒体加解密、二维码落盘竞态、数字菜单与身份隔离；未使用用户的真实飞书应用或微信账号进行完整收发验收，首次使用仍需创建应用/扫码并验证平台权限。
