# 新会话数据结构说明及测试方法

## 真实目标

会话、消息、分支、记忆和功能任务属于用户项目数据，应当透明、可检查、可单独恢复。SQLite 继续发挥分页和定位性能优势，但不得成为用户事实的唯一容器，也不得影响模型读取完整历史。

本结构遵守四条硬合同：

1. 一个事实只有一个权威来源。
2. 不同会话默认不共同改写总表。
3. 缓存可以删除，删除后不丢功能、不丢历史。
4. 看板可以分页，模型上下文不得因为看板分页而被隐式截断。

## 最开始的旧版情况

早期版本使用多份 JSON/JSONL：会话索引集中在 `index.json`，分支关系集中在 `branch_graph.json`，每个会话另有 `messages.jsonl`、压缩记录和状态文件。

透明文件方向是对的，但“所有会话共同改写一个总表”造成了实际问题：多 AI 和后台任务并发时会争用项目级锁；一次业务动作连续写多个文件时可能只完成一部分；界面读取恰好撞上改写会看到短暂不一致；总表越大，任何小变化的改写范围也越大。

## 为什么改成 SQLite

2026-08-13 将项目会话运行状态收口到 `.Tiance/tiance.db`，利用事务和 WAL 解决半写入、并发读写和共享总表性能问题。这个决定针对的是真实故障，不是无意义绕路。

随后暴露出的代价同样真实：用户无法直接检查单个会话；同步或恢复必须整体处理数据库；一个逻辑损坏会影响整个项目；工具和看板容易依赖数据库内部表；“项目数据是用户可拥有文件”的产品哲学被削弱。

## 为什么又回到文件

这次不是恢复旧结构，而是保留 SQLite 阶段学到的并发边界后重新分配职责：

- 单会话事实只写本会话目录。
- 跨会话创建、删除和分支操作才使用项目级协调锁。
- JSON 对象使用临时文件、落盘和原子替换。
- JSONL 追加先写可恢复意图，异常退出后下次读取会完成或确认该次追加。
- 项目记忆每次提交一个独立原子批次，不反复改写共同事件总表。
- SQLite 只保存从消息文件推导出的分页索引，可随时重建。

这样同时保留透明性、并发隔离和查询性能。

### 文件职责

- `storage.json`：结构版本和事实源声明。当前版本为 2，声明文件是权威来源、SQLite 是可删除索引。
- 根目录 `state.json`：项目文件工作区状态，不保存会话历史。
- `control.json`：当前选中会话，仅负责导航。
- `session.json`：一个会话的身份、模型设置、更新时间和消息计数。
- 会话内 `state.json`：该会话的置顶、草稿、引用和运行状态。
- `branch.json`：该会话自己的分支节点和消息版本记录。
- `messages.jsonl`：从第一条到最后一条的完整原始消息，一行一条，不设隐式数量上限。
- 其它 JSON/JSONL：压缩、命名、附件、记忆投递和功能任务的真实记录。
- `cache/conversation-index.db`：仅加速分页、游标和单轮定位。完整历史读取绕过此库。
- `migrations/sqlite-v1/tiance.db`：旧库迁移校验成功后的恢复备份，只读留存。

## 旧 SQLite 自动迁移

项目第一次打开时，如果存在旧 `.Tiance/tiance.db` 且没有新版 `storage.json`，程序会：

1. 校验旧库结构版本。
2. 通过 SQLite 一致快照生成恢复备份。
3. 导出会话、完整消息、会话事件、会话文档、项目记忆、工作区状态和分支关系。
4. 复读导出文件，核对各类记录数量。
5. 最后才写入 `storage.json`，再移除运行位置的旧数据库及 WAL 临时文件。

迁移中途失败不会写新版完成标记，也不会删除旧数据库。新版运行不保留 SQLite 与文件双写。

## 看板、功能和工具的读取规则

- 会话索引看板从各个 `session.json`、`state.json` 和 `control.json` 派生。
- 消息、压缩、注入预览和项目记忆看板直接读取权威文件；消息看板显示最近部分时必须同时返回总数和明确的截断标记。
- 请求模型完整上下文时直接顺序读取 `messages.jsonl`，不使用看板条数，也不从 SQLite 缓存取完整历史。
- 内置“会话原始历史检索”工具逐行检索 `messages.jsonl`，不依赖后端内部模块和缓存数据库。
- 本分支只更新仓库内置工具，不发布在线工具市场。

### 必测场景

1. 新项目只产生 `storage.json` 和按需事实文件，不产生权威 `tiance.db`。
2. 旧 SQLite 项目首次打开后，各数据家族数量一致，恢复备份存在。
3. 删除 `cache/conversation-index.db` 后，消息分页自动重建并保持结果一致。
4. 超过 100 条和超过 1,000 条消息时，模型历史读取仍包含首条与末条。
5. 多个会话并发追加后，每个会话数量与内容均完整，不互相覆盖。
6. 同一会话写入受本会话锁串行保护，异常 JSON/JSONL 会明确报错并停止覆盖。
7. 分支、压缩、记忆投递、功能会话、附件和看板仍能读取迁移后的记录。
8. 消息看板若只展示最近记录，界面必须明确显示总数和“仅展示部分”；该限制不得进入模型请求链路。

## 回滚与恢复

本改造位于独立 Git 分支，可以直接切回保留 SQLite 事实源的主分支。对已经迁移的项目，旧库备份位于 `.Tiance/migrations/sqlite-v1/tiance.db`。恢复旧版本前应先完整备份当前 `.Tiance`，再由明确的恢复流程处理；不要把缓存数据库改名冒充旧事实库。
