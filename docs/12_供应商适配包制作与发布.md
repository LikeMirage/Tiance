# 供应商适配包：制作、验证、发布与兼容更新

> 实现基线：2026-08-22。

本文说明如何制作一个可被天策在线供应商市场安装的供应商包，以及后续怎样发布不会破坏用户配置的更新。

## 1. 先理解供应商包的边界

供应商包有两个用途：

1. **首次安装**：提供完整的供应商定义、默认模型和声明式适配规则；
2. **已有供应商更新**：只发布新的包版本和声明式适配知识。

供应商没有“官方”“内置”或特殊等级。随天策安装包提前提供的供应商、用户自己制作的供应商、任意市场下载的供应商使用相同目录、相同稳定 ID、相同校验和相同更新规则。

本地供应商目录的文件所有权如下：

| 文件 | 首次安装 | 已有供应商更新 | 所有权 |
| --- | --- | --- | --- |
| `manifest.json` | 安装 | 替换 | 包身份与版本 |
| `provider-rules.json` | 安装 | 替换 | 可更新的供应商级适配知识 |
| `model-rules.json` | 安装 | 替换 | 可更新的模型级适配知识 |
| `provider.json` | 作为初始模板安装 | 不读取、不合并、不替换 | 用户在供应商看板维护 |
| `models.json` | 作为默认模型模板安装 | 不读取、不合并、不替换 | 用户在模型管理中维护 |
| `credentials.json` | 客户端创建空文件 | 不读取、不修改 | 用户密钥 |
| `cloud-model-cache.json` | 客户端创建空文件 | 不读取、不修改 | 用户本地发现缓存 |
| `.Tiance/` | 不属于供应商包 | 禁止读写 | 会话、消息、记忆、任务等运行数据 |

因此，更新包中即使带有新的默认接口地址和默认模型，它们也只影响**以后首次安装这个版本**的用户，不会覆盖已经安装用户的接口地址、协议选择、鉴权方式、启用状态和模型列表。

## 2. 稳定 ID、显示名称和版本

- `id` 是供应商包的稳定身份，只能使用小写字母、数字、下划线和连字符，长度为 2 到 64 个字符；
- 同一市场索引中不能出现重复 ID；
- 显示名称可以相同。两个同名供应商只要 ID 不同，就会被视为两个独立项目；
- 版本使用语义化版本，例如 `1.0.0`、`1.1.0`、`2.0.0-beta.1`；
- 只有相同 ID 且远端版本更高时，客户端才显示更新；
- 本地已有相同 ID、但还没有 `manifest.json` 的供应商会显示“可更新”。用户确认后只写入包清单和两份规则，从这一版开始参与版本比较，原有配置仍不被覆盖。

ID 一旦发布就不要改。需要做不兼容变化时，应使用新 ID 发布；新包仍可以沿用原显示名称。

## 3. 压缩包结构

ZIP 必须且只能包含一个以供应商 ID 命名的顶层文件夹，文件夹内必须且只能有五个 UTF-8 JSON 文件：

```text
sample-provider/
├── manifest.json
├── provider.json
├── provider-rules.json
├── model-rules.json
└── models.json
```

不允许放入密钥、缓存、`.Tiance`、脚本、依赖、图片、说明文件、符号链接或额外子目录。客户端还会限制：

- 每个文件不超过 1 MiB；
- 解压后总大小不超过 4 MiB；
- 拒绝加密文件、链接、重复文件和路径越界；
- 下载字节数和 SHA-256 必须与市场索引一致。

## 4. 编写五个文件

以下示例使用现有 `generic` Profile 和 `openai_compatible` 协议。实际字段必须选择天策当前已经支持的枚举值。

### 4.1 `manifest.json`

```json
{
  "schemaVersion": 1,
  "kind": "tiance-provider-package",
  "id": "sample-provider",
  "name": "示例供应商",
  "version": "1.0.0",
  "author": {
    "name": "作者名称"
  },
  "summary": "示例供应商的天策协议适配包。",
  "license": "CC0-1.0",
  "compatibility": {
    "minTianceVersion": "0.3.22"
  },
  "managedModelIds": [
    "sample-model"
  ]
}
```

`managedModelIds` 必须无重复，并且必须与 `models.json` 中的全部 `modelId` 完全一致。它描述这个版本完整安装包内提供的模型模板，不代表已安装用户当前实际拥有的模型。

### 4.2 `provider.json`

```json
{
  "schemaVersion": 1,
  "id": "sample-provider",
  "displayName": "示例供应商",
  "profileId": "generic",
  "protocolFamily": "openai_compatible",
  "generationAuthSchemes": {
    "openai_compatible": "bearer_token"
  },
  "modelDiscoveryStrategy": "openai_models",
  "modelDiscoveryAuthScheme": "bearer_token",
  "generationUrls": {
    "openai_compatible": "https://api.example.com/v1/chat/completions"
  },
  "modelDiscoveryUrl": "https://api.example.com/v1/models",
  "enabled": false,
  "reasoningReplayMode": "tool_call_rounds",
  "createdAt": "2026-08-22T00:00:00Z",
  "updatedAt": "2026-08-22T00:00:00Z"
}
```

要求：

- `id` 必须与顶层文件夹、`manifest.json` 和市场索引一致；
- `displayName` 必须与 `manifest.json.name` 和市场索引名称一致；
- `protocolFamily` 必须与市场索引的 `protocol` 一致，并且在 `generationUrls` 与 `generationAuthSchemes` 中都有对应项；
- `profileId` 必须是当前天策已经提供的 Profile；仅靠 JSON 包不能新增代码 Profile；
- 包中不得填写 API Key；
- 首次安装时客户端会强制设为未启用，并重新生成本地创建、更新时间。

### 4.3 `provider-rules.json`

最小有效文件：

```json
{
  "schemaVersion": 1,
  "capabilities": {},
  "request": {},
  "behavior": {}
}
```

这里声明供应商级能力、请求字段和行为差异，例如输出格式、思考模式、采样参数、最大输出、工具调用、需要省略的请求参数、流式用量和缓存时长。只写当前程序已经支持的字段；未知字段会被拒绝，不会被静默忽略。

### 4.4 `model-rules.json`

最小有效文件：

```json
{
  "schemaVersion": 1,
  "families": {},
  "models": {}
}
```

`families` 按 `models.json` 中的 `familyGroup` 复用一组模型差异，`models` 再按精确 `modelId` 覆盖。最终合并顺序是：供应商规则 → 模型家族规则 → 精确模型规则。

### 4.5 `models.json`

```json
{
  "schemaVersion": 1,
  "items": [
    {
      "modelId": "sample-model",
      "displayName": "Sample Model",
      "familyGroup": "sample",
      "capabilityTags": [],
      "note": "",
      "priceCurrency": "CNY",
      "inputPricePerMillion": null,
      "cacheHitPricePerMillion": null,
      "outputPricePerMillion": null,
      "createdAt": null,
      "updatedAt": null
    }
  ]
}
```

这是首次安装的默认模型模板，不是远程强制模型表。用户安装后可以自行增加、删除和修改模型；兼容更新不会重新合并这份文件。

## 5. 创建 ZIP 和计算完整性信息

在包含 `sample-provider` 文件夹的目录执行 PowerShell：

```powershell
New-Item -ItemType Directory -Force -Path .\packages | Out-Null
Compress-Archive -Path .\sample-provider -DestinationPath .\packages\sample-provider-1.0.0.zip
$providerPackage = Get-Item -LiteralPath .\packages\sample-provider-1.0.0.zip
$providerSha256 = (Get-FileHash -Algorithm SHA256 -LiteralPath $providerPackage.FullName).Hash.ToLowerInvariant()
$providerPackage.Length
$providerSha256
```

不要使用 `sample-provider\*` 作为压缩输入，否则 ZIP 可能缺少必须的顶层 ID 文件夹。修改任何一个 JSON 后都必须重新压缩，并重新计算大小和 SHA-256。

## 6. 编写市场 `index.json`

市场仓库发布后的静态结构至少为：

```text
index.json
packages/
└── sample-provider-1.0.0.zip
```

示例索引：

```json
{
  "schemaVersion": 1,
  "kind": "tiance-provider-market",
  "name": "我的供应商市场",
  "updatedAt": "2026-08-22T00:00:00Z",
  "providers": [
    {
      "id": "sample-provider",
      "name": "示例供应商",
      "version": "1.0.0",
      "author": "作者名称",
      "summary": "示例供应商的天策协议适配包。",
      "license": "CC0-1.0",
      "protocol": "openai_compatible",
      "modelCount": 1,
      "packageUrl": "packages/sample-provider-1.0.0.zip",
      "sha256": "替换为小写的六十四位SHA256",
      "size": 1234,
      "compatibility": {
        "minTianceVersion": "0.3.22"
      }
    }
  ]
}
```

索引中的 ID、名称、版本、作者、简介、许可证和最低天策版本必须与包内 `manifest.json` 一致；协议必须与 `provider.json.protocolFamily` 一致；`modelCount` 应与 `models.json.items` 数量一致。

`packageUrl` 可以是市场目录内的相对 HTTPS 资源。客户端会把它限制在同一个市场目录或同一个已授权 GitHub 仓库内，不能指向任意第三方文件。

## 7. 发布到 GitHub Pages 或私人仓库

### 公开市场

1. 把 `index.json` 和 `packages/` 提交到市场仓库；
2. 在仓库的 GitHub Pages 设置中选择实际发布这些静态文件的分支和目录；
3. 等待 Pages 部署完成；
4. 直接访问 `https://<owner>.github.io/<repository>/index.json`，确认返回的是最新 JSON；
5. 再访问索引中的 ZIP 地址，确认可以下载且大小、SHA-256 与索引一致；
6. 在天策“在线供应商”连接 `https://<owner>.github.io/<repository>`，刷新并安装。

### 私人市场

私人仓库不使用公开 Pages。用户先在天策中完成 GitHub App 授权并允许访问该仓库，再把 `https://github.com/<owner>/<repository>` 作为市场来源。仓库根部仍使用同一份 `index.json` 和 `packages/` 结构。

## 8. 发布兼容更新

兼容更新按以下步骤完成：

1. 保持原 `id`、`schemaVersion` 和 `profileId` 不变；
2. 修改 `provider-rules.json` 或 `model-rules.json`；
3. 提高 `manifest.json.version`；
4. 为了让新用户首次安装时得到完整最新模板，同步维护包内 `provider.json` 和 `models.json`，但不要期待它们覆盖已有用户；
5. 重新生成完整五文件 ZIP、大小和 SHA-256；
6. 更新索引中的版本、包路径、大小、哈希、更新时间和必要的最低天策版本；
7. 部署后先验证远端 `index.json` 与 ZIP，再在天策中刷新；
8. 更新确认框会明确提示只替换清单和两份适配规则。

客户端执行更新时会先备份本地 `manifest.json` 和两份规则，然后逐个原子替换；中途失败会恢复这三个文件。用户配置和 `.Tiance` 从一开始就不进入更新流程，因此不存在“合并错了再恢复”的隐式风险。

## 9. 哪些变化不是兼容更新

以下变化不能沿用原 ID 直接覆盖：

- 改变 `profileId` 或供应商数据结构版本；
- 要求用户重置 API Key、接口地址、协议选择或模型配置；
- 需要迁移、删除或重写用户本地数据；
- 依赖天策当前不存在的代码 Profile、协议适配器或声明式规则字段；
- 只有替换 `provider.json` 或 `models.json` 才能让已有用户正常工作的变化。

处理方式只有两种：

1. 如果只是依赖较新的天策能力，先随天策软件发布代码，再把 `minTianceVersion` 提高到包含该能力的版本；
2. 如果供应商身份或用户配置合同已经变化，使用新的稳定 ID 发布一个独立包。显示名称允许与旧包相同，旧包是否继续保留由市场作者明确决定。

客户端会比较本地与新包的 `schemaVersion` 和 `profileId`。不一致时会拒绝更新，并返回稳定原因 `provider_incompatible_update`，不会尝试部分覆盖。

## 10. 发布前检查表

- [ ] ZIP 顶层文件夹名称与供应商 ID 完全一致；
- [ ] ZIP 内只有五个规定 JSON；
- [ ] 所有 JSON 是 UTF-8 对象且通过真实字段校验；
- [ ] 包、清单、供应商定义和索引的 ID、名称、协议一致；
- [ ] `managedModelIds` 与模型 ID 完全一致且无重复；
- [ ] 包内没有密钥、Token、缓存、个人地址、会话数据和 `.Tiance`；
- [ ] 版本高于已发布版本；
- [ ] 最低天策版本真实反映所需程序能力；
- [ ] 同 ID 更新未改变 `profileId` 或数据结构版本；
- [ ] 已重新计算 ZIP 大小和 SHA-256；
- [ ] 远端 `index.json` 和 ZIP 均能从最终市场地址读取；
- [ ] 在天策中确认首次安装和已有供应商更新显示符合预期。
