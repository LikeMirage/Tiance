# 工具系统、动态加载与权限

## 工具项目结构

正式工具位于 `Data/tools/<project_id>/`，核心合同通常包括：

```text
.tool/tool.json
.tool/input.schema.json
.tool/output.schema.json
.tool/examples.json
.tool/permissions.json
program/ 或前端能力声明
requirements.txt（可选）
```

`tool.json` 定义稳定调用名、显示信息、运行位置、入口和加载方式。Schema 是参数和结果合同；案例不能代替 Schema；权限是本地执行策略，不是提示词。

## 三种运行位置

- Python 工具：独立子进程，JSON 输入输出，可有工具私有依赖目录。
- client tool：后端创建请求，由已登记前端执行器完成。
- 后端 host capability：工具使用短期凭据访问有限的供应商/GitHub 等能力。

三种路径都必须回到统一工具调用生命周期和标准结果，不能通过修改会话消息 Schema 获得特殊待遇。

## 启用和注册

执行前至少检查：工具项目存在、调用名唯一、全局启用、会话启用、运行入口有效、参数符合 Schema。注册表重建失败不能继续把旧 enabled 状态当作当前事实。

工具调用审计记录与正式工具结果分开。未知工具或解析失败也需要可观察记录，不能因为无法加载元数据就丢掉审计。

## 动态工具

`loading.dynamic=true` 的工具初始只向模型提供轻量目录。模型通过：

- `load_tool_info` 获取目标 Schema/案例；
- `execute_dynamic_tool` 提交 `tool_name + arguments` 执行。

包装器必须重新验证目标启用状态、参数和权限，并透传 `content` 与 `structuredContent`。动态加载只减少初始上下文，不降低权限。

## 权限决策

权限策略为 `deny`、`ask`、`allow`。决策需要结合真实参数解析作用范围，例如工作区内外路径、网络目标、凭据、运行环境修改和天策业务写入。

需要询问时，后端生成一次确认请求并等待用户决定。确认必须具有明确生命周期；断线、取消和超时后不能留下永久等待的会话。

市场包可以携带发布者默认权限，但它不是用户授权事实。安装和更新必须让本地策略保持可见，不能因为更新工具包静默扩大权限。

## 依赖

工具依赖安装有同步入口和任务入口，当前前端主要使用任务流程。依赖目录按 Python 版本放在工具项目内。安装过程会修改正式运行环境，因此需要互斥、取消/关闭协调和完整失败信息；不能把半安装目录当作成功。

## 当前安全边界

工具子进程是依赖隔离和进程隔离，不等于操作系统沙箱。第三方工具代码仍可能使用进程权限访问本机资源；只安装可信工具，并在权限提示中核对真实目标。
