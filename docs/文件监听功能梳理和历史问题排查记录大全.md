# 文件监听功能梳理和历史问题排查记录大全

本文记录天策项目文件监听的产品职责、当前 Windows 实现、历史事故、根因、排查方法和发布验收边界。它用于避免后续维护只修复一次现象，却再次破坏“监听失败不能影响聊天”的总体合同。

## 一、文件监听究竟负责什么

项目文件树的读取和文件监听是两个不同系统。

- 文件树读取负责在用户进入项目、展开目录或手动刷新时读取磁盘内容。
- 文件监听只负责发现外部变化，例如 AI 工具、终端、Git、解压或安装程序在项目目录中新增、修改、移动、删除文件。
- 前端收到变化后，只重新读取根层或当前已经展开的受影响目录。
- 已打开的文件标签页也使用同一变化通知检查内容是否在外部改变。
- 关闭监听后，文件读写和手动刷新仍然可用，只是不再自动刷新。

文件监听不负责构建完整文件索引，也不应递归扫描整个项目来维持文件树。

## 二、不可破坏的总体合同

1. 任何目录名称和文件系统结构都必须有限终止，不能靠写死 `node_modules` 才避免循环。
2. Windows 目录链接、junction 和 symlink 可以显示和访问，但后台监听不得跟随它们形成递归。
3. 监听进程崩溃、阻塞或过载时，只能损失自动刷新，不能拖垮聊天、会话、工具和桌面壳。
4. 事件队列必须有固定容量，生产速度超过消费速度时不能无限等待或积压。
5. 丢失细粒度事件后必须发送明确的 `overflow`，由前端重新核对可见状态，不能静默丢事件。
6. 自动刷新只读取根层和当前展开目录；折叠目录不因后台变化被遍历。
7. 手动刷新始终可用。
8. `.Tiance` 是天策自己的会话和内部状态目录，不参与项目文件树自动刷新；除此之外不按业务目录名写死排除规则。
9. 内部路径必须在进入固定容量跨进程队列之前过滤，不能等队列溢出后再丢弃。
10. `overflow` 只表示具体路径丢失，不等于所有已打开资源都已变化；资源预览必须通过修改时间等证据确认后再重载。

## 三、当前 Windows 数据流

```text
ReadDirectoryChangesW 独立子进程
  -> 不遍历目录链接的系统子树通知
  -> 入队前排除 .Tiance 与内部原子写临时文件
  -> 固定容量跨进程队列
     -> changed：相对路径批次
     -> overflow：事件过载，需要重新核对可见树
     -> failed：监听子进程失败
  -> FastAPI SSE
     -> ready / changed / overflow / unavailable
  -> 前端共享项目监听通道
     -> 文件树：根层 + 当前展开且受影响的目录
     -> 标签页：只核对可能受影响的已打开文件
```

### 1. 文件树按需读取

普通列表请求只读取项目根层或指定目录的一层。用户展开目录时才读取其子项。搜索是明确的递归操作，不属于常驻监听流程。

### 2. Windows 原生监听

Windows 使用一个目录句柄调用 `ReadDirectoryChangesW`，让系统报告项目子树变化。它不会像用户态递归扫描那样逐个进入 pnpm 创建的目录链接，因此目录链接不会形成无限递归。

事件路径按词法转换为项目相对路径，不调用 `Path.resolve()` 追踪链接目标。

### 3. 独立进程隔离

原生监听器运行在单独子进程。后端通过跨进程队列接收事件：

- 子进程异常退出时，后端 SSE 报告 `unavailable` 并按 1 秒、5 秒、30 秒上限退避重启；
- FastAPI、聊天 WebSocket 和健康检查不运行原生监听调用；
- SSE 断开时只终止对应监听子进程，不影响后端主进程。

响应发送层负责关闭事件迭代器，文件事件路由和 Windows 监听包装层逐层显式关闭下层监听，不依赖垃圾回收。断开时取消并等待未完成的事件读取，再关闭监听；回收过程受取消保护，等待子进程退出后释放进程句柄和队列。终止后等待 2 秒，仍存活则强制结束并再等待 2 秒；仍未退出明确报错，不启动替代进程。启动失败也释放已创建的资源。

文件事件接口空闲时每 15 秒发送一次 SSE 注释 `: keep-alive`，避免网关默认 100 秒空闲超时触发反复重连。这个间隔是传输保活策略，不限制订阅时长、不取消当前读取，也不会产生 `changed` 事件或触发文件刷新。

### 4. 严格过载降级

跨进程队列容量固定为 4。队列满时不等待：

1. 清除已过时的细粒度事件；
2. 只放入一个 `overflow`；
3. 前端重新读取根层和当前展开目录；
4. 后续变化继续通过新的批次通知。

单批相对路径超过 256 条也直接转为 `overflow`，不发送巨大 SSE 数据。

### 5. 前端局部刷新

- 根目录直接子项变化时刷新根层。
- 某个文件变化时，只刷新它的父目录，并且该父目录必须仍处于展开状态。
- `overflow` 时执行一次受控刷新：根层加当前展开目录。
- 已加载但已经折叠的目录不会自动刷新；再次展开时会按正常目录读取流程获得最新内容。
- 监听不可用时显示“文件自动刷新暂不可用，请使用刷新按钮”，手动刷新入口不受影响。

## 四、历史问题与版本演变

### v0.3.13 以前：全量事件直接推动刷新

安装依赖、解压仓库等操作会短时间创建大量文件。大量 SSE 和前端刷新可能造成 CPU、内存和请求量上升。

### v0.3.13：以排除和轮询规避过载

当时加入了三类措施：

- 默认忽略 `node_modules`、`.git`、`dist`、`.venv` 等高噪声目录；
- Windows 强制使用轮询；
- 超过 256 条变化后只发送顶层目录。

这能缓解当时的卡顿，但存在结构性问题：目录名排除承担了防循环职责，关闭排除后正确性无法保证；全项目轮询对大型项目代价过高。

### v0.3.14：撤销特殊排除后发生回归

为了实现“所有用户目录都能正常监听”，v0.3.14 删除了高噪声目录写死排除和 Windows 强制轮询，恢复 `watchfiles` 原生递归监听，但没有先替换底层递归机制。

DSH 使用 pnpm。其 `node_modules` 中存在大量目录链接，其中 `@deepseek-ai/cordis` 的链接关系被 `watchfiles` 识别为指向祖先的文件系统循环。日志出现：

```text
WatchfilesRustInternalError: File system loop found
```

同一次安装还先后产生 1,648 和 13,337 条变化，随后后端和桌面壳重新启动。

“超过 256 条再压缩”没有挡住事故，因为该逻辑位于 `watchfiles` 产出事件之后；底层递归已经先报错或制造事件风暴。

### 崩溃后的会话闪烁

崩溃时会话运行状态仍可能保存为 `running`。重启后 WebSocket 订阅不存在的旧运行任务返回 404，但此前没有执行 HTTP SSE 路径已有的状态核对，因此前端反复尝试恢复，发送按钮在暂停和发送之间切换。约 150 秒的过期逻辑最终把状态改为空闲，所以闪烁一段时间后自行停止。

修复后，WebSocket 订阅发现运行任务不存在时立即调用统一状态核对，将孤立的 `running` 状态恢复为空闲。

### v0.3.17：内部会话写入导致 Office 预览反复刷新

会话草稿在停止输入 500 毫秒后保存到 `.Tiance`，发送消息和流式输出还会更新会话运行状态。Windows 子进程最初把这些内部通知也放进容量为 4 的队列，只在主进程取出事件后才过滤。内部写入密集时队列先产生 `overflow`，前端随后核对全部已打开资源；文件列表又没有提供修改时间，导致无法证明资源未变化，Word、PDF、Excel、PPT、图片、视频和数据库预览都可能被无关重载。

修复后的边界是：

- Windows 子进程在入队前排除 `.Tiance` 和内部原子写临时文件；
- 文件列表为文件节点提供修改时间，供打开标签页建立稳定基线；
- `overflow` 核对中，元数据未知不再视为文件已变化，只有确认修改或删除才更新资源版本；
- Word 新版本在独立容器中完成解析后一次替换，内容指纹相同则不重建，避免合法外部更新时出现中途白屏。

### DSH 安装自身失败

DSH 的 pnpm 安装已经下载大量依赖，但 `koffi` 安装阶段报告缺少 `LOCALAPPDATA` 和 `APPDATA`。原因是工具进程安全环境白名单没有继承这些 Windows 标准目录变量。

修复后只补充 `APPDATA`、`LOCALAPPDATA`、`HOMEDRIVE` 和 `HOMEPATH`，没有改成继承全部环境变量，避免把无关密钥传入工具进程。

### 2026-08-31：文件监听重连与子进程回收缺口

用户报告 Windows 上累积超过 1200 个 Python 进程。本机网关日志中，1905 条文件监听连接结束记录有 1865 条持续约 100 秒；接口缺少心跳，与网关空闲超时相符。源码及模拟实验确认，发送过程中断开连接、关闭外层迭代器时，底层监听进程不保证立即回收。修复补全了响应、迭代器和进程的资源归属，并加入上述传输保活；没有禁用自动刷新、增加定时清理进程或修改文件事实。报告时程序已经关闭，历史 1200 多个进程的身份未重新逐个核验。

## 五、为什么不再用目录名排除保证安全

性能排除可以是用户配置，但不能成为正确性基础。以下名称都可能包含巨大目录或循环链接：

- `node_modules`
- `vendor`
- `packages`
- `cache`
- 用户自定义目录

当前 Windows 安全边界来自系统通知不递归遍历链接，而不是目录叫什么。即使项目完整显示和监听 `node_modules`，后台也不会沿链接形成循环。

## 六、故障排查顺序

### 1. 确认运行版本

检查 `system/version.json`、软件更新页和 GitHub Release 标签是否一致。不要先假设用户没有更新。

### 2. 检查桌面和后端日志

重点查找：

- `File system loop found`
- `WatchfilesRustInternalError`
- `Project file watcher failed`
- `Isolated project file watcher failed`
- 短时间内几千或几万条 `changes detected`
- 后端进程、桌面壳的重新启动时间

### 3. 区分三类问题

- 监听问题：自动刷新、CPU、事件风暴、监听子进程退出。
- 会话恢复问题：重启后状态闪烁、重复订阅、旧任务不存在。
- 工具安装问题：命令退出码、工具日志、PATH 和 Windows 用户目录环境变量。

三者可能在同一次操作中出现，但不能用一个补丁混成同一根因。

### 4. 检查前端刷新范围

观察是否只请求：

- 项目根层；
- 当前展开的受影响目录；
- 受影响的打开标签页。

如果折叠目录仍持续发起列表请求，应检查展开集合判断；如果 `overflow` 后文件树永久不一致，应检查受控刷新是否执行。

### 5. 检查进程隔离

监听子进程失败后应满足：

- `/api/health` 继续成功；
- 聊天 WebSocket 不断开；
- 文件树显示自动刷新不可用；
- 手动刷新仍可读取文件；
- 监听按退避策略重启，不形成快速崩溃循环。

## 七、自动验证与人工验收边界

自动测试覆盖：

- 路径转换不解析目录链接；
- `node_modules` 等用户目录不会被特殊过滤；
- 队列满后只保留一个 `overflow`；
- 变化批次聚合与上限；
- Windows 原生通知能收到嵌套目录变化；
- 文件监听在发送时断开、空闲断开、发送失败和重复取消时完成回收；
- 心跳不取消正在等待的读取，不改变业务事件顺序；
- 监听启动失败、运行失败和强制结束路径释放资源，回收失败明确报错；
- Windows 真实监听子进程连续三次连接、断开后逐个退出，不累积；
- WebSocket 孤立运行状态立即核对；
- 工具进程继承必要 Windows 目录变量；
- 前端类型检查、状态测试和生产构建。

真实 DSH 的“安装依赖、过载、软件重启和继续操作”属于人工端到端验收。本次发布按用户要求不由自动开发会话执行，不能在报告中写成已经通过。人工验收结果应在后续问题记录中补充。

## 八、当前平台边界

当前正式发布平台是 Windows，独立进程和原生目录通知合同只对 Windows 正式承诺。Linux 和 macOS 暂不作为本次发布完成条件，也不能在发布说明中宣称已经达到同等隔离能力。

未来扩展其他平台时，应保持相同上层事件合同：`ready`、`changed`、`overflow`、`unavailable`，底层分别选择对应系统能力，而不是让前端理解平台差异。
