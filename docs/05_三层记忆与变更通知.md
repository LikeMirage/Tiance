# 三层记忆与长期记忆变更通知

> 实现基线：2026-08-02。准确地说，当前是“三层记忆”，其中项目层和全局层属于可提取、可增删改的长期记忆；会话层由累计摘要承担。

把所有记忆写成一个巨大系统提示词很简单，却会同时制造三个问题：不同项目互相污染、旧会话不知道记忆何时改变、每次修改都破坏模型已经缓存的请求前缀。

天策把记忆按作用范围拆成三层，并把“当前内容”和“发生过什么变化”分开传递。

## 第一层：会话累计摘要

会话层只服务当前会话。压缩功能把旧摘要与新历史合并成一份新的累计快照，保留正在工作的目标、决定、证据、状态和交接信息。它不会被其它项目或其它无关会话自动继承。

这一层解决“这条会话如何继续”，不负责声明用户在所有项目中的稳定偏好。

## 第二层：项目长期记忆

项目记忆保存只对当前项目长期有效的信息，例如项目规范、确认过的结构、固定路径和持续约束。达到提取阈值后，系统从当前会话创建一个“项目记忆管理”功能会话。

该会话必须先通过 `manage_memory` 读取现有全局与项目记忆，再逐项判断新增、更新或删除。它只能调用这一种工具，不能借记忆提取之名继续执行原任务。

项目记忆使用事件流保存，而不是每次覆盖一份不可审计的全文。每个事件记录范围、操作、目标 ID、内容、关键词、依据和来源任务，因此可以恢复当前快照，也能解释它是如何变化的。

## 第三层：全局长期记忆

全局记忆只保存跨项目长期有效的信息，例如用户稳定偏好、普遍工作约束和反复适用的决策习惯。当前默认触发阈值高于项目记忆，以减少把偶然项目事实提升成全局规则的风险。

项目独有路径、一次性进度、密钥和短期状态不能进入全局记忆。全局管理同样通过独立功能会话和 `manage_memory` 工具完成。

## 提取为什么使用真实会话

项目与全局提取不是后台偷偷调用一次模型。系统会：

1. 依据上次完成边界计算新覆盖的完整消息组；
2. 复制到来源边界为止的合法会话快照；
3. 创建带明确功能类型的子会话；
4. 使用会话指定或功能设置指定的模型运行；
5. 校验它只调用了 `manage_memory`；
6. 成功后推进提取边界，失败则保留旧边界并按设置重试。

这样，用户可以打开功能会话，看见提取依据、模型和最终修改，而不是只能相信一个不可见的总结器。

## 阻塞与异步提取的调度边界

项目记忆管理与全局记忆管理分别遵循各自的 `blockingEnabled` 设置。阻塞检查只处理设为阻塞的功能，后台检查只处理设为异步的功能；必须在等待该功能的任务锁之前判断模式，不能先等后台提取结束，再发现它本来不应阻塞主会话。

同一来源会话、同一记忆范围的提取仍串行执行，避免重复创建任务或推进同一边界。真正排队的检查拿到锁后，重新读取会话开关与功能配置，以当前设置为准；项目与全局的提取边界仍独立维护。这一调度修复不改变阈值、工具权限、提取内容或消息历史。

## 变更通知：为什么不能只改前置记忆

假设一条会话昨天已经使用“用户偏好 A”建立了长前缀缓存，今天全局记忆把 A 更新成 B。如果直接改最前面的系统记忆，模型会得到正确内容，却会立即失去整段缓存；如果完全不改，它又会继续依据旧事实工作。

当前做法是为每条会话维护一份投递状态：

- 首次接入时，把当前全局和项目记忆作为基线系统消息；
- 后续新增、更新和删除，作为带有“变更前、变更后、变更依据”的完整通知，附在下一条用户消息之前；
- 通知拥有明确的开始、结束和“用户本轮消息”标识，避免模型把背景变化误认为用户指令；
- 每条会话保存事件游标，保证同一变更不会反复投递；
- 当旧消息因压缩不再可见时，对应通知会折回基线快照，语义不丢失。

## 与供应商缓存有效期联动

供应商的 `provider-rules.json` 可以声明提示词缓存有效期。只要供应商、模型和时间窗口没有变化，新的记忆变更优先追加在后面，保护已有前缀。

时间窗口从当前会话正式历史中最近一条成功 AI 回复的创建时间计算，普通文本回复和工具调用回复都计入。用户消息、工具执行结果、失败或取消的回复，以及后续编辑消息的修改时间，不延长有效期。投递状态不另存一份活动时间；分支沿用复制消息的原始时间，并核对最近成功回复和本次请求的供应商、模型。没有成功回复时，不视为已有有效缓存。预览待投递变更使用同一判断，但不推进正式投递游标。

一旦超过有效期，或切换供应商/模型，继续保护旧前缀已经没有收益。系统会把未折叠的通知合并进前置基线，下一次请求从一份干净、完整的新快照开始。未声明时使用保守默认值；DeepSeek 的当前预设为 6 小时。

## 压缩中的原文保护

记忆压缩开关控制是否发起新的压缩任务，不控制已有压缩结果的使用。关闭开关后，请求仍使用已完成且适用于当前历史的累计摘要；功能分支同样使用继承的摘要，避免重新发送压缩前的原文。原始正式消息仍完整保存在会话中，不因请求使用摘要而删除。

变更通知是记忆的审计链，也是后续回复的语义依据。因此累计摘要提示词明确要求：从“长期记忆变更开始”到“长期记忆变更结束”的完整块必须逐字、按序保留，包括范围、ID、操作、变更前后与依据；不得合并、改写或遗漏。

这条规则只针对真实存在的通知块，不要求压缩模型另外发明长期记忆输出字段。

## 当前边界

- 会话层目前是累计摘要，不是第三份可独立增删改的长期记忆库。
- 项目与全局记忆提取默认阈值分别为 50,000 和 100,000 Token，可在功能模型设置中调整。
- 缓存有效期只决定何时折回基线，不改变供应商实际缓存时长，也不能保证命中。
- 记忆通知服从用户本轮明确表达；它是背景，不是比用户指令更高的命令。

## 2026-08-13：项目内记忆状态的存储变化

项目记忆事件、会话压缩记录、长期记忆管理边界和每条会话的记忆投递状态，现已随项目会话一起进入 `.Tiance/tiance.db`。这样，推进提取边界、写入任务状态和更新会话关系可以共享同一个事务，失败时不会留下“记忆已经变了、会话边界却没有推进”或相反的半完成状态。

全局长期记忆仍属于整个应用而不是某个项目，因此继续保存在运行数据目录的全局记忆事件文件中。项目数据库保存每条会话已接收的基线内容、绑定用户消息的完整变更通知及同步进度，用于独立重放这条会话的上下文；它不是供其它会话使用的第二份全局记忆库。

## 换电脑与记忆来源变化（2026-11-06）

历史重放和发现新变化是两个职责。组装已有记忆上下文，只读取项目 DB 内的基线和投递记录；每次新用户消息发送前，以及待发送预览，才读取当前环境的记忆日志以发现新变化。全局日志位于 `Data/memory/global_memory.jsonl`，项目记忆事件与会话同在项目 DB 中。

不得假设外部记忆日志永远存在或始终是同一份。仅检查“当前条数不少于旧游标”也不够，另一台电脑可能有同样长或更长的不同日志。

投递状态 v3 将两种进度分开：

- `cursors`、基线 `event_count` 和通知 `cursor_after` 表示会话内的单调递增顺序，不再直接充当外部日志偏移。
- `sources` 保存当前日志的已读条数与规范化记录前缀的 SHA-256；基线 `source` 和通知 `sources_after` 同时保存对应检查点。复制同一日志到其它路径仍是相同前缀；同长度替换、截断后重新增长也能识别。
- 正常追加时按原顺序投递完整增删改事件，包括中间变化，不将它们合并成一个净结果。
- 来源缺失、缩短或前缀不匹配时保留会话已有快照和通知，按当前来源的有效内容产生必要的新通知。只因旧 ID 没出现在新来源中，不能推断它已被删除；新来源明确记录的最终删除仍正常生效。来源恢复时接入当前快照，避免再次通知已经投递过的中间变化。
- 新会话没有记忆时不注入记忆消息；已有会话不能因新电脑没有日志而清空其历史背景。整个过程不修改或覆盖目标电脑的全局记忆文件。
- 分支按分支点继承读取位置和来源检查点，不能复制主会话较晚的检查点。压缩、缓存到期折回基线时也同时移动检查点。关闭记忆仍不向模型注入该范围内容，按既有规则折回该范围的投递状态；缺失来源不会导致旧背景被清空。
- 待发送预览不推进持久状态；同一用户消息的重复提交保持幂等。损坏的 JSON、非法投递结构、读取权限和真实 IO 错误仍明确报错，不伪装成空记忆。

已有 v1/v2 状态没有来源指纹，首次使用时将旧游标对应的日志快照与会话已经接收的内容比较：可对应则接续增量，不对应则按来源变化接入。随后保存 v3 检查点。不扫描其它项目，不改数据库表结构，不删除正式历史或审计记录。

换电脑时应正常退出后复制完整 `.Tiance`，以包含 DB 外的图片等附件；复制单个 DB 不会带走这些附件。本修复解决记忆来源不匹配导致的发送阻断，不替代附件和当前环境的模型、工具配置。

回归入口：`tests/test_memory_delivery_portability.py`、`tests/test_conversation_memory_delivery.py`（相对 `1_PythonServer`），包括仅复制 DB 后在没有原全局日志的环境继续组装请求。
