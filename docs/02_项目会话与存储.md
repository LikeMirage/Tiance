# 项目、会话与存储

> 本文区分正式事实、运行状态、展示状态和缓存。它们不能互相替代。

## 项目

普通项目、知识、经验、角色、主题、工具和供应商都具有稳定 ID、目录和分类关系，但各自内容合同不同。通用项目仓库组合不同类型的文件目录；页面不应通过扫描磁盘重新定义项目是否存在。

普通项目可以使用天策管理的目录，也可以指向用户选择的外部工作目录。所有文件操作都必须由项目 ID 解析真实根目录并做范围校验，不能根据前端当前选中项目猜测归属。

### 项目删除与系统回收站（BE-063，2026-10-29）

- 外部项目的“移除项目”只移除登记，保留真实文件；“删除本地文件”和托管项目删除调用文件所在电脑的 Windows 系统回收站接口。文档及 `.Tiance` 一起回收，之后可在系统回收站恢复或清理。
- 不再写入天策私有 `.trash` 或另建同盘归档，不再使用 shutil.move 的跨盘复制兜底；系统不提供回收、取消或回收失败时停止，不自动转为永久删除。
- 回收成功后移除项目登记。若登记写入失败，明确报告文件已回收且登记尚未移除，可重试移除登记；不假装回滚系统文件操作。
- 分类删除先校验所有目标，再逐项回收并移除登记，最后删除空分类。中途失败保留未完成项和分类，并返回已完成项目；前端刷新真实状态。分类新增并发项目时，不随清理分类而丢弃新项目登记。
- 旧版 `.trash` 内容不会自动搬运或清理；本次变更只作用于新的删除操作。创建失败的空目录使用 rmdir 清理，不递归删除其中后来出现的文件。

实现入口：`app/infra/system_recycle_bin.py`、`app/infra/projects/project_storage.py`、`app/services/project/projects.py`（相对 `1_PythonServer`）。系统接口为 `IFileOperation`；进度回调拒绝永久删除，检查实际回收结果和中止状态，不把“接口返回”直接当成成功。

## 会话

普通对话、分支、AI 子会话和功能会话共享会话身份、父子关系、消息与运行状态。当前功能会话包括自动命名、记忆压缩和记忆管理；具体功能差异来自配置与运行器，不应成为另一套消息数据库。

会话关系至少包含：

- 项目和会话 ID；
- 父会话、来源消息与关系类型；
- 创建者和历史方式；
- 运行状态、模型/角色/工具设置；
- 正式消息、工具调用和工具结果。

## 项目数据库

项目数据库是每个项目 `<项目根>/.Tiance/tiance.db`，保存该项目的会话设置、草稿、引用、消息、分支关系、运行事件、记忆与压缩记录，以及原始请求/响应的审计快照。它不保存工作区里的 Word、Excel 等普通文档正文。全局 `Data/db/tiance.db` 保存工作区偏好、功能模型配置、网络配置和活动统计；Token 与费用明细单独保存在 `Data/usage/usage.db`。

2026-10-30 删除兼容代码后，首次补丁只恢复了全局 v48→v49 和项目 v5→v7；遗漏表内功能配置升级，导致 v32 压缩配置在每次聊天开始读取阻塞设置时让请求直接失败。本次按删除前能力清单恢复已知升级路径，重构实现结构，而非要求用户手动重设。新版本必须同步维护新库快照、迁移步骤、冻结资源与历史样本测试；只验证空库或最新相邻版本不足以验收。

发布检查见[数据库升级发布检查](09_开发验证与发布.md#数据库升级发布检查)。工具项目 `.Tiance/tool-calls/records-index.sqlite3` 是由 `records.jsonl` 生成的派生索引，通过 `PRAGMA user_version` 登记索引版本（当前 v1）。首次查询遇到无版本、版本不符或表/索引结构不符时，自动从 JSONL 重建，不要求用户操作；删除旧索引结构、完整重放与版本登记位于同一 SQLite 事务，失败回滚并在后续访问重试。重建更新分页快照标识，已有页面按快照失效流程刷新；索引版本和结构正常时仍只索引新增行。索引结构或字段含义变化时必须提升 `INDEX_SCHEMA_VERSION`，无需保留逐版本迁移步骤，不得删除 JSONL 正式记录。工具私有业务库和用户主动查看的数据库不由平台统一升级。

### 压缩记录的局部写入（BE-090，2026-10-29）

压缩记录继续保存在 `conversation_session_events` 的 `compressions` 流中，保留原来的 ordinal、JSON 内容及只读数据视图。新增记录直接追加；运行、失败、完成和陈旧任务恢复按当前会话的 `compression_id` 更新一条记录，不再读取并替换整段压缩历史。`ProjectConversationMemoryRepository.append_compression` 也使用同一追加入口。

`idx_compression_record_id` 按会话和压缩 ID 定位记录；`idx_compression_status` 支持查询活动任务及最新完成结果。索引包含在当前新库的完整结构中，旧库通过 v6→v7 的正式迁移建立或校验。历史列表与分支快照继承仍按原规则读取，不为状态更新引入另一套记录来源。

来源记录、功能会话结果和任务文档仍在原有项目写事务内提交；SQL 失败依赖事务回滚，取消原来的全量写回补偿。创建失败时只额外清理本次新建的物理会话目录。重复运行状态和已完成任务的重复提交不重写记录；任务冲突、压缩边界校验及陈旧任务等待时间保持原规则。

实现入口：`1_PythonServer/app/repositories/project/conversation_compression_records.py`；回归入口：`tests/test_compaction_record_updates.py`（相对 `1_PythonServer`）。

项目内正式会话状态保存于：

```text
<项目根>/.Tiance/tiance.db
```

会话附件仍位于项目 `.Tiance` 下的会话附件目录。JSON、JSONL、缓存和前端 store 不应成为同一正式消息的第二个权威来源。

SQLite 中的主要事实由 repository 读取和写入。合法 JSON 但结构不符合领域合同的数据不能被当作“不存在”；损坏数据应明确报错或进入可观察修复流程。

## 审计快照的增量存储

数据库 schema v6 起，逻辑模型记录 `model_exchanges` 和物理 HTTP 交换使用 `audit-manifest-v2`。对外仍返回每一轮完整、脱敏后的请求与响应；存储层记录实际 JSON 结构的变化，不重新运行上下文组装、记忆压缩或工具选择逻辑来猜测历史内容。

- `conversation_session_events` 的模型记录保存版本引用；HTTP 工件的 `conversation_artifact_payloads` 保存 gzip 压缩后的版本引用，标记为 `gzip+audit-manifest-v2`。
- `conversation_audit_snapshots` 按会话、记录类型建立独立版本链，保存追加/替换、删除、列表区间替换和对象键顺序变化。记忆压缩导致消息列表缩短或替换时同样保存实际变化。
- 大于等于 1 KiB 的字符串和工具定义集合进入 `conversation_audit_blocks`，按内容哈希去重并 gzip 压缩。同一项目的不同轮次、会话和审计类型可以共用内容块。
- 最多连续保存 32 层增量，然后保存压缩检查点；增量比检查点更大时也直接保存检查点。检查点仍引用共用大块，不把大块正文复制回来。
- `conversation_audit_snapshot_blocks` 记录检查点和增量新引入的块引用。用户删除会话或替换该会话的逻辑审计记录时，事务内释放无人引用的 v2 块，共用块继续保留。

版本、内容块、引用关系及所属事件/工件在同一个 SQLite 写事务内提交。读取在同一个数据库快照内还原，逐层校验结构哈希，校验块哈希，并核对最终完整正文的大小及 SHA-256。缺失基版本、损坏内容块或跨会话/跨类型引用必须报错，不能返回删减后的请求。

增量基准是同一会话、同一类型上一条已持久化记录。异步任务完成次序不决定业务轮次；业务时间、轮次和尝试编号仍来自原记录，版本链只负责无损存储。

### 原始响应缓冲与正常退出

- 每次物理 HTTP 请求独立持有 `ResponseCapture`；正文解析与原始记录捕获使用同一批网络数据。原始响应不超过 8 MiB 时使用内存，超过后转为临时文件。阈值只选择暂存介质，不截断响应，也不累计整个工具调用循环。
- 流式结束后直接移交可分块读取的缓冲，不调用无长度限制的 `read()`。接收端和保存端分别持有引用；最后一个持有者释放时关闭临时文件。各层流式迭代器必须显式关闭，不能等垃圾回收才登记最后的保存任务。
- 保存端最多同时执行两份 HTTP 审计重型写入。UTF-8 验证、必要时的 Base64 转换、JSON 字符串转义、大小及哈希计算、gzip 压缩均按块执行。完整记录的大小与哈希同时用于工件及快照，不重复构造整份 JSON。压缩内容通过 SQLite BLOB 分段写入，审计存储继续使用 v6 引入的 `audit-manifest-v2`。
- 内容准备在会话写锁之外执行；内容块、快照、工件状态和完成事件仍在同一事务内提交。保存失败保留原始缓冲，退出重试可重新保存同一个工件，不创建重复成功记录。
- 正常退出由 `DesktopExitCoordinator` 统一停止新会话及后台任务，等待运行中会话取消收尾、后台任务结束、已登记操作提交或回滚，最后排空审计保存。取消收尾仍允许登记最后的记录。只有上述工作成功完成，桌面退出准备接口才返回 `ready=true`；保存失败保留窗口并支持重试。
- 桌面壳销毁窗口后的 8 秒后端退出保护不再承担上述业务数据保存的等待期限。突然结束进程或断电的恢复策略不在本次改造范围内，原始临时文件不是崩溃恢复日志。

运行错误继续保存在 `conversation_journal` 的 `model.request_attempt.failed` 等事件中，最终状态及兜底错误继续保存在 `conversation_runs`。对话中的实时错误仍来自流事件，历史错误仍由原来的运行/尝试接口返回；不会依赖解压审计快照来显示错误。

存储约束与体积口径：

- 正常审计读写只支持增量快照格式，不混读旧格式。旧内联 JSON、gzip 全量正文、`audit-manifest-v1` 及 `gzip+audit-manifest-v1` 的解码集中于迁移模块，由 v5→v6 和 v7→v8 步骤调用。v1 按历史清单恢复 `.Tiance/conversations/audit_blobs/<哈希前两位>/<哈希>.blob`，检查路径、大小、SHA-256、UTF-8 和占位位置，再转换为 v2 并校验完整正文；原外部块保留，不删除。缺失、损坏或未知格式明确失败并回滚。
- 项目初始化由同库写锁合并并发请求。确定性的迁移校验失败只记录错误文本、数据库/WAL 及本次读取的外部文件状态，不保存正文或异常调用栈；这些输入未变化时，后续界面请求返回原错误，不再次迁移或创建备份。数据库/相关外部文件改变，或后端重启后重新尝试。SQLite 锁忙、普通文件 IO 故障和取消不记作持久的校验失败。
- 新库直接创建当前完整结构；旧项目库在正常读取前按版本链升级至 v8，建立审计表并转换原记录，包括旧 v6/v7 库中残留的内联审计。正常审计读写只使用当前格式。旧审计的一次性数据清理仅指下述已经发生的操作，当前程序不包含清理入口。正式聊天、运行记录和错误事件独立保留。
- 2026-10-19 经用户明确授权，一次性清理当前 9 个项目的 3,107 条旧逻辑审计、3,260 条旧 HTTP 正文和 2,345 个旧外部块，保留工件元数据及错误事件关联；逐库校验其余数据不变。清理脚本执行后移除，不作为应用的升级或兼容流程保留。
- `size_bytes` 仍表示还原后的完整正文大小；`stored_size_bytes` 表示工件自身的压缩引用大小，不包括共享版本和内容块。统计实际占用应合计相关表及索引，不能把每条逻辑正文大小当作实际磁盘占用。
- 2026-10-19 对一个真实项目 100 条逻辑记录进行只读抽取及临时库回放：旧记录 JSON 45,059,407 字节、引用外部块 1,501,028 字节，新临时数据库含索引 2,060,288 字节；100 条完整正文逐条 SHA-256 校验一致。这是样本结果，不是固定压缩比。

## 四类状态

### 启动时恢复工作区位置（2026-11-02）

全局 `workspace.last_opened` 保存各分类最近选中的项目和会话 ID，属于导航偏好。读取时只核对分类、项目及其归属，不打开这些项目的会话数据库，也不检查每个记住的会话是否仍存在。实际加载选中项目的会话列表时，再以该列表判断记住的 ID 是否有效；失效时使用该项目当前有效的会话。显式保存新的项目/会话选择仍校验目标归属与存在性。

启动封面在语言、主题及应用框架就绪并完成绘制后移除。项目、工具和供应商目录各自显示加载、错误及重试状态，不以全部目录请求结束作为显示主界面的条件。项目数据库仍在实际使用前通过统一入口升级；读取导航偏好不等于使用所有记住的项目。

### 状态分类与通知

请求注入预览 `injection_preview` 属于派生文档。保存或删除它不增加 `conversation_revision`，也不发布会话变更通知；嵌套事务只排除该文档自身的写入，同一事务内其他真实变化仍通知。消息、设置和记忆文档继续走原来的提交后通知。完全相同的文档保存跳过数据库 UPDATE。

草稿预览前端按实际请求输入、会话设置、角色和历史消息版本更新，不依赖对象实例或草稿发布次数。`POST /api/llm/chat/injection-preview` 只返回 `{ "ok": true/false }`；完整预览仍通过现有虚拟文档路径读取，保存后只通知预览文件自身刷新。

| 类型 | 示例 | 规则 |
| --- | --- | --- |
| 正式事实 | 用户消息、完整助手回复、已提交工具调用和结果 | 进入后续模型上下文，不能被展示分页截断 |
| 运行状态 | running、waiting、error、cancelled | 表达生命周期，不冒充助手正式回复 |
| 展示状态 | 当前标签、展开节点、画布位置 | 可重建，不决定业务事实 |
| 审计 | 原始请求、响应、尝试、大小和错误 | 用于排查，不自动进入模型上下文 |

## 分支与派生

分支保留来源消息和父子关系。派生会话可以继承已经成立的压缩覆盖和记忆，但缓存谱系只用于供应商缓存提示，不能决定分支消息是否存在。

工具调用与工具结果构成协议原子组。读取历史、分页或派生时不能从组中间切开；检测到损坏组时应暴露数据问题，不能静默删除后继续生成看似正常的请求。

## 工作区展示状态

打开标签、活动会话、布局和缩放等由前端/工作区状态保存。异步保存必须防止旧请求后返回覆盖新状态。读取失败不能以空对象覆盖原文件。

聊天中自动识别出的裸文件名（例如行内代码 `报告.md`）表示按名称查找，不预先假定文件在项目根目录。点击查看、资源管理器、系统应用或复制路径时，读取当前项目内容文件快照；文件名唯一匹配后才执行，重名列出实际路径，读取不完整则明确提示。此查找沿用内容文件快照范围，不包括根级 `.Tiance`、内部临时文件和符号链接；这些文件应提供明确路径。绝对路径、带目录的相对路径、`./报告.md` 和显式 Markdown 链接始终按指定路径处理，不替换为其他同名文件。消息原文和文件都不因此改写。

文件读取返回不存在时，标签页显示“找不到文件”和实际路径；仅凭找不到不能断言文件曾被删除。

## 全局使用统计

状态栏的性能、Token 用量、任务耗时、工具调用使用统一尺寸的四个页签。三个统计页按本机时区和自然月显示每日柱状图（28～31 天，零值日期也保留）；累计数和整体前三名不受月份筛选影响。展开时刷新，展开期间每 30 秒更新，切换月份会取消旧请求。

- Token 用量保存在独立的 `Data/usage/usage.db`，覆盖主对话和功能模型，不读取会话正文或审计。明细按请求去重；累计值与明细在同一事务中更新，月度查询按时间索引读取选定日期范围。
- 模型用量前三名直接读取累计表，按 `(provider_id, model_id)` 合并各功能及币种的 Token；同名模型在不同供应商下分别排名，使用历史用量而非当前模型清单。只为入榜供应商读取当前显示名称；配置已删除或无法读取时显示历史供应商 ID，模型显示实际模型 ID。账本不存显示名称快照，无法恢复已删除配置原来的自定义名称。删除供应商或模型配置不会调用用量清除，也不自动按时间淘汰用量记录；只有显式清除模型用量才会删除对应明细和汇总。
- 耗时从 `Data/db/tiance.db` 的 `workspace_activity_records` 汇总。`ai_run_elapsed_ms` 活动的 `source_id` 是运行 ID，另外保存项目 ID、会话 ID、用户消息 ID；同一运行重复结算只计一次，同一用户消息再次运行分别计数。完成、失败和取消均记录实际经过时间，包含执行期间的工具与重试等待；正在执行的任务不进入已结算统计。跨日任务归入结算日，并行任务分别累加。已完成请求的幂等回放不产生新的耗时记录。
- 耗时排行由全局库按耗时索引先取前三名，再定向读取对应会话标题和单条任务摘要。没有关联信息或源会话已删除时保留耗时和任务编号，不遍历所有项目补找。新增关联列不回填历史会话、不改变旧统计数值。
- 工具统计复用工具项目 `.Tiance/tool-calls/records.jsonl`。首次建立仅含工具名、时间、成功状态的内存缓存，之后只解析追加记录；替换、截断或移除文件会失效缓存。统计缓存不保存参数和结果正文，不增加持久化账本。

查询入口为 `/api/workspace/statistics/{tokens|runtime|tools}`，参数为 `month=YYYY-MM` 与 IANA `timezone`。夏令时日期按各天的本地午夜换算 UTC 边界。窗口展示和图表不承担任务计时、去重或业务记录写入。

### 用量账本与累计汇总（2026-10-29，BE-079）

`models.json` 等模型集配置仍只保存配置；用量和已结算金额由独立账本管理。前端/API 的返回结构不变。

- `usage_records` 保存有效用量明细、原始时间、项目/会话/请求身份、功能分类、各类 Token、计价时保存的金额/币种以及估算标记。时间另外规范化为 UTC 微秒索引，用于本机时区的日边界查询；不会拿当前模型价格重算旧账。
- `usage_totals` 按模型及会话两个范围保存累计值，并保留供应商、模型、功能、币种维度。供应商顶部、模型列表、会话统计及项目分类看板直接查询这些汇总，不扫描历史明细，也不把全部历史常驻 Python 内存。不同项目的同名会话 ID 不合并；混合币种沿用“不合并金额”的既有合同。
- 请求 ID 优先去重，缺少请求 ID 时沿用消息 ID；两者都没有则按明细 ID 保存。同一次请求修正用量时，先减旧值再加新值，保留首次记录的归属和时间。不同请求即使共享助手消息 ID 也分别计数。明细和所有汇总使用一个写事务提交，不能只成功其中一部分。
- 使用 WAL 与独立连接，读取使用一致性快照，写入由 SQLite 串行提交。聊天流结算中的阻塞写入通过现有 `finish_thread` 执行，不占住异步事件循环；取消或正常关闭会等待已经开始的写入线程结束。

正常业务只读取 `Data/usage/usage.db`。首次创建空库时直接创建明细、索引和汇总表；启动迁移在尚无完成标记时自动重放旧 JSONL，或从旧全局用量表导入。重放先在临时库完成并核对汇总，再在目标库事务内合并缺失记录、核对汇总并写入完成标记；现有记录优先，旧删除事件只作用于历史数据，历史源文件和源表保留。2026-10-30 曾移除导入程序，2026-11-01 已集中恢复至 `app/migrations/usage_db/`，普通读取不承担兼容转换。

显式清除模型用量会直接删除其明细和汇总，不再追加删除日志。空闲页可被后续写入复用，删除后执行有界的增量回收；不在每次记录用量时整理整个库。维护接口 `UsageSqliteStore.maintain(full=True)` 可在空闲时执行完整 `VACUUM`，需要额外临时磁盘空间并等待写锁。`rebuild_totals()` 可从保留的明细原子重建汇总，保留原计价，不重放旧备份。两个维护接口都不是高频后台任务。

已有 JSONL 只是历史文件，当前程序不读写，也不擅自删除。备份当前账本时应通过 SQLite 备份接口，或停服后复制整个用量目录，不能在数据库活跃时仅复制 `usage.db` 而漏掉 WAL。

实现入口：`app/repositories/llm/usage_sqlite_store.py`、`usage_repository.py`。回归测试包括 `test_usage_sqlite_storage.py`、`test_usage_batch_overview.py`、`test_chat_usage_recording.py` 和 `test_workspace_statistics.py`。

## 会话展示同步（2026-10-27）

触发本次改造的事故复盘见 [隐式截断与隐藏默认值专项问题分析](22_隐式截断与隐藏默认值专项问题分析.md) 案例 8：后台压缩期间全量历史请求被重复取消、完成提示与子会话生命周期耦合。以下描述修复后的同步合同。

- AI 生成仍通过运行级 WebSocket 传输增量事件；选中会话另订阅通用会话更新通知，生命周期不依赖 AI 运行或压缩子会话。
- 数据库提交后发送轻量失效通知，事务回滚不通知。通道只保存有界唤醒信号，不缓存正文、不另建一份历史。
- 项目 `conversation_revision` 用于同步会话列表；消息追加/替换在同一事务中维护会话消息版本，替换另更新重置版本。读取分页和版本使用一致的只读快照。
- 首次展示请求最近 80 条消息；向上滚动通过 `before_message_id` 补历史，新增消息通过 `after_message_id` 分页补齐。工具消息页边界会补齐关联助手调用。展示分页不影响后端完整历史和 AI 上下文组装。
- 同一会话读取串行化、合并重复刷新，保留流式本地内容和旧页面；状态改变不取消在途读取，读取失败可重试。
- WebSocket 初次订阅和重连均返回版本快照；断线期间前端每 15 秒只校对轻量版本。服务端仅在订阅存在时每 15 秒检查一次版本，以覆盖直接写数据库的独立工具进程，不扫描历史。正常后端事务和工具结果落盘会立即唤醒订阅。
- 压缩成功以 `submit_memory_compaction` 保存摘要并提交 `completed` 状态为准。监测只读任务状态，不分析 AI 回复文案，不以子会话空闲推测成功；完成提示继续遵循主会话回复边界。

## 取消边界与已经完成的提交（2026-10-30）

取消是运行状态变化，不能把已经完成的工作改写为“未执行”。并行工具维持正常的结果顺序；停止时先停止并收齐正在运行的子任务，再保存队列内已经完成的结果，只有没有完成结果的调用才登记取消。

最终助手回复、助手工具调用轮次和工具结果的落盘与内存完成标记构成一个提交单元，由 `finish_commit` 等待完成后再传递取消。重复停止不能打断这个标记同步，否则同一条已保存回复可能再被登记成取消回复。提交失败仍传播错误，不报告虚假的成功；不会为了收尾重新执行工具。

回归：`1_PythonServer/tests/test_current_schema_and_commits.py`，覆盖快慢并行工具与最终保存线程阻塞期间重复取消。

## 相关文本文件的一次保存（FEA-014）

文件工作区提供 `saveTextFiles` / `PUT .../files/content-batch`，普通项目与工具项目使用同一文件事务实现。先校验全部路径和文件版本，暂存全部新内容并备份原文件，再替换目标；任一替换、文件信息生成或工具注册表重建失败时恢复原文件。工具层只负责现有标准文件校验和一次注册表重建，不让通用文件层认识工具字段。

这是一次保存失败后的成组回滚，不宣称多个文件对所有外部读取者瞬时可见，也不提供断电恢复日志。恢复失败会明确报出保留的恢复文件，不删除唯一可恢复副本。前端工具基础设置和示例设置各提交一个批次，不再串行发两次互相独立的保存请求。
