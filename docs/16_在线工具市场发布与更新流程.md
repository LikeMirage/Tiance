# 在线工具市场发布与更新流程

这份文档说明如何把工具发布到在线工具市场，以及客户端如何发现和更新工具。当前工具市场仓库为：

```text
https://github.com/LikeMirage/Tiance-tools
```

公开市场通过 GitHub Pages 提供只读内容，客户端读取仓库根目录的 `index.json`，再按清单下载工具文件。

## 一、源码仓库与发布站点

市场源码仓库的基本结构是：

```text
tools/
  <tool-id>/
    manifest.json
    ...工具文件...
scripts/
  build_market.py
  tool_package.py
.github/workflows/publish.yml
```

推送到 `main` 后，GitHub Actions 会运行 `scripts/build_market.py`，校验全部工具并生成 `dist/index.json` 和 `dist/packages/*.zip`，再部署到 GitHub Pages。客户端读取的是 Pages 发布站点，不是直接读取源码仓库中的 `tools/`。

`index.json` 负责列出市场中有哪些工具；每个源码工具的 `manifest.json` 负责描述版本、作者、许可证和兼容范围，`.tool/` 则保存调用名、说明、参数、输出、案例和权限默认值等真实工具合同。构建脚本从这些源文件生成索引、安装包大小和 SHA-256，不应手工维护一份重复的发布索引。

稳定工具 ID 是更新关系的依据，显示名称不是稳定身份。修改显示名称不会产生新工具；修改稳定 ID 会被客户端视为另一个工具。

## 二、发布前检查

进入工具市场仓库，先同步远端并确认工作区：

```powershell
cd <Tiance-tools仓库>
git pull --ff-only origin main
git status --short
```

检查每个工具：

- `manifest.json` 是合法 JSON；
- `id`、`name`、`version`、`entry` 和参数定义完整；
- 入口文件确实存在；
- 工具说明中的调用名与 manifest 一致；
- 依赖清单只包含工具运行时真正需要的依赖；
- 示例和规则文件路径与 manifest 一致；
- 每个顶层输入参数都已明确配置 `permission_type`，普通配置参数使用 `none`，不能靠缺失字段代替发布者判断；
- `.tool/permissions.json` 存在，且 `tool.json.files.permissions` 指向该文件；
- 权限默认值按能力和作用范围配置，不把所有权限点机械设成同一种处理方式；
- 不包含 API Key、Token、个人项目文件、会话、数据库和本机缓存。

如果工具依赖需要安装，依赖应落在工具自己的依赖配置和依赖目录规则中，不把开发机全局环境当作发布包的一部分。

## 三、版本和清单

工具有行为、参数、规则、入口或依赖变化时，递增工具自己的版本号。版本号写入该工具的 `manifest.json`。市场根目录的发布索引由构建脚本根据全部工具自动生成，不手工同步版本条目。

发布前确认：

```powershell
Get-ChildItem tools -Recurse -Filter manifest.json
python scripts/build_market.py
```

本地构建会重新创建 `dist/`，并一次性报告结构、路径、清单或兼容性错误。不要把未实现的参数写进正式合同，也不要手工修改生成的 `dist/index.json` 来掩盖源工具问题。

## 四、提交和推送

```powershell
git add tools/<tool-id>
git diff --cached --check
git diff --cached --stat
git commit -m "release tool <tool-id> <version>"
git push origin main
```

推送后必须等待 `Validate and publish tool market` 工作流成功。该工作流使用 Python 3.13 重新验证并构建市场，然后部署 `dist/` 到 GitHub Pages。Pages 更新后，客户端重新读取 `index.json`；客户端还会校验安装包大小、路径和 SHA-256，校验失败时不会安装。

## 五、客户端更新规则

客户端使用稳定工具 ID 查找本地已安装工具，并直接比较工具根目录 `manifest.json` 中的版本。显示名称和本地调用名都不是更新身份；工具市场不在 `.Tiance` 中保存来源或版本收据。

首次安装使用完整工具包，并采用包内 `.tool/permissions.json` 作为初始权限策略。已有工具更新时，市场拥有程序代码、资源、参数权限分类等标准 `.tool` 合同、依赖声明和 `manifest.json`；用户拥有本地调用名、启用/停用状态、动态加载状态、`.tool/permissions.json`、`program/config.json`、`dependencies/`、本地分类和 `.Tiance/` 运行数据。更新时：

1. 下载远端清单和工具文件；
2. 校验 HTTPS、路径范围、文件大小和 SHA-256；
3. 在临时目录完成解压和结构检查；
4. 把本地调用名、启用状态和动态加载状态写入已校验的新版工具合同；
5. 将完整旧工具目录改名为回滚备份，再把完整新版快照切换到正式位置；
6. 从旧备份直接移动 `.Tiance/`、`dependencies/`、`.tool/permissions.json` 和 `program/config.json` 到新版目录，不复制大目录，也不合并用户配置；
7. 重建工具注册表；全部成功后才删除旧备份，任一步失败都把本地状态移回并整体恢复旧版。

完整快照替换可以让新版已经删除或改名的旧程序文件真正消失，避免简单覆盖产生新旧代码混用；本地大目录使用同盘移动，避免长会话和依赖环境被重复复制。包内的 `program/config.json` 只作为首次安装模板：已有工具的本地配置始终原样保留。兼容更新的程序必须能读取原有配置；需要改变必填配置合同的版本应使用新的稳定工具 ID 发布。

更新不会改变用户已经选择的启用、停用或动态加载状态，也不会删除已安装依赖。新版声明了依赖时，客户端继续明确打开依赖管理入口，由用户决定安装；工具市场包本身不得携带依赖环境。

供应商凭证、用户项目、会话、数据库和本地密钥不属于市场包，不能被工具市场覆盖。

## 六、发布后核对

- 在 GitHub 仓库确认提交已经进入 `main`；
- 在 Actions 中确认 `Validate and publish tool market` 成功；
- 通过 GitHub Pages 地址直接打开 `index.json`，确认能看到新版本；
- 在软件中刷新在线工具市场；
- 检查工具版本、显示名称、调用名和说明；
- 安装或更新一次工具，确认入口可执行；
- 检查工具本地配置和依赖没有被无关覆盖；
- 删除或改名的工具应在索引中明确处理，不能留下指向不存在文件的条目。

## 七、常见错误

### 推送工具后立即在客户端判断失败

源码进入 `main` 不等于 Pages 已完成部署。先检查市场构建工作流，再刷新客户端；不要因为短暂看不到新版本就手工修改发布索引。

### 本地构建失败却只提交单个工具

市场每次会验证全部工具，而不是只打包本次目录。正式推送前运行 `python scripts/build_market.py`，一次修正所有阻塞错误，不能依赖客户端安装阶段替市场发现结构问题。

### 只更新显示名称

显示名称不是稳定身份。若误改了 `id`，客户端会把它当成新工具，可能造成重复安装。

### 把凭证打进市场包

市场包可被下载和缓存。任何 API Key、Token、供应商凭证和个人数据都必须留在本地，不得进入仓库。

### 直接修改已发布版本

客户端可能缓存旧清单。已经发布的版本内容应保持不变；有修复时递增工具版本再推送。
