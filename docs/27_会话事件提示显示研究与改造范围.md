# 会话事件提示显示研究与改造范围

记录日期：2026-10-08。实施更新：2026-10-09。状态：已完成显示投影、通知边界及相关稳定性修复，验证记录见第 14 节。

最新用户约束（2026-10-09）：保留现有“左右横线、中间提示框”的外观，不换成用户消息样式。提示在处理范围内随“已处理”折叠、范围外独立显示，重点修正通知归属、运行状态及显示稳定性。后文独立状态栏、用户消息卡片外观均为此前讨论的备选方案，没有采用。用户随后授权“开始完整优化修复”，已按这些约束实施。

追加约束：所有会话系统提示仅在完整消息边界插入。当前模型流式响应进行中收到的提示先记录并等待，等这一次流式响应结束后展示；无需等整个用户回合或整轮工具调用结束。

本文记录对话区事件提示的完整范围、与回合判定和折叠的冲突、已完成的最小复现，以及后续可以评估的显示方案。当前明确需要研究调整的是“左右横线、中间提示框”这一组提示；工具、思维过程和“已处理”等原有会话容器及其折叠功能不在改造范围内。

阅读说明：第 1—13 节保留研究时的现状、讨论及约束，其中“尚未修改”等描述对应当时阶段。当前实际行为、实施文件和验证结果以第 14 节为准。

## 1 用户反馈与范围约束

用户反馈 AI 调用工具期间，对话区有时高频闪烁。截图中可见消息正文、思考或工具块暂时消失，而复制、导出按钮及 Token 用量行仍然显示；另外也出现过仅剩最后一条失败提示、上方大片空白的画面。

用户还观察到：AI 仍在继续运行时，出现记忆压缩提示会使前面的回复提前汇总用量、折叠为“已处理”，表现得像本轮已经结束。请求失败提示也有类似表现。

本次范围以用户指定的外观和组件为准：

- 需要研究调整所有使用“左右横线、中间提示框”的运行提示。
- 保留工具调用容器、Thinking 容器、AI 过程时间线和“已处理”容器。
- 保留上述原有容器的手动折叠和自动折叠功能，不将其迁移为新的通知界面。
- 用户消息、AI 正文、Token 统计、复制和导出功能、普通 System 消息不是本次需要迁移的提示。
- 本阶段先记录和研究，不修改程序，不将备选布局视为已经批准的产品方案。

“第三方消息”是本次讨论中对运行提示的称呼，不代表提示一定来自第三方服务器。压缩状态、模型切换等也由程序自身生成。

## 2 完整提示类型清单

全前端检索 `ConversationEventNotice`、`chat-msg__event` 和 `chat-msg__event-label` 后，确认这一外观统一来自 `ConversationEventNotice`。它包含左右伪元素横线和中间图标、文本提示框，共有四类业务调用者。

| 类型 | 组件 | 样式类 | 触发来源 |
| --- | --- | --- | --- |
| 记忆压缩提示 | `MemoryCompactionNotice` | `chat-msg__memory-compaction` | `role=system` 且 `name=memory_compaction` 的记录 |
| 请求失败和其他错误提示 | `RunFailureNotice` | `chat-msg__run-failure` | 单次请求失败、运行最终失败，以及其他 `role=error` 消息 |
| 请求重试提示 | `RetryNotice` | `chat-msg__upstream-retry` | AI 消息上的 `retryStatus` |
| 模型切换提示 | `ModelSwitchNotice` | `chat-msg__model-switch` | 相邻有效模型标识发生变化 |

### 2.1 记忆压缩提示

同步和异步压缩都使用同一显示组件。目前后端产生以下八种文案：

| 阶段 | 同步压缩 | 异步压缩 |
| --- | --- | --- |
| 进行中 | 正在执行记忆压缩。 | 正在异步执行记忆压缩。 |
| 完成 | 已完成记忆压缩。 | 已完成异步记忆压缩。 |
| 失败 | 记忆压缩失败。 | 异步记忆压缩失败。 |
| 取消 | 记忆压缩已取消。 | 异步记忆压缩已取消。 |

显示颜色由消息状态决定：`error` 为错误、`done` 为完成，其余为进行中。取消文案目前也走错误样式。

开始、完成、失败和取消提示均通过通知缓冲区在主会话的完整回复边界追加。它们是不同记录，不强制相邻；正在输出正文时不会把提示插进正文中间。

状态消息使用 `notice_{compression_id}_{status}` 作为稳定消息 ID，在同一个数据库事务中检查和追加，实现重试去重。任务结果提交成功即可安排完成提示，不再等待压缩子会话最终回复和收尾；之后的运行失败不能覆盖已提交的压缩成功状态。

### 2.2 请求失败和其他错误提示

这一组件覆盖三种来源：

1. 单次物理请求失败，通常显示“第 X/Y 次请求失败：原因”。
2. 整轮运行最终失败；没有单次失败记录时，显示“请求失败（共尝试 Y 次）：原因”等文案。有单次失败记录时，最后一条失败记录可以携带最终运行结果，避免重复显示最终错误。
3. 其他映射为 `role=error` 的错误消息，包括请求启动或会话请求阶段的错误。

余额不足、`All connection attempts failed`、生成未完整结束 `length`、超时等属于错误原因，不是新的提示组件类型。原始 JSON 较长时，当前失败框会换行并增高。

失败提示有两个显示出口，后续不能遗漏任何一个：

- 消息列表中的独立错误消息，由 `ChatMessageItem` 渲染。
- AI 过程时间线中的 `attempt_failure` 项，由 `ChatAssistantProcessTimeline` 渲染。

### 2.3 请求重试提示

当前文案为“上游请求失败，正在进行第 X/Y 次尝试”。图标具有旋转动画，错误详情放在提示的 `title` 中。

该提示是 AI 消息上的附属状态，没有独立消息身份。收到后续正文、思考或工具调用进展后，会清除活动重试提示；已经记录的尝试失败记录仍然保留。

### 2.4 模型切换提示

`buildModelSwitches` 按显示消息顺序比较模型标识。用户消息使用 `targetModelId`，其他消息使用 `modelId`；第一次出现有效模型不显示切换提示，之后不同模型才显示。

它显示在对应消息前方，文字是切换后的模型标识。它不是独立消息，但仍占据消息列表高度；列表测量对模型切换提示另有高度补偿。

## 3 明确不纳入的原有组件

| 组件或内容 | 当前职责 | 本次范围 |
| --- | --- | --- |
| 用户消息及其展开、时间、复制、编辑 | 展示用户输入 | 保留 |
| AI 正文 | 展示模型回复 | 保留 |
| Thinking 容器 | 展示思维过程及用时 | 保留容器及折叠功能 |
| 工具调用容器 | 展示调用列表、状态、权限确认和详情 | 保留容器及折叠功能 |
| 工具自身的失败计数和结果 | 反映某个工具的执行事实 | 保留，不等同于上游请求失败提示 |
| AI 过程时间线 | 组织思考、说明、工具等过程 | 保留；其中事件提示自身的显示出口可单独研究 |
| “已处理”容器 | 折叠已经结束的处理过程 | 保留容器及折叠功能 |
| Token 用量行 | 展示请求用量 | 保留；不能因运行提示出现而误判回合已结束 |
| 普通 System 消息 | 展示普通系统消息正文 | 不属于横线提示框，不能批量迁移 |

研究事件提示的归属不等于重做这些会话组件。后续若要修复提示引发的错误收起，应纠正传给容器的运行状态和回合身份，而不是改变容器本身的折叠交互。

## 4 已验证的冲突

### 4.1 最后一行被用作正在运行的回复

`ChatMessageList` 从 `displayMessages` 的最后一个元素取得 `liveMessage`，并且只给最后一行传入流式状态和计时时钟。`ChatMessageItem` 进一步要求 `isSessionStreaming && isLastMessage && role=assistant && status=running` 才将消息识别为流式回复。

因此，如果后面追加压缩或失败提示，仍然运行的 AI 回复会失去界面上的流式身份。它会走历史显示分支，可能自动归档为“已处理”、显示 Token 行，并使 Markdown 从流式路径切换到完整后台渲染路径。

通过实际组件静态渲染，保持同一个 `running` AI 消息不变、仅改变末尾提示是否存在，获得以下结果：

| 场景 | 工具名称可见 | “已处理”可见 | Token 行可见 |
| --- | --- | --- | --- |
| 工具运行，AI 回复是最后一行 | 是 | 否 | 否 |
| AI 回复后追加压缩提示 | 否 | 是 | 是 |

这验证了状态分类冲突。静态渲染不能测量实际闪烁频率。

### 4.2 提示切断合并过程并提前汇总用量

`coalesceAssistantTurnProcesses` 遇到独立请求失败记录或非 assistant/error/tool 记录时，会调用 `flushAssistantTurn(false)`。该参数让前面的片段被视为已经关闭，即使整个会话仍为 `running`。

最小复现中，两条回复的用量分别为 10 和 20，最后一条正文为空但含有运行中的工具。未加入提示时保持两条回复；加入压缩提示后，前面两条回复被合并，用量提前变为 30。

合并过程还使用最后一条回复的消息身份作为合并结果身份。消息合并或拆分可能改变 React 挂载结构，不能将其当成纯文本提示更新。

### 4.3 单次失败记录被当作最终错误

`findLastAssistantLikeMessage` 同时接受 `assistant` 和 `error`，没有排除单次请求失败记录。`finalizeTerminalConversationTurns` 取到末尾错误后，会将它的错误状态用于收尾前面的工具。

最小复现保持会话 `runtimeStatus=running`、AI 消息 `status=running`，并追加一次 `attempt_index=1, attempt_count=2` 的失败记录。显示投影仍保留 AI 消息的 `running` 状态，但工具状态从 `running` 变成 `error`。

这里改变的是前端显示投影，不代表实际工具执行已经失败。一次请求失败和整轮最终失败必须区分。

### 4.4 流式显示和刷新后的表示不同

流式累计器收到 `retry_reset` 时：已有提交过程则将失败提示插入 `processItems`；没有提交过程则生成独立错误消息。刷新映射则把持久化尝试失败记录映射为独立 `error` 消息，再按时间与正式消息合并排序。

重连恢复又将当前回合的多个片段整理为一个运行中的 AI 消息，其中尝试失败被放回过程项。压缩 System 记录不作为该 AI 正文或过程项保留。

相同提示在不同阶段可能处于不同结构，影响它是否受“已处理”折叠、是否处于列表末尾，以及是否改变渲染身份。

### 4.5 虚拟列表与后台 Markdown 渲染的相关风险

虚拟列表当前保证列表最后一条记录保持挂载，没有单独指定“当前运行的 AI 回复”。末尾被提示占据后，原回复可能失去这项保证。

完整 Markdown 在后台解析和隐藏 DOM 准备结束前不显示正文。回合合并、折叠或渲染分支切换引起重新挂载时，父消息的按钮和 Token 行可能仍显示，正文暂时为空。这与截图的部分表现一致。

这些是经代码核对的触发路径。尚未捕获用户实际闪烁现场的完整更新序列，因此不能认定它们已经解释全部高频空白，也不能认定左右横线或边框的 CSS 本身是根因。

## 5 备选显示方案与实现边界

“固定状态栏加可展开提示记录”是此前提出的备选方案，用户尚未选定具体布局。当前确定的要求只有四类提示都应重新研究显示方式，并保留原有会话组件。

若评估这个方案，状态栏可放在输入框上沿、消息滚动列表之外，更新时保持固定尺寸；长错误显示可读摘要，完整原文通过详情查看。提示记录按时间保留，不使用会自动消失且无历史入口的短暂通知替代。

| 提示 | 可以评估的呈现方式 | 状态归属 |
| --- | --- | --- |
| 压缩 | 一次任务的状态由进行中更新为完成、失败或取消 | 压缩任务，异步压缩不结束主会话运行 |
| 单次请求失败 | 失败摘要与重试状态显示，历史保留每次失败 | 所属请求尝试及运行 |
| 最终失败 | 保持可见的最终错误摘要和详情入口 | 明确的运行终态 |
| 模型切换 | 简短模型信息及历史记录 | 对应消息或回合的模型变化 |

无论选择哪种布局，都需要满足：

1. 运行提示不能决定 AI 回复是不是最后一条有效回复，不能成为隐式回合结束标记。
2. 正常完成、最终失败和用户取消由实际运行状态、结算事件或正式运行结果确认。一次尝试失败不是运行终态。
3. 事件具有稳定身份和归属。请求失败已有 `run_id`、`user_message_id`、`event_id`；压缩应关联任务身份，并考虑跨用户回合完成的异步压缩。
4. 提示更新不重新挂载已经显示的正文，不清除手动折叠状态，不重置滚动位置。
5. 流式显示、历史加载和重连恢复使用一致的事件表示，避免同一失败提示来回进入或退出“已处理”容器。
6. 保留旧会话记录。显示层调整不能删除现有消息或审计记录，也不能把运行事件拼入正式模型上下文。
7. 工具自身的真实执行结果继续留在工具容器中；不能因为上游请求提示失败而无条件改写工具状态。

## 6 后续验收场景

- AI 正在调用工具时，异步压缩开始、完成、失败或取消：原回复继续计时，不提前归档，不出现结束后的用量展示，不改变用户展开状态。
- 第一次请求失败、第二次继续生成：失败记录保留，当前回复继续运行，已完成工具不重复执行或消失。
- 最后一次失败且运行已结算：最终错误可见，之前已经提交的回复和工具事实仍保留。
- 错误原因是长 JSON：更新摘要或展开详情不导致消息列表持续改变高度和跳动。
- 工具、Thinking 和“已处理”容器被用户手动展开或收起：提示更新、刷新和重连后维持原有交互语义。
- 长会话虚拟化、滚动浏览历史时收到提示：不替换正在运行的回复身份，不产生持续重新挂载。
- 多次压缩或压缩跨回合完成：按真实任务关联，不把不同任务的开始和结束错误合并。
- 模型切换：旧回复稳定显示，切换记录清楚，不改变工具和过程容器。
- 老会话、缺少新事件元数据的记录：内容保留，无法确定关联时不强行合并。

## 10 独立通知容器与直接修复的方案比较

补充日期：2026-10-09。用户补充同一会话截图：一条用户消息后的处理过程被“正在异步执行记忆压缩。”分隔，前后分别出现“已处理”和用量行；要求继续研究修复难度及独立通知容器，尚未授权实施这一改造。

### 10.1 新增对照复现

直接载入当前前端显示模块，构造同一用户回合的两段回复：A 已有说明、输出用量 10，B 正文为空、输出用量 20 且包含运行中的工具。会话运行状态始终保持 `running`，不连接上游、不改变真实会话。

| 处理方式 | 回复显示结果 | 工具状态 |
| --- | --- | --- |
| 不加入通知 | A、B 两段，用量分别为 10、20 | running |
| 加入压缩提示，消息投影完成后再隐藏提示 | 只剩合并后的 B，用量为 30 | running |
| 在进入消息合并之前抽出压缩提示 | A、B 两段，用量分别为 10、20 | running |
| 在末尾加入第 1/2 次失败提示 | 只剩合并后的 B，用量为 30 | error |
| 在进入消息合并之前抽出该失败提示 | A、B 两段，用量分别为 10、20 | running |

这项对照验证了分离通知数据的有效位置：必须位于消息分组、回合合并及终态收尾之前。仅在 JSX 或 CSS 中隐藏通知，或投影完成后将通知移到另一个位置，无法撤销已经发生的错误合并、用量汇总和工具状态修改。

该复现验证数据投影结果，没有运行真实浏览器的完整暂停/重连流程；不能将它描述为实际高频闪烁或桌面退出已经修复。

### 10.2 两种方案的范围与难度

| 方案 | 主要工作 | 优点 | 局限与风险 |
| --- | --- | --- | --- |
| 保留通知在消息列表内，修正状态和边界 | 活动回复按真实运行身份定位；通知不能关闭回合；单次失败不能设置工具终态；统一历史和重连表示 | 当前界面变化较小，后端可保持较小改动 | 通知仍占据主列表高度、参与虚拟测量及滚动；以后每新增通知类型，都要遵守这些例外规则 |
| 独立通知容器与独立通知数据视图，同时修正运行判定 | 显示前提取事件；独立状态区和历史详情；运行身份及终态明确；流式、历史、重连统一归属；压缩补充任务关联 | 通知更新不直接改变主消息列表结构，职责更清晰，适合持续扩展 | 初始改动涉及多个入口，不能只添加一个 UI 组件；遗留压缩记录缺少直接任务关联，旧数据需兼容 |

判断：属于中等规模改造，前端为主，后端补充事件关联信息。主要复杂度是保持各条更新路径的一致性及旧记录兼容；原有工具、Thinking、“已处理”、用户消息容器和手动折叠逻辑继续使用。无需为这项显示修复整体重写聊天区。

推荐第二种方案。独立容器是使通知脱离会话显示算法的实施手段，仍然需要明确活动回复身份、最终运行状态以及 Markdown/虚拟列表挂载稳定性，不能把“移走通知”视为涵盖全部闪烁触发因素。

### 10.3 建议界面，仍为待实施方案

- 在输入框上沿、主消息滚动区域之外保留一条高度稳定的状态栏。显示简短状态，例如“请求失败，正在第 2/2 次尝试”“正在压缩上下文”“运行已停止：余额不足”。
- 活动错误及停止原因应有持续可见的摘要；完成或已解决的状态留在通知历史，不依赖短暂弹出后消失的 toast。
- 状态栏提供“通知记录”入口及数量。展开到独立滚动的浮层或侧栏，显示时间、类型、状态、所属回合和完整详情；多行错误 JSON 在详情中查看，不撑高主消息列表。
- 同时进行多个任务时保留每项状态，主栏显示当前较重要的摘要及其余数量。异步压缩和主模型运行分别记录；压缩完成不表示模型回复结束。
- 同一次压缩可表现为一项从进行中更新为完成、失败或取消，详情中保留开始和结束事件。前提是有可靠的 `compression_id`。
- 模型切换属于信息型记录，可在历史中查看；当前所用模型仍由原有模型选择控件展示。

这是一组产品建议，没有视为用户已批准具体位置、高度或浮层交互。

### 10.4 哪些进入通知，哪些保留原容器

| 内容 | 建议归属 |
| --- | --- |
| 同步/异步压缩的开始、完成、失败、取消 | 独立通知 |
| 单次上游失败、自动重试进度 | 独立通知；保留尝试编号及原始详情 |
| 最终运行失败、会话启动错误 | 独立通知；终态同时更新真实运行状态 |
| 模型切换信息 | 独立通知历史 |
| 用户发送的内容、引用、发送时间和编辑 | 原用户消息容器 |
| AI 正文、思考、工具及工具自身失败结果 | 原会话容器和时间线 |
| “已处理”、手动展开/收起、Token 统计 | 原组件，依据所属运行和真实结束状态展示 |
| 普通 System 正文、模型上下文中的记忆通知 | 按其原语义保留，不按 `role=system` 一刀切搬走 |
| 输出上限保留的 AI 片段、自动续接的正式 user 消息 | 保留为正式对话内容；截断及恢复的状态可另外产生通知 |
| 桌面 GUI 锁定栏、全局权限或文件打开提示 | 保留其原有全局职责，不合并为会话通知 |

不能将所有 `role=error` 行整体删除或搬走。旧显示对象可能包含已提交的 AI 正文、思考或工具事实，应提取错误状态并保留内容；实际工具的失败结果仍展示在工具容器中。

### 10.5 数据与持久化设计

建议先建立统一通知结构及只读适配层，得到两个独立视图：`conversationMessages` 与 `conversationNotifications`。原始记录保留，用现有消息、运行结算、请求失败事件及压缩任务生成通知，不因显示拆分而删库或重写旧历史。第一阶段无需为了 UI 拆分新建数据库。

通知需要稳定的事件 ID、项目/会话 ID、类型、严重程度、状态、发生时间，以及适用时的 `run_id`、`user_message_id`、`compression_id`、尝试编号和详情。展示文案不作为分类、任务匹配或结束判定依据。

需要处理的当前缺口：

1. 压缩开始与结果是两条独立 system 消息，生成辅助函数没有传递 `compression_id`。后端已有压缩任务记录，可补充明确关联；旧记录不可靠匹配时保留为独立历史事件，不能强行两两合并。
2. 历史失败记录已有真实 `event_id/run_id/user_message_id`；流式累计器目前构造临时负事件号，使用 AI 展示 ID 代替 `run_id`，用户消息 ID 为空。统一通知时要使用真实启动身份和事件序号，并明确刷新、重连后的去重规则。
3. 当前错误提示分别进入独立 error 行、过程 `attempt_failure` 项和回复上的 `retryStatus`。需要在入口统一通知来源，避免同一次失败重复出现或刷新后改变归属。
4. 模型切换目前从消息模型标识派生，移出列表后仍需稳定的来源消息 ID，并避免提示自身携带模型信息造成错误切换判定。

当前后端模型请求组装会排除界面用的 system/error 记录。通知视图继续保持该边界；不要把新的通知历史拼成额外模型消息。已经由输出上限策略正式创建的续接 user 消息属于另一种业务语义，应按现有策略保留。

### 10.6 需要同时修正的显示和运行规则

- 活动回复根据所属运行、用户回合及实际活动片段识别，不能继续要求它恰好位于整个混合列表最后一行。
- 回合关闭依赖真实运行完成、失败、取消或后续正式用户回合；压缩、模型切换和单次请求失败不能关闭它。
- 单次失败修改重试/通知状态；最终结算才负责收尾尚未完成的思考和工具。已提交的工具结果不被显示投影改写为失败。
- 主列表和原容器使用稳定身份，通知更新不改变已有正文的 React key，不重置手动折叠、不启动全会话加载，不主动滚动到通知。
- 虚拟列表保留真实活动回复，并检查高度测量、滚动跟随与隐藏 Markdown 准备是否导致反复挂载和取消。worker 重启异常需要专门记录，不能由新的通知 UI 掩盖。
- 真正结束时统一显示本回合用量；过程中使用原有运行中的统计入口，不能因为通知插入而多出一条像最终回答的汇总。

### 10.7 实施入口与验证顺序

前端主要入口是 `chatMessage.ts` 的历史映射、`chatStreamAccumulator.ts` 的实时处理、`conversationStreamResume.ts` 的恢复、`chatDisplayMessages.ts` 的投影，以及 `ChatMessageList/ChatPanelBodyFrame` 的活动行和独立容器接入。原有容器继续使用，通知相关的 `attempt_failure` 显示出口改走统一通知视图。后端主要补充压缩任务关联及必要的运行事件元数据。

建议先统一数据及运行语义，再接入通知外观，最后核对全部路径：

1. 运行中插入/完成压缩，主过程、工具状态、用量和折叠不发生错误改变；新通知不引发历史正文重载。
2. 第一次失败、第二次成功：保留失败详情，继续运行；最终失败：停止状态和错误持续可见。
3. 暂停后发送、切换会话、历史刷新及断线重连，通知不重复、不丢失、不重新进入“已处理”。
4. 异步压缩跨用户回合完成，归属原任务，并保持当前回复的运行身份。
5. 长错误详情、多通知、长会话虚拟列表及公式内容，通知更新不触发持续 worker 重建或滚动跳动。
6. 历史数据及最新输出上限三种动作继续工作，原工具/Thinking/“已处理”的手动折叠保留。

本阶段完成代码核对及内存中的对照复现，仅更新本研究文档；没有修改程序或构建产物。

## 11 按用户最新方向评估：对话内通知卡片与原有折叠

用户进一步提出：参考用户消息的显示模式，将提示作为完整卡片插在消息之间；属于“已处理”范围的提示一同折叠，范围外的提示保留为外部消息。该方向优先于第 10 节尚未实施的独立状态栏建议，本节继续研究，没有修改程序。

### 11.1 可行性与复杂度

可行。复用用户消息的背景、边框、宽度、内边距和换行排版比较方便；复用完整用户消息的业务身份则不合适。当前显示投影、回合结束判定及折叠作用域以真实 `role=user` 为回合边界，把通知改成 user 会制造新的用户回合，并可能带入编辑分支等交互。

建议抽出可共用的消息卡片外观，由通知渲染自己的类型、状态、文字、时间和详情。通知维持系统事件语义，保留现有后端记录及模型上下文边界。该 UI 复用不等于让系统模拟用户发送新消息。

整体仍是中等规模的显示规则修复，界面布局变化少于新增常驻通知区域。主要工作集中在通知归属、活动回复识别和三条数据路径一致性，原有工具、Thinking、“已处理”容器及手动折叠继续使用。

### 11.2 现有可复用基础

`ChatAssistantProcessItem` 已经有 `attempt_failure` 项，`AssistantProcessTimeline` 可以将该项交给 `RunFailureNotice` 渲染；`ProcessedProcessBlock` 会对归档范围内的所有项逐项渲染并一起折叠。这证明“通知是处理过程中的一项，并随原容器折叠”有现成入口。

可以将这一专用失败项扩展为统一的通知项，与思考、工具和中间说明平级。位于流程中的压缩及重试等通知走该入口；流程之外的通知使用相同的卡片组件单独显示。归属属于展示层，无需把工具或 Thinking 改成新的通知容器。

### 11.3 消息分段和运行结束分别判定

一条模型消息完整结束后，AI 仍可能继续调用工具或发起下一次模型请求。因此“完整消息之间插入一条卡片”只决定显示顺序，不能直接决定整个用户回合结束。

当前故障的核心仍需修改：通知插入会触发 `flushAssistantTurn(false)`，最后一行决定流式身份，单次请求失败可能参与工具终态收尾。新的卡片继续放在主列表中也可以，但这些判定必须明确绕开通知，按真实运行和回复身份处理。

视觉上可分为“上一段处理 → 通知卡片 → 下一段处理”；同一运行仍属于同一个用户回合。真正结束时，这些过程项及其内部通知一起进入一个“已处理”范围，最后回复按原有规则显示。

### 11.4 归属与边界建议

- 本轮处理过程中发生的通知，关联本轮运行和稳定的消息边界，成为原处理时间线中的通知项；在运行期间显示，在该过程归档后一起折叠。
- 位于处理范围之外的通知，保留独立消息卡片，继续按原先的消息顺序展示。
- 最终运行失败可以放在本轮处理结束后的独立卡片中，保持停止原因可见；这与本轮内部的单次请求失败区分。
- 后续通知到来、任务状态更新及历史刷新不改变已显示正文的消息 ID，也不重置展开状态。新通知造成的一次正常排版变化，不应发展成旧正文持续卸载、取消解析和重建。
- 用明确的消息边界、运行身份和任务关联确定位置；不能仅依赖最近的文字、列表末尾或当前数组索引判断折叠归属。

### 11.5 “通常在完整消息之间出现”的边界条件

上游失败和重试通常发生在一次请求结束或失败时，模型切换通常处于新请求边界；这些提示容易放在完整片段之间。异步压缩的完成、失败和取消由后台任务独立产生，可能在主模型仍输出正文时到达，也可能跨过一个用户回合。

若严格要求只在完整消息之间显示，通知可以先记录，等当前模型回复片段完成后在稳定边界插入。只延后其界面展示，不取消或重新请求模型、不拆开正在生成的 Markdown。终态失败和用户暂停本身已结束相应活动片段，应及时呈现相应结果。

排队的通知仍需在取消、最终失败、刷新和重连时恢复，不应仅存在于临时内存队列。后台压缩任务继续按原机制执行。跨回合完成的压缩通知保留可靠任务关联；没有关联的旧记录保留为独立卡片，不强行塞入当前运行。

### 11.6 实施边界及验证

建议保留原始历史数据，在显示适配层识别“内部通知项”和“独立通知卡片”。实时、历史、重连恢复采用相同归属算法；请求失败沿用已有持久化事件身份，压缩补充 `compression_id` 及所需边界关联。

重点验证：在两个完整模型片段之间插入通知不关闭运行；内部通知随“已处理”展开和收起；外部通知继续可见；工具、思考及用量真实状态保留；运行中异步通知排队后不会遗漏或重复；暂停、新发送及重连不重置旧正文和手动折叠。

当前结论：可以采用该方案。复用外观及原折叠容器能减少界面改造，仍需一次统一的通知归属和运行状态修正；不能仅改成用户消息样式就视为闪烁已修复。

## 12 最新约束：保留现有提示样式，修正显示语义

用户明确选择保留现有提示的左右横线、居中提示框、图标及状态外观，不复用用户消息卡片样式。因此第 11 节的用户卡片外观建议不再适用；第 10 节的独立状态栏也仍是未采用的备选方案。

当前研究方向：

- 保留 `ConversationEventNotice` 的现有外观及原工具、Thinking、“已处理”容器和手动折叠交互。
- 提示按可靠的运行、任务及消息边界归属：处理范围内作为过程项一起折叠，范围外继续独立显示。
- 插入提示只影响其所在的显示位置，不能隐式结束 AI 回合、提前汇总用量或误修改工具状态。
- 活动回复按真实身份识别，避免因提示成为列表末尾而失去流式显示状态。
- 实时、历史及重连采用一致表示，并验证提示更新不会引发正文持续卸载、Markdown 解析取消及重建。

修复重点是数据投影和运行语义。保留外观并不意味着维持现有的错误分组、收尾和重新挂载行为。本次仅更新方案约束，没有修改程序或构建产物。

## 13 系统提示统一等待单次流式响应结束

用户明确指定：所有系统提示在完整消息之前或之后插入。异步压缩结果若在主模型流式输出期间到达，应等当前这一次流式响应结束后插入；该边界不是整个工具循环或整个用户回合结束。

### 13.1 展示规则

1. 当前模型响应进行中：收到压缩状态、失败/重试、模型切换等通知时，及时记录其事实及原始时间，暂不插入正在输出的会话显示结构。
2. 当前响应结束：先提交该响应剩余的正文、思考和工具参数缓冲，形成稳定的消息边界，再将待显示通知按确定顺序插入。工具执行或下一次模型请求可以继续；通知不改变本轮运行状态及折叠终态。
3. 当前没有模型响应正在输出：可以在现有完整边界及时插入提示，包括工具执行等待期间，无需等待工具完成。
4. 当前响应失败、达到输出上限或被取消：同样释放该响应的展示边界，按原业务机制处理失败、重试或取消，并呈现相应通知。不能因缺少正常完成标记无限等待下一次成功。
5. 系统提示保持现有外观。进入已归属的处理范围后随原“已处理”折叠，范围外独立显示；不在当前 Markdown 正文中间插入或拆开消息。

等待只影响提示的显示时间，不延迟压缩结果生效、错误处理或其他后台任务，不向模型追加新的用户消息。提示原始发生时间与实际显示时间可以不同；历史和重连要使用相同边界归属，避免刷新后把延后提示重新插回输出中间。

### 13.2 当前代码的边界缺口

`ChatCompletionService.stream` 处理一次模型响应结束；但 `conversation_tool_loop.py` 遇到该响应含有工具调用时，会消费该次 `DONE`，继续保存回复并执行工具，再进入下一次模型请求。现有的 `conversation_run_settled` 标记的是整个运行结算。

因此前端不能直接等待整个会话完成，也不能只依赖目前透传的 `done` 覆盖所有工具响应。实施时需要明确单次模型响应的开始和结束边界，并覆盖含工具调用的响应、上游内部重试、输出上限恢复和取消路径。正文暂时没有新 token、Thinking 转正文、收到用量信息或工具参数开始出现，都不能单独作为可靠结束判据。

通知若已经落库，历史刷新、会话切换或重连期间也要遵守该显示门槛，不能绕过实时通知队列直接进入列表。边界记录与通知的归属需要可恢复和去重，而不是只依赖临时定时器。

### 13.3 验证场景

- 异步压缩完成发生在正文输出过程中：本次输出保持连续，结束后才显示完成提示。
- 一次响应输出工具调用后结束，工具仍执行数十秒：通知在本次响应结束后显示，不等工具结束或整轮结束。
- 当前只执行工具，没有模型正在流式输出：通知及时出现，不额外排队到下一次模型请求。
- 单次请求失败并重试、输出上限恢复或用户暂停：提示不会一直滞留，也不导致前面正文丢失、工具被错误收尾或整个用户回合被提前关闭。
- 等待期间刷新或重连：同一提示在同一完整消息边界显示一次，原有手动折叠保留。

本次只补充研究约束并核对结束事件，没有修改程序或构建产物。

## 14 实施记录：通知边界、折叠归属与渲染稳定性

实施日期：2026-10-09。按用户后续授权完成，保留现有提示外观、原有工具/Thinking/“已处理”容器及其手动、自动折叠。没有新增独立通知栏，没有更换用户消息样式，没有重写已有会话数据库。

### 14.1 本次修正的原因

确认存在的是一组相互放大的显示问题：

1. 压缩、错误等提示被当作助手回合的分隔或终态，导致过程提前归档、用量提前出现；一次请求失败甚至影响尚在执行的工具状态。
2. 提示成为列表最后一行后，真正活动的助手消息失去流式身份及虚拟列表的挂载保护。
3. 新一段模型回复与上一段合并后，显示消息的编号变化，引发整行重新挂载。Markdown 在卸载时取消解析，再挂载时重新创建 worker。
4. 内容异步准备过程中，临时空白高度参与虚拟列表测量，进一步推动消息卸载、解析取消、重新测量。
5. 暂停后的历史刷新、上一轮延迟刷新可能与新发送交错，覆盖或重新构造正在输出的本地快照。

修改覆盖上述可复现路径。2026-10-09 曾发生的原生桌面退出没有完整 WebView 崩溃记录，不能仅凭这些修复判定其唯一根因或保证退出问题已经彻底消除。

### 14.2 四类提示的实际处理

| 类型 | 现在的行为 |
| --- | --- |
| 记忆压缩的开始、完成、失败、取消 | 继续使用 `system/memory_compaction` 和原提示框；通过单次模型响应边界队列写入、推送；不进入模型上下文。 |
| 单次请求失败、最终失败及其他错误 | 继续使用原错误提示框；单次失败不会结束整个运行、修改活动工具状态。处理范围内部作为通知过程项，最终范围外的错误独立显示。 |
| 活动重试提示 | 继续作为助手上的重试状态，在失败响应结束后出现；新响应有进展时按原规则消除活动提示。失败事实仍保留。 |
| 模型切换提示 | 继续按真实消息模型变化生成并显示在消息边界；压缩或错误记录即使携带模型信息，也不触发虚假的对话模型切换。 |

普通 System 消息没有转换为这组通知。现有模型切换提示、活动重试提示仍保留原有数据表示；没有强行生成新的用户消息或通知数据库表。

### 14.3 单次流式响应边界

后端内部增加可选的 `model_response_started`、`model_response_finished` 事件，仅项目会话流启用。通用模型调用默认不增加这组事件。

- 每次实际向模型发起请求，包括内部重试，都有独立开始/结束边界。
- 输出正文、思考或工具参数期间产生压缩状态，先进入当前会话的待处理队列，不立即插入显示历史。
- 含工具调用的响应结束后，先保存完整助手工具调用消息，再释放通知，最后执行工具；不会等待整个工具循环。
- 最终正文响应结束后，先保存助手回复，再释放通知，随后执行原有运行结算及后续工作。
- 达到输出上限时，如果角色选择保存截断内容，顺序为截断助手消息、待处理通知、自动续接用户消息。保留内容不会被通知挤到错误位置。
- 当前没有模型响应、只有工具执行或等待时，通知及时落库，通过 `conversation_notice` 流事件推送，无需等待工具结果或反复拉取整段历史。
- 取消及关闭生成器先清理仍在运行的流/工具等待，再结算暂停状态、保存可保留片段，最后排空通知队列。工具等待与工具执行的取消范围沿用原定义。

压缩结果和压缩任务状态仍独立保存、生效；延迟的是会话状态提示。队列按项目和会话隔离，写入及响应切换由同一锁串行处理；单条通知写入异常不会让主会话失败。待处理队列仅服务活动运行，结束后释放。

压缩开始提示不再回插到旧的压缩快照消息之后，改为追加到实际可展示的完整响应边界。原压缩任务仍记录原快照边界，没有改变压缩所使用的历史范围。

### 14.4 归属与运行状态

显示投影把通知作为透明的处理过程项，而非结束助手回合的依据。两段助手消息之间的通知加入原处理时间线，随原“已处理”折叠；第一段处理之前和最后正文之后的独立通知继续保留。

工具结果查找所属调用时可以跨过通知；旧历史中工具结果先于助手行、两者之间有通知的情况也保留工具及通知的原顺序。用户消息、普通 System 消息、保存的输出上限片段仍属于真实边界。

是否结束处理、是否收尾工具、是否显示用量，取决于真实助手/运行终态，不取决于列表最后一行或单次失败提示。活动助手和时钟通过当前用户回合里的真实助手身份识别；末尾有通知时仍保持其流式展示与工具计时。

### 14.5 保持挂载、历史、重连一致

助手消息合并后保留最终正式 `id`，用于导出、导航和后端请求；另用首段稳定的 `displayKey` 作为 React 行及高度缓存的显示身份。新模型段落及通知出现不会仅因正式编号变化就重挂整行。

虚拟列表同时保护活动助手和最后一行。隐藏 DOM 尚在准备时，`aria-busy` 阻止临时空白高度覆盖已知高度；尺寸观察按帧合并。Markdown 在同一次界面更新中卸载后重新挂载相同内容时，复用在途解析；真正离开且没有订阅者的旧工作仍会取消，迟到结果仍不能覆盖当前内容。

历史刷新复用未变化的历史对象；活动输出期间仅合并新通知，保留流快照。当前请求的失败事实由活动流负责显示，避免再混入另一编号的持久化失败记录而重复显示。

重连恢复点跳过通知，使用真实助手、工具或自动续接用户消息。处理范围内的通知保留在过程项中，前后的独立通知也不丢失。明确的重连/完整重放重置使用正式历史快照；正常刷新不覆盖在途输出。

### 14.6 暂停与新发送

点击停止后立即登记该会话的停止状态。在后端停止、消息结算和历史刷新完成前，发送路径和输入区忙状态共同阻止同一会话开始新请求。上一轮安排的延迟刷新遇到新一轮正在发送时，只补充通知，避免用旧历史覆盖新输出。

通知推送与模型事件合并时，关闭生成器会显式关闭内层工具流、取消并等待其子任务。该清理顺序由既有的客户端工具等待取消测试验证，保持 `cancel_scope=wait`，不会错误解释为取消了被等待的任务。

这些改动减少暂停→新发送时的显示及请求竞态。用户消息仍按既有请求接收及持久化路径保存；没有把输入框草稿当作已保存消息，也没有声称能够恢复原退出事件中从未落库的那条新消息。

### 14.7 与输出上限、上下文及旧数据的兼容

- 保留角色的输出上限停止、重试、发送新内容及截断片段保存策略，不改变其重试预算。
- 通知处理不生成模拟用户消息；只有用户已配置的输出上限自动续接路径仍创建原有可见用户消息。
- 提示和失败审计保持原有非上下文用途；半截工具参数仍不执行，已成功的工具消息及用量记录保持原机制。
- 新的状态提示明确 `include_in_context=False`；压缩结果的上下文更新不依赖提示展示。
- 原会话记录无需迁移或清理，历史数据在显示层按相同规则投影。已有截断片段仍不被合并为最终回复。
