## 4 本地源码中已核对的处理链路

本节先记录当前本地工作区源码的处理链路。续查另外读取了联想包内的相关源码：适配器和共享 HTTP 客户端与本地文件 SHA-256 一致；请求服务、工具循环、流式结算文件哈希不一致，但联想文件中下面涉及 `length`、相同请求重试和清空当前轮次的关键分支已直接核对。前端安装包仅包含 dist，不能把本地前端测试当作联想构建的逐文件验证。

### 4.1 `length` 提示的生成位置

`1_PythonServer/app/infra/llm/chat_adapters/openai_compatible.py` 在收到上游流后读取 `finish_reason`。如果最终为 `length` 或 `content_filter`，适配器产生：

- 事件：`ERROR`。
- 错误码：`upstream_response_incomplete`。
- 文案：“上游生成未完整结束：{finish_reason}。”

非流式解析也将这两种结束原因视为未完整响应。

用户看到的这条具体文案对应上游结束原因分支。续查已读取实际响应尾部事件，两次均明确返回 `finish_reason=length`，输出和思考用量均为 32768，见第 10 节。

### 4.2 为什么会重新尝试并最后停止

`1_PythonServer/app/services/llm/chat/service.py` 的流式请求层按 `upstream_retry_count + 1` 计算最多尝试次数。

适配器返回错误事件后：

1. 记录本次请求尝试失败。
2. 如果还允许重试，发送 `RETRY_RESET`，重新发送当前模型轮次的完整逻辑请求。
3. 最后一次仍失败，则向会话层返回最终错误，由会话层结算运行。

这里的重试是重做当前模型请求，当前实现不会因为 `length` 自动把已收到的片段当作已提交回答，再接着续写。若相同请求反复触发相同结束条件，仅增加尝试次数不一定改善结果。

默认设置中的 `upstream_retry_count` 为 1，即最多两次；续查读取到联想该会话当前保存的设置也是 1，历史事件的 `attempt_count` 为 2，与截图一致。历史请求参数以实际审计为准。

### 4.3 为什么已经显示的内容可能消失

重试合同明确区分：

- 当前模型轮次尚未成功提交的流式正文、思考和未完整工具调用。
- 更早已经成功提交的工具调用、工具结果及关联回复。

`conversation_tool_loop.py` 收到 `RETRY_RESET` 会清空当前模型轮次的临时正文、思考和工具指令累计。前端 `chatStreamAccumulator.ts` 收到重试或最终错误时，会回退到最近的已提交快照。

前端在收到 `tool_result` 后保存已提交过程快照。若最后错误时没有任何已提交内容，则当前临时 AI 消息可能被失败提示替换；有已提交过程则保留该过程，再追加失败提示。

因此，“此前在屏幕上出现过”不自动等于“已经作为正式消息提交”。目前必须区分两种情况：

| 情况 | 当前合同及需要确认的事项 |
| --- | --- |
| 消失的是当前未完整结束的生成片段 | 可能符合现有重试回退行为；需评估展示上是否应另行保留失败片段，但不能作为正式模型上下文提交 |
| 消失的是更早已经成功提交的工具轮次或正式消息 | 不符合保留已提交事实的要求，需要查持久化记录与前端显示是否一致 |

续查确认截图中的已完成 `inspect_workspace`、工具结果及此前 28 字回复仍在正式消息表中。两次 `length` 响应的正文均为零，思考约 8.3 万字符；这一轮未作为成功消息提交。证据支持该次消失的是失败轮次的临时思考过程，不能据此断言其他更长运行中不存在正式内容显示或恢复问题。

详细合同见 [上游响应异常重试与会话运行结算机制](23_上游响应异常重试与会话运行结算机制.md)。

### 4.4 实际请求的输出上限已经确认

当前本地前端默认会话设置和后端会话设置均为 `max_output_tokens=32768`。OpenAI 兼容请求构造会在该值非空时将它映射为 HTTP 请求中的 `max_tokens`。

续查的两次原始请求确实传入 `max_tokens=32768`，响应也均报告 `completion_tokens=32768`、`reasoning_tokens=32768`。因此这次已确认是单次输出额度被思考耗尽；不能把它解释成会话历史超过上下文上限或电脑性能不足。

### 4.5 连接失败的调查边界

`All connection attempts failed` 属于连接请求失败信息。当前共享 HTTP 客户端支持直连、系统网络设置和自定义代理，分别使用配置的连接及读取超时。

在取得对应请求地址、错误类型、网络模式、代理和设备连通性之前，不应判断是供应商服务器、代理、DNS、设备网络还是本机请求配置造成。不得把它与 `length` 合并为同一个已确认原因。

### 10.5 审计关联中的两个注意点

失败尝试事件 9 的 artifact_id 指向 `artifact_9d39b602abdb415a93be20c4bf13d8fc`，但该审计实际是已成功返回 `tool_calls` 的首个请求，耗时 1.836 秒、输出 105 token。真正第一轮 length 的审计是稍后 HTTP 交换事件 10、11 中的 `artifact_1a9c5764b9da49aeb8980e97fb5bb2ee`。

第二次失败尝试事件 12 的 artifact_id 为空，但 HTTP 交换事件 13、14 保存了第二次 length 的审计。其他 length 事件也可能出现空关联。调查时必须按会话、运行、请求开始完成时间、尝试和 HTTP 事件一起核对；不能把空 artifact_id 当成没有响应，或把过早关联的上一轮工具请求当成失败响应。

此外，这些审计的 error 字段中出现 `GeneratorExit`，包括已成功返回 `tool_calls` 的请求。这属于生成器退出时的审计记录表现，不应直接当作连接失败原因或否定 HTTP 成功。实际结果应结合 HTTP 状态、SSE 结束原因、请求尝试完成/失败事件判断。本次没有修改审计关联或退出分类代码。

### 10.6 后续处理方向，仅研究记录

- 将 length、网络错误、鉴权/余额/HTTP 错误分别处理，避免所有错误都盲目重做同一请求。
- 若保留失败轮次已经显示的思考或正文，需要将其作为可查阅的失败片段保存，与正式可回放模型上下文区分；不执行截断工具调用。
- 对 length 给出明确的单次输出上限及已用思考/正文额度信息，便于判断是否需要调整思考强度或额度；当前未改变实际设置。
- 第一组截图已有成功的工具过程必须继续保留；不得将本次调查扩展成改动原有工具、思维过程或“已处理”折叠容器。
- 对历史连接失败继续保留未定结论，不把当前成功的连通性检查当成修复证明。

以上是根据现有证据记录的处理方向，尚未实现、未部署，也没有用付费生成验证。

### 11.2 官方文档提供的约束

### 11.3 项目实际做法

Hermes 对正文截断追加已生成文本和续写提示，限制恢复次数，最终仍可保存 partial。工具参数截断则重新生成并扩大额度，不执行坏参数；纯思考、无正文的部分兼容路径使用一次性关闭思考的恢复，而另一些思考块或重复循环会直接停止。它不是统一的无限续写。见 [Hermes truncation recovery](https://github.com/NousResearch/hermes-agent/blob/1e0c7730d791f5ce855c5c78935cfea6fb1e43a9/agent/turn_truncation.py)。其当前自定义 OpenAI 兼容端点不自动下发目录里的输出上限，依赖服务器默认值，见 [Hermes provider documentation](https://github.com/NousResearch/hermes-agent/blob/1e0c7730d791f5ce855c5c78935cfea6fb1e43a9/website/docs/integrations/providers.md)。

DeepSeek Harness 将错误尝试的完整流保存为 `assistant/attempt`。max-tokens 有独立结束原因，保留文本和思考，剔除工具调用，再结束当前回合；所查核心循环没有在该分支盲目重发同一请求。见 [Harness agent loop](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/core/agent-loop/src/agent.ts)、[block assembler](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/llm/llm/src/assembler.ts)。

Codex 完成输出项后立即记录，降低后来取消造成已完成内容丢失的风险。但所查 main 仍把非 interrupted 的 incomplete（包括 max_output_tokens）转成 Stream 错误，流错误允许重试；不能将其表述成已解决本问题的标准答案。见 [completed item persistence](https://github.com/openai/codex/blob/b6e8a2e207e5591780061c62c50df417670f8d75/codex-rs/core/src/stream_events_utils.rs)、[SSE parsing](https://github.com/openai/codex/blob/b6e8a2e207e5591780061c62c50df417670f8d75/codex-rs/codex-api/src/sse/responses.rs)，对应 [issue 38831](https://github.com/openai/codex/issues/38831) 查阅时仍为 Open。

OpenCode 的 session processor 增量保存正文/思考，清理时结束现有片段并将未完成工具标记为中断错误；core runner 也以事件更新内容。已查路径没有证明存在专门覆盖所有 length 情况的自动续写，所借鉴的是内容持久化和工具状态分离。见 [session processor](https://github.com/anomalyco/opencode/blob/388406238bd5ca15564a762840a2362c3a45bd9c/packages/opencode/src/session/processor.ts)、[runner event publication](https://github.com/anomalyco/opencode/blob/388406238bd5ca15564a762840a2362c3a45bd9c/packages/core/src/session/runner/publish-llm-event.ts)。

### 11.4 天策建议：预算、留存、恢复分别负责

建议先将“看到的内容必须留存”和“哪些内容允许进入模型上下文或执行工具”分开。正式提交要求继续严格执行，但失败片段不能只藏在原始审计中或从用户界面消失。

**用户明确约束（2026-10-09）：保持现有重试的输入边界，不得在后台或会话历史中插入模拟用户发送的“继续”等指令。** 当前重试循环复用失败模型轮次的完整消息列表，只更新尝试次数；当前运行尚未完成工具调用时，重发以真实用户输入为基础的请求；工具结果已提交后，重发包含已有 assistant 工具调用和 tool 结果的请求，不重复执行已完成的工具。这里“重发”不是只发送最后一条消息。若以后考虑协议原生续接，必须有明确能力依据，不能通过伪造用户指令实现。以下恢复建议均受此约束，尚未实施。

当前还有一个与重试无关的协议适配细节：工具返回图片时，`tool_resource_message` 会生成 `role=user`、文字为“工具返回了以下图片资源。”的图片载体，并标记 `derived_tool_resource_message`；它不落为用户发送历史，也不提供“继续”指令。后续若要要求上游请求中所有 user 角色都只能来自真实用户，需要另行研究各协议对工具图片的承载方式，不能把当前实现描述为完全没有派生 user 角色消息。

**A. 输出额度采用 Auto 或显式上限。** 新配置区分自动策略与用户手动数字，记录参数来源及生效值。支持省略额度的协议可使用供应商默认值；必须传额度的协议根据模型能力补足。不能对所有兼容网关都假定省略就有足够额度，也不应统一设成模型最大值。用户明确选择 32K 时保留选择并解释不足；旧会话的 32768 无法仅凭数值区分默认还是手动，不能无声覆写。max 思考配置应保留，不把自动降低或关闭思考当作必然恢复策略。

**B. 增加持久化的尝试快照。** 建议每次模型尝试有稳定 ID，关联 run、round、attempt、正文、可见思考、工具参数片段、用量、结束原因、恢复动作和审计引用。失败快照用于查阅，默认不进入模型上下文。正文和思考可复用现有容器渲染；完整失败尝试可收在详情中，正在恢复时显示同一条简短状态，不产生一串伪用户/系统消息。

使用批量快照或追加流片段，避免每个 SSE token 写数据库；在发送重试清空事件或最终结算前完成终态快照持久化。重连、切换会话、重启都从同一份持久状态恢复，不依赖浏览器临时 buffer。原始 HTTP 审计继续保留，不必把每份约 10MB 的 SSE 在多个表里原样复制。

**C. 将 length 归类为 incomplete。** 适配器返回结构化结束原因、部分输出及用量，交由恢复策略判断；不要一进入适配器就把它压成普通 ERROR。网络、限流、服务器错误仍走通用重试；输出上限、上下文不足、内容过滤、用户取消有各自结果。运行“结束”与“成功完成”应分开，保留 incomplete 标记，避免用正常完成状态掩盖截断。

| 截断情况 | 建议动作 | 不应做的事 |
| --- | --- | --- |
| 只有思考，正文为零 | 保存思考快照；协议明确支持且续接状态有效时才续接，否则按 Auto 策略扩大额度重新请求；次数或预算用完则保留为未完成 | 相同 max 思考、相同额度、相同输入不停重做；伪装存在通用思考断点续接 |
| 正文已经输出且没有未完整工具调用 | 保存失败片段供查阅；只有协议原生支持、续接状态有效时才评估有限续接，否则按原始轮次输入重新请求；处理重复前缀，最终未完成也保留已有片段 | 清空可查阅片段；后台或界面追加模拟用户发送的“继续”等指令 |
| 工具参数 JSON 截断 | 保存只读片段；从本轮已提交事实重新生成完整调用，扩大额度或要求分批、小块输出；重新通过完整性和 schema 校验后才执行 | 给 JSON 补个括号就执行；将字符串后半截直接拼成可执行代码 |
| 上下文空间不足 | 走上下文整理/压缩策略，再重新判断是否能请求 | 单纯抬高输出额度，或继续追加片段扩大已满的上下文 |

所谓续写不等于恢复供应商内部推理状态。DeepSeek 普通 Chat 请求不能因带了任意 `reasoning_content` 就被认作支持断点续接；其文档中的前缀补全 CoT 输入是 Beta 能力、要求指定前缀与相应接口。初期可不引入 Beta，先实现正确额度、片段留存和受控重新请求。

**D. 给恢复设置独立、明确的上限。** 网络重试次数、截断恢复次数与整个任务的 token/费用/时间预算分别记录，不能塞进隐藏循环。建议第一阶段截断恢复默认最多一次，并明确展示恢复动作；只要上下文不够、没有可用的更高额度、重复输出或用户取消，立即停止自动恢复。该默认值是设计建议，需落到显式设置，尚未生效。

**E. 保持工具执行边界。** 已执行、已提交的工具结果是恢复锚点，不能回放重做。Chat Completions 第一阶段继续使用整轮提交，不因某个参数字符串看起来是完整 JSON 就提前执行；以后仅对协议明确提供的完成项及可去重调用考虑更细粒度检查点。调用完成标记、参数有效、批准状态、执行结果都必须明确。对可能已经执行但结果丢失的外部动作，先核对执行事实，不能凭请求重试直接重复操作。

**F. 失败用量也应可追踪。** 每次尝试用量单独保存，成功步骤用量和本次实际消耗分别汇总。仅第一组截图的两个 length 请求就消耗了 65536 个输出 token；重试不能让这些消耗从运行统计中消失。没有供应商用量时保留未知或估算来源，不能记成确定的零。

### 11.5 实施顺序与验收建议

建议顺序：先保存失败片段并改正 length 分类，再加入按模型能力的 Auto 输出额度，随后实现受控续写和工具截断恢复，最后评估协议级逐项检查点。只调整 32768 的数字可以降低复现率，但没有解决下一次到上限时的内容消失。

实施时需要更新第 23 号重试合同，把通用异常重试与截断恢复分开；不能只在前端改提示。涉及请求适配器、重试策略、工具循环、运行结算、存储和前端内容来源，原有工具/思考/已处理折叠容器保持职责与布局。

至少验证以下场景：

1. max 思考、正文为零时，保存完整失败快照，下一请求额度或策略确实发生改变；恢复耗尽后可查看已收到思考。
2. 正文输出后 length，恢复不删除前缀、不重复已生成文本，刷新/重启后仍可查看未完成正文。
3. 文件写入参数中途截断，零次执行坏参数；恢复成有效调用后只执行一次。
4. 已完成多个工具轮次后，新轮失败，早先过程、执行事实和结果全部保留。
5. 不同协议与自定义网关下，Auto 额度遵守实际能力；用户手动上限不会被静默改写。
6. 上下文不足、余额不足、限流、网络失败、取消按不同策略结束或恢复，取消不触发下一请求。
7. UI 展示失败尝试不改变当前回合完成判断、不提前折叠处理过程、不让整片历史重新加载。
8. 所有尝试有正确审计关联、结束原因和消耗统计，包括第一次失败后自动恢复成功的情况。

本节是结合原始失败证据与公开代码提出的天策方案，尚未实现或通过模型实测。

## 12. 输出上限专用恢复：保存片段并通知模型（2026-10-09 讨论）

### 12.1 用户提出的方案与授权边界

用户提出：达到最大输出长度后不再简单清空重发，而是保存截断前内容，并把“达到最大长度”的系统消息作为新消息提供给 AI，评估能否据此继续任务。本节记录可行性研究，不表示已经批准实施全部细节，也没有修改程序。此前“不得偷偷模拟用户发送继续”的要求仍然成立；由运行器生成、明确标记来源的系统运行通知可以单独设计。

建议将此行为命名为达到输出上限后的恢复，仍保留原有网络异常重试：普通重试复用失败模型轮次的输入，特殊恢复可以按明确规则带入片段和运行通知。必须让用户看得到进入恢复及其次数，不能在原有次数之外隐藏增加收费请求，也不能默默提高用户手动输出上限或降低思考强度。

### 12.2 已核对的公开实现与官方能力

- Hermes 在已核对提交 `1e0c7730d791f5ce855c5c78935cfea6fb1e43a9` 中，对于正文截断保存 assistant 片段并追加续写提示，限制恢复轮次；但提示实际为 `role=user`，不是原生 system 角色。工具参数截断另走提高额度、重做请求的分支，不拼接坏参数执行。可以参考片段留存和边界处理，不能照搬其派生用户提示。见 [turn_truncation.py](https://github.com/NousResearch/hermes-agent/blob/1e0c7730d791f5ce855c5c78935cfea6fb1e43a9/agent/turn_truncation.py)。
- DeepSeek Harness 在已核对提交 `5badb15009ae1756c3afe0ae0cef1faafc290ccc` 中，先保存已生成 assistant 内容；max-tokens 时移除 tool-call 块并返回 max-tokens 结束，不是自动追加系统通知继续。见 [agent.ts](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/core/agent-loop/src/agent.ts)、[assembler.ts](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/llm/llm/src/assembler.ts)。
- Claude 当前官方支持部分模型在会话中途追加 `role=system` 指令，无需为这项能力添加 beta header；支持范围与模型有关，不能推广到所有 Messages 接口或兼容网关。该文档证明运行通知可通过真正的系统通道发送，不证明商业产品都采用输出截断自动恢复。见 [Mid-conversation system messages](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)。
- Claude 对截断的 tool_use 建议提高 max_tokens 重新请求，获取完整工具调用；OpenAI 官方明确思考阶段也可能耗尽额度、正文为零。两者都说明不能只凭一条“达到上限”的提示就保证断点续接。见 [Claude stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)、[OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning)。

没有确认上述项目都实现了“保存任意截断内容＋真正新增 system 角色消息”的统一方案；也没有足够公开证据推断闭源产品内部实现。

### 12.3 三种截断分别处理

| 截断位置 | 应保存什么 | 下一次请求的边界 |
| --- | --- | --- |
| 正文中途，无未完整工具调用 | 已生成正文、思考、用量、结束原因及尝试快照，标记未完成 | 接口允许时携带 assistant 正文片段和运行通知续写；处理重复前缀。下一次得到新额度，但这是新采样，不能保证逐字无缝续上 |
| 只有思考，正文为零 | 已收到的可见思考和用量，仍供用户查阅 | 仅在原生续接状态合法有效时续接；否则从已提交事实重新请求。保存思考文字不等于恢复模型内部状态，不能构造空 assistant 或把 reasoning_content 随意回放到所有接口 |
| 工具调用参数 JSON 中途 | 正文、思考、工具名称与参数片段作为未执行快照 | 不执行坏参数，不伪造工具结果；恢复请求移除未提交的整轮工具调用，从已提交事实重新生成完整、尽量较小的调用，完整性及 schema 校验通过后才执行 |

前面已成功执行的工具调用和结果始终保留。若后面有多个工具参数且其中一个截断，当前整轮提交规则仍保持，不因第一个 JSON 恰好完整就提前执行。参数重生成可以替换当前有效尝试，但失败快照不能从可查阅历史删除。

### 12.4 运行通知内容与发送方式

通知必须来自后端已验证的结束原因和执行事实，不直接把上游任意错误正文或模型片段提升成高优先级系统指令。内容应包含：原因、达到的输出额度、正文/思考是否存在、是否有未执行工具调用，以及当前恢复目标。两类建议文案应分开：

正文恢复的示例：

> 天策运行通知：上一轮模型生成达到单次输出上限，结束原因为 length。已生成正文作为未完成片段保留，任务尚未完成。本次请求允许继续原任务；请接续剩余正文，避免重复已完成内容。

工具参数恢复的示例：

> 天策运行通知：上一轮在工具参数生成期间达到单次输出上限。该轮工具调用没有执行，请勿假定已写入文件或完成操作。请重新生成完整且较小的工具调用；需要大量内容时分成多次可独立完成的操作。

这些是模型可见运行通知，不是模拟用户的新问题，不是工具运行失败结果。不能仅把文字放进 user 消息并加上“系统”标题。内部通知需有稳定类型、关联 run/round/attempt、记录来源，按当前协议与模型支持映射到 system/developer 或对应系统字段；不支持会话中途 system 时可以评估合入本轮系统指令，且须明确其缓存与位置影响，不能悄悄降级为用户指令。

通知只对当前恢复阶段生效。任务结束、用户取消或新的真实用户输入改变当前运行后，停止旧恢复并清理待发送通知，不能使后续无关对话反复收到“上一轮截断”的指令。

### 12.5 当前天策需要改的实际路径

1. `conversation_request_messages.py` 当前过滤正式历史中的 system/error 消息；现有压缩/错误标签不能直接当作模型可见运行通知。需要专门的运行通知投影，避免把所有 UI 提示送给模型。
2. `chat/service.py` 当前在重试内部立即发送 retry_reset，并保持输入不变；特殊恢复需要在清空之前完成失败快照保存，再交给具有结束原因及片段数据的恢复分支。
3. `conversation_tool_loop.py` 当前工具轮次依赖整轮成功提交；恢复必须维持调用与结果配对、已经执行工具不重放以及坏参数不执行。
4. `conversation_stream_settlement.py` 当前请求失败不提交当前 AI 片段；需要持久化可查阅的未完成内容，同时区分哪些内容能回放到模型。
5. 当前 Anthropic 和 Gemini 适配器会将内部 system 消息集中到请求顶部系统字段，不保留会话中途通知的位置；若要使用原生中途 system，需要按模型能力增加明确适配，不能仅在公共列表尾部 append 后就宣称成功。
6. UI 应显示“达到输出上限，正在恢复”这类运行状态，但不因此提前把整个用户回合判成已完成，不破坏原有工具、思考、已处理容器；失败片段要在切换会话、刷新和重启后仍可查阅。

### 12.6 必须防止的具体问题与验收

- 重复或跑偏：保留正文可能使新采样重复之前内容，或让模型只讨论截断提示。检查恢复是否有有效增量，重复/无进展时停止，不能无限追加通知。
- 上下文变大：保存片段供 UI 查阅与将片段全部发给模型是不同动作。新增内容必须在输入＋输出允许空间内；上下文已满不能靠提示解决。
- 高优先级污染：只有运行器控制的固定文案及结构化事实能进系统通道，片段、工具文件内容和原始上游错误不提升为系统指令。
- 执行事实混淆：工具参数中的“已写入”等文字不代表工具执行成功；通知应明确当前未执行，不得伪造 tool 返回值或补括号后执行。
- 次数与费用：每次特殊恢复都是真实新请求，按明确上限计数并统计失败用量。达到次数、用户停止或连续无进展时停止，保存片段。
- 缓存影响：若必须修改顶部系统提示，原有缓存前缀可能失效；原生中途通知是否可用、是否保留前缀由接口能力决定，不能保证所有网关缓存无影响。

模型实测至少覆盖：正文截断恢复且不重复；纯思考截断不声称原生断点续接；写文件参数截断零次执行；恢复后完整调用只执行一次；取消不再发下一请求；系统通知没有派生 user 指令；各协议消息排序合法；上下文不足和恢复无增量及时停止；失败片段跨重启留存。尚未进行这些实测，不能把此方案写成已经验证可完全解决联想原请求。
