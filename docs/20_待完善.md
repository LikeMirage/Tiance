## MCP 工具接入统一工具系统（低优先级，暂不实施，2026-11-09）

**当前决定：用户要求先完整记录设计思路，这不是要紧事项，暂不开发。本节只记录讨论方向、接入边界与待确定问题；没有新增 MCP 接口、配置、工具目录或运行能力。后续实施需重新核验当时的代码和协议版本。**

### 1. 目的与范围

接入的主要价值是使用别人已经提供的工具服务，减少为每个第三方系统重新制作天策工具的工作。MCP 是外部能力的接入协议，进入天策以后仍应表现为普通工具，符合“能力通过工具调用表达、对象有明确文件结构、调用过程透明可查”的设计方向。

现有 Python 独立工具、前端能力桥工具继续保留，不需要为了支持 MCP 改写成 MCP 服务。模型侧继续使用现有供应商协议的标准工具调用，由天策负责转换和转发，不要求模型供应商额外提供 MCP 功能。

本次讨论的是“天策作为客户端调用外部 MCP 服务”。“把天策自己的工具开放为 MCP 服务供其他软件使用”是另一个方向，没有纳入本次方案。第一阶段建议优先考虑工具能力和本地进程、远程 HTTP 两种连接；MCP 的资源读取、提示词模板及其他扩展能力暂不承诺支持，也不能在只支持工具时宣称完整支持全部 MCP 能力。

### 2. 用户提出的核心组织方式

接入一个 MCP 服务时，自动创建以该 MCP 名称命名的工具分类，将该服务提供的每个工具作为独立工具放入分类。用户看到的结构例如：

```text
工具集
├─ 基础工具
│  ├─ 读取文件
│  └─ 执行命令
└─ 办公系统 MCP
   ├─ 查询订单
   ├─ 查询库存
   └─ 创建工单
```

上图是界面分类关系，不表示必须把物理目录改为按分类嵌套。现有分类由 `Data/tools/catalog.json` 管理，工具有各自稳定项目身份与目录；应复用这套关系。

每个导入工具也应有本地工具文件夹和标准 `.tool` 配置，承载工具名称、摘要、参数定义、本地使用说明、启用状态、动态加载、并发和权限等管理信息。实际执行程序由 MCP 服务提供，不为每个工具生成一份无意义的 Python 转发脚本，也不假装远端源码已经下载到工具项目里。

用户对执行方式的表述是：**仍由本地统一执行器处理调用，但这类工具的参数经 MCP 通道执行，其他管理方式尽量与现有独立工具相同。** 因此不是另建一套只供 MCP 使用的模型工具列表、对话系统或历史记录。

### 3. 工具发现、上下文注入与动态加载

“工具发现”与“注入模型上下文”分开处理：

- 连接服务后，软件通过 MCP 的 `tools/list` 获取工具名称、说明和输入 Schema。这是软件取得工具定义的步骤，不要求 AI 先调用一个发现工具。
- 普通加载的工具，按现有方式将名称、说明和完整参数 Schema 放入模型请求的工具列表，与天策原有工具并列。
- 动态加载的工具，复用现有轻量目录、`load_tool_info` 和 `execute_dynamic_tool`，需要时再取得完整参数并调用；不能因为工具来自 MCP 就绕过全局启用、会话选择和权限检查。
- MCP 的界面分类只是管理方式，不意味着模型请求里需要单独的“MCP 分区”。启用连接也不等于必须把它提供的全部工具完整注入每轮请求。
- 有些客户端提供“搜索工具→按需加载”的模型可见发现步骤，那是客户端的上下文策略。本次方案不以新增这种搜索机制为前提，先复用天策已有动态加载。

初次导入时工具是否默认启用、是否默认动态加载，以及以后服务新增工具是否自动启用，尚未选定产品规则。不能在同步时以隐藏默认行为扩大当前会话的工具范围。

### 4. 三种身份分开：分类、连接、工具

| 对象 | 职责 | 需要保持的边界 |
| --- | --- | --- |
| 工具分类 | 展示、组织工具，初次接入时使用 MCP 名称 | 分类名称不作为连接地址或执行路由依据；重名、重命名、移动工具不能改变调用目标 |
| MCP 连接 | 记录一个服务实例的地址或启动方式、认证引用，管理连接状态 | 使用稳定连接 ID；同一服务的不同账号或实例可独立配置；凭据和连接配置不在每个工具里重复保存 |
| MCP 导入工具 | 保存本地工具身份、工具合同、本地管理设置及来源映射 | 通过连接 ID 与远端工具名定位目标；本地显示名称与远端调用名分开 |

建议在工具的运行配置中增加 MCP 运行类型，引用稳定连接 ID 和远端工具名；具体字段名、连接配置文件位置及管理入口仍待设计，不是已经存在的配置合同。连接配置应可持久化、可查看和维护，不能只藏在前端内存或分类名称中。

天策工具调用名当前要求全局唯一。不同 MCP 服务可能都提供 `search`、`read_file` 等名称，导入时需要稳定且符合模型协议要求的本地调用名，并保存它与远端原名的映射；不得因重名导致整个工具注册表无法加载。分类或显示名称变化不应重建工具身份、丢失历史或使会话中的工具选择失效。

首次接入、重新连接和同步清单不是反复创建分类与工具。重复导入如何识别现有连接、同名分类如何处理、删除分类与删除连接是否分别操作，仍需明确，不能把普通分类操作暗中变成停止服务或删除远端数据。

### 5. 统一执行流程与 MCP 连接职责

期望的调用流程：

```text
模型发出标准工具调用
→ 统一解析工具身份，检查全局启用和会话选择
→ 校验参数，按统一权限机制处理
→ 根据运行类型执行
   ├─ Python：运行独立工具程序
   ├─ 前端能力：交给现有前端能力通道
   └─ MCP：按连接 ID 和远端工具名转发调用
→ 按统一结果合同保存结果、错误、耗时与调用记录
→ 将工具结果返回模型，继续现有会话流程
```

动态包装调用最终也要经过同一目标工具校验和 MCP 执行路径。通用层只认识运行类型、配置与结果合同，不按某个 MCP 服务名称写业务分支，不为每个工具额外增加专用后端接口。MCP 连接与传输可以有独立模块，但不能成为绕过统一工具机制的入口。

“MCP 执行”不等于“远端执行”：本地 stdio 服务通常由客户端启动进程，通过标准输入输出通信；远程 HTTP 服务则由客户端连接已有服务。两种都应由统一的连接管理处理生命周期，不能把普通 Python 工具的“一次进程输入输出”合同原样套到 MCP 长连接上。

同一连接下多个工具需要复用连接管理；不应每次调用或每次读取注册表都重新启动服务、认证并抓取全量清单。是否能并行、是否具有会话状态，应根据协议和服务实际能力设计，同时保留工具现有并发设置，不能默认所有工具都适合共享可变会话状态。

### 6. 远端定义同步与本地设置

需要区分两种来源的信息：远端决定它支持哪些工具、哪些参数和结果结构；用户决定本地是否启用、是否动态加载、权限策略及自己补充的使用说明。复用本地文件结构不意味着两种来源可以无区别地相互覆盖。

- 同步时取得完整有效的清单；如果服务分页返回，需要完成分页。部分成功、超时、认证失败或临时断线不能解释为“服务已删除其余工具”。
- 保留最后一次成功获取的定义和明确的不可用状态，避免短暂离线使工具分类、工具文件与历史全部消失；实际调用失败仍应如实返回，不能凭缓存宣称连接正常。
- 更新定义时保留本地启用、动态加载、权限与用户补充说明。摘要、显示名称等既可能来自远端也可能被用户编辑的字段，需要明确覆盖优先级、恢复远端默认值和同步冲突处理方式。
- 修改本地参数 Schema 不会让远端程序支持新参数。参数展示和编辑应说明真实来源，不能把本地修改伪装成远端能力更新。用户需要自定义转换时，应有明确的适配实现，而非偷偷改写参数。
- 对确定已从完整清单移除的工具，建议保留身份及历史并标记不可用；具体清理方式待定。不能自动抹去用户配置或历史调用记录。
- 同步过程需要避免半套配置进入注册表；旧调用尚未结束时如何更新合同，需保证本次参数、执行结果与记录使用一致的定义。缓存失效和同步频率待定，不引入无必要的高频全量轮询。

### 7. 权限、结果与失败必须保留原意

MCP 工具也要进入现有权限机制，但 MCP 返回的 Schema 和提示性元数据不天然包含天策的参数权限分类。权限映射和用户配置入口需要设计；未识别的能力不能暗中当成 `none` 或直接绕过校验，也不能仅凭参数名字猜测后声称已准确识别权限。连接认证与工具调用权限是不同事项。

工具结果可能包含文本、图片、结构化内容、资源链接和错误标记；适配时必须保留其语义，兼容当前标准内容块与动态工具结果透传。远端未声明输出 Schema 时不能伪造严格合同；声明了 Schema 时也不能丢弃。资源 URI 未必是本机路径，不得按本地文件直接读取；超出本阶段支持的内容类型应明确说明，不能静默丢弃后报成功。

连接失败、认证失败、协议错误、远端工具失败、执行超时与用户取消需要进入统一记录和会话展示。遵循原有失败可追溯要求：参数已经接收但尚未成功连接服务，也不能因此没有调用记录；连接凭据不作为工具参数或明文日志泄露出去。

执行时限优先复用现有 `tool.json` 中公开的运行超时配置。连接、传输和收尾若需要独立时限，必须说明职责与关系，不允许再出现隐藏的固定时限提前结束用户配置的长任务，或收尾无限等待使总超时失效。

暂停一次工具调用应通过协议支持的取消方式处理，并让本地等待有明确收尾。取消或断线不一定意味着远端工作已撤销，不能将“本地停止等待”报告为“远端已确定停止”。共享连接中取消一个调用不能顺手中断其他会话的调用；结果不明的有副作用调用不能在重连后无条件自动重放。

## 功能任务的会话内执行模式（暂缓，2026-11-03）

**当前决定：用户要求先不做，完整记录问题与候选方案，以后再讨论。没有选定最终防重或完成判定方案，不得把下面任何候选方案直接视为实现授权。**

### 1. 要解决什么问题

自动命名、记忆压缩、项目记忆管理、全局记忆管理，目前通过功能子会话执行。用户希望增加“会话内执行”：达到相应阈值时，不创建子会话，而是在当前会话插入该功能的维护提示词，让当前 AI 通过标准工具完成维护，再继续原任务。

这个方向符合“能力由标准工具实现”的思路，但不能只增加一个选项、换一段提示词就认为完成。需要同时解决提示词插入、重复触发、提交目标、权限、结果边界、取消恢复和前端展示。

已有功能会话机制见 [06_分支会话与功能性分支.md](06_分支会话与功能性分支.md)。以下源码现状以 2026-11-03 本地工作区为准，不代表全部已发布。

### 2. 已明确的产品要求

- 四种功能都应复用通用调度与消息插入流程，各自的启用开关、阈值算法和业务结果校验仍按原配置工作。不能以“统一”为名，把命名阈值、上下文压缩阈值和记忆增量阈值改成同一个条件。
- 执行位置与模型来源是不同维度。子会话模式继续支持缓存命中优化模式、指定第三方模型，以及适用功能原有的阻塞/异步设置。会话内模式使用当前会话的模型和正常请求流程，不另选第三方模型。
- 会话内模式不需要“等待子会话完成”的阻塞开关；这不表示请求可以绕过工具调用与工具结果的先后关系。
- 每种功能保存两套独立提示词：子会话提示词、会话内提示词。两者都有默认值，用户都能修改；切换模式不能覆盖另一套提示词，也不能丢掉暂时隐藏的子会话模型和阻塞配置。
- 子会话提示词可以要求“完成维护后停止”。会话内提示词应要求“完成维护后继续刚才尚未完成的用户任务”；原任务已经完成时不能重新执行一遍。不能给用户自定义提示词暗中拼接一套冲突指令。
- 不能为了防递归，临时关闭主会话的用户开关，再猜测完成时机重新打开。运行状态不应冒充用户配置。
- 维护过程必须可见、可追溯；提示词、标准工具调用、结果和实际发送给模型的内容应对得上，不能另建一条看不见的执行通道。
- 同一个长任务可以多次合法触发维护。例如压缩成功，随后读取大量新内容，再次达到阈值，应允许继续压缩。不能擅自加“每条用户消息只能压缩一次”的硬限制。

两种防重复问题要分开：

1. 来源会话已经有某种功能子会话在执行时，不重复启动相同功能的子会话。
2. 功能子会话本身不能因为达到阈值而不断创建功能子子会话。现有子会话使用统一递归保护设置；会话内模式不创建子会话，需要另外解决提示词反复插入问题。

### 3. 已讨论的候选方案及缺漏

以下 A、B 分别表示两种功能，例如压缩与项目记忆管理。只有在尚未完成、旧条件仍成立时交替重发，才是这里讨论的异常；完成后真正积累的新内容再次达到阈值，是正常触发。

| 候选方案 | 能解决什么 | 仍存在的缺漏或代价 | 当前结论 |
| --- | --- | --- | --- |
| 只比较上一条用户角色消息与本功能当前提示词，文本相同就不插入 | 能挡住紧邻的 A→A，不用改用户开关 | 多个功能可形成 A→B→A；提示词被用户修改后，旧消息与新配置也不相等；相同提示词长期留在最后一条用户消息位置时，又可能挡住维护完成后的合法重触发 | 未采纳，不能单独保证正确 |
| 每条真实用户消息之后，每种功能最多插入一次 | 能阻止这一段任务中同类提示反复出现 | 同一用户任务读取大量新内容后，也不能再次自动压缩；重连、自动续写与真实新用户消息的边界还需定义 | 仅作为权衡方案提出，用户未选择；不能暗中采用 |
| 只看最后一次工具调用是不是本功能所需工具 | 比提示词更接近实际操作 | 提示已经插入但工具尚未调用时没有依据；调用其他工具不代表维护已完成；失败、并行调用、多个功能共用工具均有歧义 | 未采纳 |
| 同时比较上一条提示词和最后一次工具：两者都相同则阻止；提示词相同但工具不同则认为上次已完成、允许新触发 | 尝试同时覆盖提示已发出和工具已执行两种阶段 | “工具不同”不等于“维护完成”；刚插入提示时最后一条工具可能还是原任务的工具；维护期间也可能先读取、核对资料，然后才提交结果；A→B→A 的交替问题仍未消失 | 用户提出，已分析缺口，未实施 |
| 把项目记忆与全局记忆拆成两个工具 | 工具名称可以直接区分记忆范围 | 只能解决范围识别，不能证明维护已完成；同一范围仍可能多次查询、增删改，且可能没有任何需要修改的内容；还增加两个工具合同的维护成本 | 待讨论，用户没有要求现在拆分 |
| 按功能记录本次处理的内容范围/触发边界，相同范围不重复提示 | 可区分旧任务与真正新增的处理范围，不依赖最后一个工具名称 | “范围”必须精确定义：压缩按上下文与保护区，长期记忆按增量，命名还有默认标题与手动标题约束；如果每次普通工具调用都让范围变化，仍可能过早解锁；若范围过粗，又会挡住正常重触发 | 可研究方向，尚无完整合同 |
| 记录“已触发/已提交”：提示词落盘时登记开始，对应提交工具成功时登记完成 | 有明确开始和提交事实，不用猜整轮主会话是否结束 | 命名和压缩有提交点，长期记忆没有统一整轮完成信号；还需定义失败、取消、无变更、并发、重启、迟到结果和重试的处理规则 | 最后提出的方向，用户要求先暂停，未确认采用 |

“提示词＋工具”方案的具体反例：

```text
平台插入压缩提示词
→ AI 读取文件核对某个信息
→ 还没调用 submit_memory_compaction，摘要尚未提交
→ 再次检查阈值：上一条用户消息是压缩提示，最后工具却是读取文件
→ 如果据此认定维护已完成，就会重复插入压缩提示
```

另一个边界是提示刚插入、AI 尚未调用任何新工具。最后一次工具可能仍来自原任务；如果调度在这个阶段再次检查，仅靠最后工具仍会误判。是否会在此时检查，应由最终调度入口保证，而不是假设“肯定不会”。

需要保留用户对前次分析的纠正：**“压缩成功→读取新内容→再次达到阈值→再次压缩”是正常工作流。不能因为工具名称发生变化就认定异常，也不能为了规避重复问题禁止这条正常路径。**

### 4. 如果以后继续研究“明确提交”，哪些问题还没解决

这里是待设计清单，不是既定实现：

- 命名工具 `submit_conversation_title`、压缩工具 `submit_memory_compaction` 已有明确业务提交点。但“成功”应指结果通过校验并保存成功，而非仅模型发出调用、HTTP 返回成功或工具进程正常退出。
- 长期记忆 `manage_memory` 支持查询和多次增删改；一次操作成功不代表本轮维护结束。可以研究独立完成动作、最终一次操作的完成标记等形式，但不能把任意一次查询或写入成功当成整轮完成。
- “检查后无需修改记忆”也应能正常结束，不能为了让平台识别完成而强迫 AI 写一条无意义记忆。
- 需要区分工具的一次失败与整个维护任务失败。允许 AI 修正参数，不应每次失败就重新插一份提示；如果 AI 一直不提交，也不能留下永久无法解除的任务状态。具体处理规则未确定。
- 必须明确提示、任务、结果属于哪个项目、会话、运行与输入范围。取消后的旧结果、切换执行模式后的旧子会话结果，不能误完成后来新建的任务。
- 结果已经提交成功而随后暂停主任务时，不应撤销已提交事实；结果未提交时如何恢复、放弃或重新触发，需要明确定义，不能用隐藏超时或固定重试次数替代。
- 提示已经写入但网络请求尚未发出就退出、提交已经落盘但返回消息丢失、工具重试重复提交，都需要可恢复且不会重复写入的处理规则。
- “已触发”状态应与提示消息一起可靠保存，避免只有状态没有提示，或提示存在但记录缺失。优先评估现有项目数据库、任务记录及事务机制，不应另造一套会话存储或仅靠前端内存记住。
- 按上下文实际体积判断压缩，与按新增业务内容判断维护进度，并不是同一种计数。不能为了防重偷偷漏算实际发送的 Token，或者无条件忽略维护消息在上下文中的占用。

### 5. 本次查代码发现的接入点与风险

#### 提示词替换并不能直接复用子会话提交合同

命名提交会校验功能任务记录、功能分支与父会话关系，并保护用户手动标题。会话内模式没有这层父子关系，需要一个正式、受限的当前会话提交依据；不能直接删除原校验，使普通调用可以任意改名。

压缩工具的普通会话调用路径目前用于登记手动压缩请求，再由调度创建功能会话；功能会话路径才提交摘要。若仅把提示词放进主会话，工具可能仍走“创建子会话”的旧分支，并不能完成预期的会话内提交。

压缩仓库还会向功能子会话写入继承后的压缩记录。会话内模式的来源和执行会话相同，不能机械复用这一步导致同一份结果写两次。原有来源消息边界、保护区、累计摘要与 supersedes 校验仍需保留。

长期记忆子会话可以在子会话运行结束时检查工具执行结果；会话内模式还要继续原任务，不能把“整轮主会话结束”直接当作维护完成，也不能把原任务正常调用的其他工具当成维护违规。

#### 插入必须遵守正常消息与工具协议

- 在安全的模型请求边界插入；不能拆开同一组工具调用与结果。多个并行工具还未全部完成时，不能在中间硬塞 user 消息。
- 维护提示是实际发送给模型的指令，与“正在压缩/压缩完成”等界面状态通知不同。可以复用底层消息机制，但不能把它当普通状态通知塞进现有通知队列便算完成。
- 不能借用“输出达到上限自动续写”的事件名称来伪装维护。若需要复用自动插入消息的基础能力，应定义清楚事件语义，同时验证旧输出上限恢复行为。
- 首次请求、工具循环中间、最后一次回复后刚达到阈值，触发时机可能不同。最终在哪些边界检查、如何保证维护后继续原任务而不重复回答，仍待确认。
- 前端实时消息、重连回放、历史加载、暂停按钮和运行结算必须使用同一套消息身份与运行事实。不能只保证数据库有数据，却让界面漏掉后续正式回复。

#### 统一能力与配置边界

- 继续使用工具目录里的标准参数 Schema，不把工具参数偷偷写回隐藏提示词。
- 必须处理所需工具处于动态加载、全局关闭、会话未选择或权限不允许的情况。采用何种临时可用范围尚未确定；不能擅自开启用户关闭的工具，或者扩大其他工具权限。
- 执行模式判断应在进入可能长时间等待的功能锁之前完成，并在必要位置复核。不能让会话内路径先等待异步子会话，再决定不需要等待。
- 模式切换时已有子会话可能仍在执行；同一功能的新旧路径如何避免重复提交，需要统一规则，而不是各自只检查自己的记录。
- 开关、阈值与提示词可能在执行中被用户修改。应明确本次任务使用的配置、提交时需要复核的用户意愿，以及下一次触发使用的新配置。

```text
executionMode: child | inline
prompt: 子会话提示词

modelSource / modelKey / blockingEnabled: 保留原子会话配置，inline 时不生效
```

会话内提示词共同要求的草稿语义：这是当前会话的维护步骤，不替代原用户任务；维护成功提交后继续未完成工作，不重复已完成步骤；原任务已结束时不重新开工；失败如实说明；维护提示本身不应被误写成用户原始需求。最终提示词还需要配合选定的结果提交合同，尤其不能在长期记忆完成动作尚未定义时宣称可以“成功提交整轮维护”。

### 7. 恢复开发前应先定下的事项

1. 用什么正式事实区分“提示已插入、维护进行中、维护已提交、可以再次触发”；不能只说“看上一条”，却不定义并行和交替情况下是哪一条。
2. 长期记忆完成信号如何表达，包括无变更、部分成功、失败和用户取消；是否拆分工具与是否增加完成动作分别评估。
3. 每种功能的输入范围、原任务继续执行时机，以及多个功能同时达到阈值时的顺序；不得偷偷限制为一条用户消息只执行一次。
4. 原有工具选择与权限怎样适用于维护；旧子会话与新会话内模式切换时怎样处理仍在执行的任务。
5. 消息持久化、运行归属、重连、取消、重启和幂等提交怎样复用现有机制。

至少应验证以下组合，而不是只测配置表单：

- 同一功能连续检查，不重复提示；A、B 同时达到阈值，不交替失控。
- 维护完成后读取新内容，同一用户任务能再次正常达到阈值并触发。
- 提示插入后尚未调用工具、维护中读取其他工具、一次回复并行调用多个工具、错误后修正参数，都不会误判完成。
- 命名不覆盖手动标题；压缩保留保护区与累计摘要；项目/全局记忆互不串范围；无变更也能结束。
- 动态工具、工具关闭、会话白名单、拒绝权限，都有明确行为。
- 在提示落盘、请求发出、工具提交、结果回传各阶段暂停或断开，恢复后不丢消息、不重复维护、不接受过期结果。
- 首次请求、长工具循环、最终回复后的触发均不丢失正式回复，历史回放与实时显示一致。
- 两套自定义提示词、模式切换、恢复单套默认值、旧配置补齐，不改写另一套配置。
- 子会话模式原有缓存优化、第三方模型、阻塞/异步、递归保护和取消结算继续通过回归测试。

## 会话角色与功能会话统一

当前自动命名、记忆压缩、项目记忆管理和全局记忆管理都使用真实的派生会话。它们与普通分支共用消息、附件、压缩状态和记忆状态的快照继承流程，不再使用另一套会话存储。

目前仍有一项临时策略：系统自动创建这些功能会话时，默认关闭该功能会话自身的记忆压缩、项目记忆提取和全局记忆提取，以免功能会话再次触发同类功能并形成递归任务。这个设置只是现阶段的递归保护，不是功能会话永久特殊化的设计。

后续由角色集提供各类功能的预设角色。每个预设角色应完整声明该功能需要的提示词、模型倾向、工具范围、完成条件和会话设置，使功能会话在内部形成闭环、自洽运行。创建功能会话时自动选择对应角色，从而在保留统一会话结构的前提下表达功能差异，并替换当前临时的关闭策略。

## 会话 ID 与历史记录查询入口

会话列表仍需增加右键菜单，支持直接复制会话 ID。复制结果用于会话历史记录查询工具的 `session_id` 参数，让用户和 AI 无需进入数据目录查找内部文件名，也不依赖界面临时坐标。

该入口只负责复制稳定标识，不直接读取或拼接对话正文。历史记录的检索、筛选与返回继续由独立工具完成，避免会话界面与具体工具耦合。

## 工具图标

工具图标体系仍待设计。图标应帮助用户快速识别工具用途和类别，例如文档、表格、搜索、图像、开发、会话与前端操作；同类工具保持统一视觉语言，同时避免仅靠颜色区分。图标需要成为工具项目的正式资源和清单字段，不能由界面按工具名称写死。

## 工具系统权限

工具系统仍需建立统一的权限模型，避免权限判断散落在单个工具或前端页面中。每个工具参数都应能声明其可能触发的行为及作用范围，由平台根据统一权限表在调用前完成判断，工具只描述能力，不自行决定是否放行。

权限表至少需要同时表达两层信息：

- 行为范围：工作区内、工作区外。文件读取、写入、覆盖、删除、执行程序、网络访问和外部服务调用等行为，都应按真实作用范围归类。
- 用户策略：禁止、询问、总是允许。策略应能按工具及其具体参数设置，而不是只能对整个工具一刀切。

后续还需要为工具参数提供独立开关。用户可以关闭某个危险或不需要的参数能力，同时保留该工具其他安全能力；关闭后的参数不能只在界面隐藏，工具调用校验也必须拒绝。权限表、参数开关、调用前确认和调用记录应使用同一份正式配置，避免界面状态与实际执行权限不一致。

## 主题集

主题集仍需完善和优化。现有主题选择与管理偏向“先有入口”，还没有形成成熟的主题预览、信息层级、分类筛选、适用范围、资源校验和编辑反馈。后续应围绕真实的选择与管理流程重新梳理，确保用户能看清主题差异、当前状态和作用范围，并避免只增加数量而缺少质量控制。

## 工具集专有看板

工具集的专有看板仍需完善前端细节。现有部分选择器、卡片、统计块和配置入口只是为了具备基本功能而设计，信息密度、状态反馈、尺寸统一、文字完整显示和操作层级都不够成熟。

后续应按工具管理的真实任务重新设计，包括工具浏览与分类、能力与权限查看、参数开关、案例管理、依赖状态、调用记录、市场状态和危险操作确认。看板应复用统一的工具数据与权限配置，不为某个工具写专用判断，也不能用外观入口代替真实能力。
