# 后端供应商能力桥与内置网络搜索

> 实现基线：2026-08-02。这里的“后端桥”准确名称是后端供应商能力桥。

一个普通 Python 工具有时需要使用当前会话供应商已经提供的能力，例如 OpenAI、Anthropic 或 Gemini 的内置网络搜索。最直接的做法是让工具读取供应商配置和 API Key，但这会把密钥、数据库结构和每家协议都泄漏给工具。

天策在工具进程与供应商客户端之间增加一条受控能力桥：工具只得到一次性授权和统一接口，后端保留密钥并选择具体协议适配器。

## 为什么不是把 API Key 传给工具

如果工具直接拿到密钥：

- 任意工具都可能读取或记录它；
- 工具必须理解供应商配置文件；
- 每个工具都要重复处理 OpenAI、Anthropic、Gemini 差异；
- 密钥轮询、用量统计和错误转换会分散；
- 工具市场中的第三方代码获得了不必要的权限。

能力桥只授予“本次工具调用可以使用当前会话的网络搜索”，而不是“这个进程可以读取当前供应商所有秘密”。

## 授权模型

后端在启动已登记的工具时生成高强度随机授权，绑定：

- 能力类型，目前为 `web_search`；
- 工具调用与工具身份；
- 当前项目、会话；
- 当前供应商和模型；
- 创建与过期时间。

授权只存在后端内存。工具把短期 Bearer 凭据提交给本机能力接口；后端验证能力和有效期后，从绑定上下文解析真实供应商配置与加密密钥。工具结束后授权被撤销，过期授权也会清理。

## 通用网络搜索工具

内置 `network_search` 是普通 Python 工具。对模型而言，它只有稳定的查询合同；对工具而言，它只调用天策本机的统一网络搜索能力；真正的供应商请求由后端适配器完成。

当前适配器覆盖 OpenAI Responses、Anthropic 和 Gemini 的供应商内置搜索形式。后端负责：

- 选择供应商与模型；
- 构造各协议需要的搜索工具或请求；
- 使用本地加密凭据；
- 解析答案与来源；
- 记录独立的 `provider_web_search` 用量；
- 把上游错误转换成稳定错误。

因此工具不需要出现 `if provider == ...`，新增协议也优先扩展后端适配器，而不是复制一份新搜索工具。

## 三条桥的分工

天策当前常被混称为“桥”的结构实际有三条：

| 桥 | 连接什么 | 解决什么 |
| --- | --- | --- |
| Python 工具运行桥 | 后端工具循环 ↔ 独立 Python 进程 | 隔离运行、JSON 输入输出、独立依赖 |
| 前端能力桥 | 后端工具循环 ↔ 前端白名单执行器 | 使用标签页、会话、界面等实时前端状态 |
| 后端供应商能力桥 | 工具进程 ↔ 后端供应商适配层 | 不暴露密钥地复用当前供应商能力 |

三者都使用标准工具调用结果，但信任边界完全不同，不应合并成一个“万能桥”。

## 安全边界

- 能力必须由后端明确授予，不能由工具参数自称；
- 授权绑定当前调用，不能长期保存；
- 工具不能指定另一个供应商或窃取另一个会话身份；
- API Key 不进入工具参数、标准输出或日志；
- 供应商能力接口只暴露已经定义的动作，不是通用 HTTP 代理。

## 当前边界

目前正式能力只有网络搜索。未来若增加文件托管、代码执行或其它供应商原生能力，应逐项建立能力枚举、请求合同、适配器和用量规则，不能把接口放宽成任意上游调用。
