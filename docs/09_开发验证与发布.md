# 开发、验证与发布

> 命令以仓库当前脚本为准。不要手工拼装正式发布包，也不要在发布时临时换包管理器。

## 环境

- 前端：Node.js `>=22.12.0`，pnpm，锁文件 `2_ReactWeb/pnpm-lock.yaml`。
- 后端和桌面壳：Python `>=3.11`。
- Windows 正式包使用仓库内 `runtime/`，无需用户另装 Python。

## 前端开发

```powershell
cd 2_ReactWeb
pnpm install --frozen-lockfile
pnpm dev
```

开发服务固定监听 `127.0.0.1:18100`。类型检查、状态测试和构建：

```powershell
pnpm check
pnpm test:conversation-state
pnpm build
```

只有依赖、入口、路由或构建配置变化时才需要把完整构建作为针对性验证；正式打包前必须保证 `dist` 来自目标提交。

### 发布后静态资源缓存（BE-013，2026-10-29）

`FrontendStaticFiles` 对 `/app/assets/` 下符合构建命名规则、文件名含内容哈希的 JS、CSS、字体、图片和 WASM 使用 `Cache-Control: public, max-age=31536000, immutable`。GET、HEAD 和条件请求的 304 响应遵守同一策略，浏览器可以复用已下载资源。

入口 HTML、favicon、启动背景及其它固定 URL 文件保留原来的禁止缓存策略。新构建改变资源内容时产生新文件名，入口重新读取后引用新资源；不要原地覆盖已有哈希文件名下的内容。该策略仅用于打包的前端静态目录，不应用于主题资源 API、项目文件或会话数据。验证入口：`1_PythonServer/tests/test_frontend_static_cache.py`。

## 访问网关诊断日志（2026-11-02）

桌面壳启动网关时，默认把 `Microsoft.AspNetCore` 和 `Yarp.ReverseProxy` 日志级别设为 `Warning`，不记录每个成功请求的开始、路由、代理和结束信息；警告、错误及宿主启动信息保留。需要临时排查时，可在启动环境显式设置 `Logging__LogLevel__Microsoft.AspNetCore` 或 `Logging__LogLevel__Yarp.ReverseProxy`，设置值优先于默认值，文件保留上限仍然生效。

`Data/logs/gateway.log` 使用以下保留策略：

- 单文件最多 **8 MiB**，保留当前日志以及 `gateway.log.1`、`gateway.log.2` 两份备份，总计最多 **24 MiB**；`.1` 比 `.2` 更新。
- 运行期间按实际写入字节数轮转，不依赖退出或重启。超长诊断输出也分块写入，单次内存缓冲为 64 KiB；日志记录可能跨文件，查看时按 `.2`、`.1`、当前文件顺序连接。
- 启动时发现旧文件超过 8 MiB，只保留其末尾 8 MiB，再按上述策略继续记录。旧的超大 `gateway.log` 不会被改名为同样巨大的永久备份；只复制末尾所需部分，不整份读入内存。整理期间会短暂存在一个最多 8 MiB 的临时文件。
- stdout/stderr 由桌面壳的独立读取线程持续接收，子进程不直接持有轮转文件的句柄。不要只把 `RotatingFileHandler` 的文件描述符传给子进程，否则改名后子进程仍可能写入旧文件。
- 日志写入失败会报告一次错误并继续读取、丢弃后续诊断输出，避免输出管道塞满而堵住网关；退出时为日志收尾最多等待 2 秒。此限制仅用于诊断日志线程，不改变模型、工具或 HTTP 请求的超时。

以上只适用于可轮转的网关诊断日志，不裁剪会话消息、模型原始响应或工具执行记录。Python 后端的 `desktop-backend.log` 仍使用其原有启动时轮转策略，不应混为同一实现。修改桌面壳源码后**重启天策生效**；无需重新编译网关 EXE，不中断正在运行的网关来强行切换日志句柄。

实现：`3_PyWebView/app/gateway_process_log.py`、`gateway_process.py`。验证：在 `3_PyWebView` 目录执行 `python -m pytest tests/test_gateway_process_log.py tests/test_desktop_auth.py -q`，覆盖连续轮转、超大写入、旧日志整理、真实进程 stdout/stderr、磁盘写入失败及启动失败收尾。

## Windows 图标与快捷方式

图标原图为 `3_PyWebView/assets/app-icon.png`；多尺寸 `app-icon.ico` 由桌面窗口、托盘、启动器和更新器共用。网页使用同内容的 `2_ReactWeb/public/favicon.ico`，本地打包页面对应 `2_ReactWeb/dist/favicon.ico`。换图标后还需运行 `3_PyWebView/launcher/windows/build.ps1` 和 `3_PyWebView/updater/windows/build.ps1`，更新已嵌入图标的两个可执行文件。

导出 ICO 时按 alpha 大于 0 的内容边界取图，去除外围完全透明的留白；按原比例居中适配 16、24、32、48、64、128、256 像素的方形画布，保留圆角透明区域。不要直接缩放整张带大幅透明留白的原图，也不要把非正方形内容强行拉伸。原始 PNG 保留，裁边只作用于图标导出。

启动器新建和更新已有桌面快捷方式时，都设置共享 ICO 路径和稳定的 AppUserModelID，并用 `SHChangeNotify` 通知 Windows 刷新对应图标文件及快捷方式。只更新指向本安装目录启动器的快捷方式，保留已有参数、工作目录和描述，不全局清除图标缓存或重启 Explorer。不要只替换 EXE 内嵌图标，却忽略已有快捷方式的图标引用与缓存。

快捷方式回归验证：构建启动器后运行 `powershell.exe -NoProfile -File 3_PyWebView/tests/test_launcher_shortcuts.ps1`，在临时目录创建并更新快捷方式，核对图标、应用标识及原有设置，不启动天策、不改真实桌面快捷方式。

## 后端验证

在具备项目测试依赖的 Python 环境中：

```powershell
python -m pytest 1_PythonServer/tests
```

优先运行与改动直接相关的测试。会话上下文、持久化、工具权限、取消/重试、更新和公共基础模块改动需要对应合同测试，不能只看服务能启动。

## 测试包

从仓库根目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/package-test.ps1
```

脚本默认从 `HEAD` 创建 `测试包/Tiance`，包含 `Tiance.exe`、`system`、`runtime`、`Data`、后端、前端 `dist` 和桌面壳。目标目录已存在时会明确失败，不会覆盖旧测试包。

若必须包含少量未提交内容，使用 `-WorkingTreePaths` 显式列出允许路径；脚本不会把整个脏工作区偷偷装包：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/package-test.ps1 `
  -WorkingTreePaths @("1_PythonServer", "2_ReactWeb/dist", "3_PyWebView")
```

## 版本

正式版本至少需要同步：

- `system/version.json`
- `1_PythonServer/pyproject.toml`
- `2_ReactWeb/package.json`
- `3_PyWebView/pyproject.toml`

提交、标签和脚本 `-Version` 必须一致。标签使用不可变的 `vX.Y.Z`；错误发布通过新补丁版本修复，不移动旧标签。

## 数据库升级发布检查

发布新版程序时，必须保证新版能自动使用其声明支持的旧版数据。升级程序本身包含数据库升级授权，用户不需要手动运行脚本或再次确认。只验证空目录安装成功，不能证明旧用户能正常更新。数据库结构与迁移实现见[项目、会话与存储](02_项目会话与存储.md)。

平台维护的数据库及检查范围如下；版本号以各库代码为准，表中数值是 2026-11-01 的当前实现：

| 数据库 | 位置与内容 | 当前版本与迁移入口 | 本次已实现的升级 |
| --- | --- | --- | --- |
| 全局库 | `Data/db/tiance.db`：工作区偏好、功能模型、网络设置、活动统计 | v49；`app/infra/database/schema.py`、`app/migrations/global_db/` | 恢复历史注册步骤至 v49，在后端启动时执行 |
| 项目库 | 每个项目根目录的 `.Tiance/tiance.db`：会话、消息、草稿、分支、运行、记忆、审计 | v8；`app/repositories/project/conversation_schema.py`、`app/migrations/project_db/` | v1～v7→v8，在使用前执行 |
| 用量库 | `Data/usage/usage.db`：Token、费用明细及汇总 | v1；`app/repositories/llm/usage_sqlite_store.py`、`app/migrations/usage_db/` | 结构仍为 v1；恢复旧 JSONL / 旧全局库用量导入，并校验明细与汇总 |
| 工具调用记录索引 | 各工具项目 `.Tiance/tool-calls/records-index.sqlite3`，由同目录 `records.jsonl` 派生 | v1（`PRAGMA user_version`）；`app/repositories/tools/tool_call_record_index.py` | 无版本、版本不符或表/索引结构不符时自动重建；重建与版本登记在同一事务，失败回滚，保留 JSONL 正式记录 |

**版本检查还必须覆盖表内配置和外部文件。** 功能模型配置版本独立于全局 schema；供应商 JSON、各项目集 catalog、工作区选择和旧用量来源也在升级范围内。迁移矩阵与来源版本见 02 号文档。不能以“全局库已经 v49”或仅有 schema 测试通过，认定全部旧数据已兼容。`app/migrations` 下冻结的 SQL/JSON 是程序文件，必须与 Python 模块一并进入安装包和更新包；setuptools 的 package-data 也需同步维护。

项目库覆盖普通、工具、知识、经验、角色、主题、供应商七类项目集，也覆盖普通项目登记的外部根目录。不能只检查 `Data/projects/` 或当前选中的项目。工具自身创建的业务数据库由该工具的版本升级负责；用户通过数据库查看器打开的数据库不属于天策平台迁移范围。

不是每次软件发布都要提升所有数据库版本；哪个库的表、列、索引、约束或持久化正文格式发生变化，就必须同步完成该库的以下工作：

1. 提升数据库版本，更新新库完整结构；数据库内 JSON、压缩正文等格式变化也属于持久化合同变化，不能只检查 SQL 表结构。
2. 在 `app/migrations/<对应库>/` 添加独立版本步骤并登记完整路径。步骤固定描述当时的源与目标结构，不能依赖以后会变化的新库 schema，也不能只改版本标记。
3. 保证旧数据在进入当前读写逻辑前自动完成升级。检查后端、项目看板、直接仓库读取，以及桌面壳启动前读取全局设置等所有入口；各项目集共用同一项目库入口。
4. 用固定旧结构样本验证数据保持、整条链失败回滚、重试、并发只迁移一次和 WAL 一致性备份。验证新库与迁移后库具备相同的当前结构；用量升级还要核对明细、累计 Token 与金额，审计升级还要核对还原正文和哈希。
5. 清点发布支持范围内的旧数据库版本，验证相邻版本和跳版本更新路径。当前登记路径以外的更老格式不能被宣称为已支持；若属于本次承诺的升级来源，必须先补齐转换与回归，不能把“不支持旧库”错误留给用户，也不能通过清空数据、换目录或重装掩盖问题。
6. 将版本常量、新库结构、迁移步骤、登记入口、读写调用方及测试一起提交到发布标签。修改格式却缺少迁移、迁移文件未进入发布包、或受支持旧库不能升级，均阻止发布。

更新包不携带 `Data/` 和任何用户数据库。完整程序更新包包含标签中完整的 `1_PythonServer/app/migrations/` 及其依赖；相邻版本增量包必须包含新增或变更的迁移文件、登记和依赖，按其声明来源版本安装后应得到完整的目标迁移模块。更新器替换程序文件；重启后由新版程序在本机迁移原有数据库。正式验收必须在隔离目录中，用旧发布版数据的副本分别完成相邻版本增量更新和跳版本完整程序更新，核对原项目、会话、工具调用记录、用量及设置可用，并再次启动验证不会重复迁移。禁止用开发者正在使用的数据库做测试。

发布说明涉及数据库升级时，应记录支持的来源版本、变化范围和验收结果；不能只写“已修复兼容性”。程序降级或恢复旧备份属于单独的恢复操作，不能让旧程序把新格式当成旧格式写入。

## 正式发布包

构建前端、提交版本并创建标签后，从仓库根目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/package-release.ps1 `
  -Version 0.3.23 `
  -Tag v0.3.23 `
  -PreviousTag v0.3.22
```

版本号仅为示例，发布时替换为目标版本。脚本生成：

| 文件 | 用途 |
| --- | --- |
| `发布包/Tiance.zip` | 完整安装包，包含公开 `Data` 预置 |
| `发布包/Tiance-update.zip` | 可跨版本更新的完整程序包，不含 `Data` |
| `发布包/Tiance-update-incremental.zip` | 相邻版本增量程序包 |
| `发布包/update.json` | 更新版本、文件名、SHA-256、大小和相邻起始版本 |

更新包内 `system/update-manifest.json` 使用 schema 2，明确 `replace`、`delete` 和 `mode`。用户数据、密钥、项目和工具配置不进入程序更新包。

## GitHub Release

发布前确认标签已经推送，随后创建 Release 并上传四个产物。推荐使用 GitHub CLI：

```powershell
git push origin main
git push origin v0.3.23
gh release create v0.3.23 `
  发布包/Tiance.zip `
  发布包/Tiance-update.zip `
  发布包/Tiance-update-incremental.zip `
  发布包/update.json
```

上传后重新下载或通过 Release API 核对文件名、大小和 SHA-256。不要发布包含 `.env`、Token、用户 `Data`、会话数据库或私人市场内容的包。

## 更新器边界

后端负责检查和下载，桌面 updater 负责替换程序文件。下载校验和应用前校验都需要基于同一可信清单；更新器应用时仍应重新确认归档完整性，并对安装目录使用互斥和可恢复事务。
