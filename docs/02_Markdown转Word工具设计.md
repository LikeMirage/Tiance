# Markdown 转 Word：从 LaTeX 到原生可编辑公式

> 实现基线：2026-08-02。对应内置工具 `md2docx`。

Markdown 转 Word 很容易做成“看起来成功”：解析几种标题，把公式截图塞进去，遇到复杂内容静默跳过。真正困难的是交付一个仍然可以在 Word 中继续编辑、排版和审阅的文档，并在不能可靠转换时明确告诉用户。

天策的转换器把问题拆成三部分：理解 Markdown、继承 Word 排版、为特殊内容选择最合适的表示。数学公式是其中最能体现这一思路的一环。

## 转换目标

当前工具支持标题、目录、段落、原生列表、任务列表、引用、表格、本地和网络图片、链接、脚注、尾注、Mermaid、块级 HTML 与数学公式。它还可以从现有 DOCX 样本提取模板，包括纸张、页边距、分节、正文与标题样式、字体字号、行距缩进、分页控制、页眉页脚、文档设置和表格样本。

这意味着转换不是把 Markdown 套进一份固定白纸，而是可以沿用组织已有的 Word 外观。

## 公式为什么不能一律转图片

公式截图在视觉上最省事，但会丢掉：

- Word 内继续编辑公式的能力；
- 字号、行内/块级位置和版式适配；
- 搜索、复制和辅助技术读取；
- 与正文一致的数学字体和对象结构。

Word 的原生数学对象使用 OMML，而 Markdown 常见输入是 LaTeX。两者并不是简单字符串替换。天策采用一条中间语义链：

```mermaid
flowchart LR
    A["LaTeX"] --> B["规范化与安全检查"]
    B --> C["MathML"]
    C --> D["MML2OMML.XSL"]
    D --> E["OMML 结构修复与校验"]
    E --> F["Word 原生可编辑公式"]
```

### 第一步：先判断能否忠实转换

转换器先检查括号、环境、`left/right` 配对和不适合直接进入 Word 的命令。常见扩展会被规范化，例如前置上下标、广义分式、颜色、边框和取消线。无法可靠解释的命令不会被假装成功。

### 第二步：借 MathML 过桥

成熟的 LaTeX 解析器先把公式变成 MathML。随后使用 Microsoft 的 `MML2OMML.XSL` 转成 Word 所需的 OMML。这样不需要手写一套不完整的 LaTeX 到 Word 语法树转换器。

### 第三步：修复并验证 Word 结构

机械 XSLT 结果仍可能包含空的求和操作数、缺失的必需节点或不符合 Word 内容模型的结构。转换器会补齐可确定的必要节点，再用专门的 OMML 校验器检查。只有通过校验的对象才进入文档。

## 三层保真降级

真正巧妙之处不只是“能转”，而是失败路径也有明确层次：

1. **优先原生 OMML**：普通数学公式成为可编辑 Word 对象。
2. **复杂图式转高质量图片**：如交换图、`tikzcd`、`xymatrix` 等 Word 难以忠实编辑的二维结构，交给 KaTeX/浏览器渲染。
3. **保留 LaTeX 源码并报警告**：解析或校验仍失败时，不静默丢失，不伪造一个看似正确的公式。

这是一条“可编辑优先、视觉保真其次、信息不丢失兜底”的交付阶梯。

编号与引用命令不直接进入 OMML。转换器只在转换副本中提取 `\tag`、`\label`、`\nonumber` 和 `\displaystyle`：公式主体继续生成可编辑公式，纯文本 `\tag` 作为右侧编号排版，`\label` 形成稳定的 Word 书签，`\nonumber` 抑制编号，`\displaystyle` 由 Word 的独立公式样式接管。原始 Markdown 不会因此被删除或改写；多个编号、复杂编号或编号语义冲突时仍保留源码并返回警告，不能把 LaTeX 命令当普通文字伪装成转换成功。

工作台中的 Markdown 预览与可视编辑不直接复用这条 Word 转换链。前端使用 KaTeX 负责即时显示，Word 工具使用 MathML/OMML 负责可编辑交付；二者只共享“保留源码、失败可见、转换不反写源文件”的产品约束，避免一种输出格式的兼容规则暗中改变另一种格式的内容合同。

## Mermaid、HTML 和图片

Mermaid 与块级 HTML 天生更适合浏览器布局。工具使用内置浏览器渲染资源生成图片，再写入 DOCX。远程图片下载会限制协议、大小和超时；本地图片按工作区规则读取。图片失败时会留下占位或警告，而不是生成一份表面完整但缺图的文件。

## Word 模板不是简单复制样式名

同名的“标题 1”在不同模板中可能拥有完全不同的字体、段前段后、编号和分页规则。模板提取会读取真实样式与页面设置，再由转换器把 Markdown 语义映射到这些样式。表格还要考虑单元格宽度、跨列、长文本和页面可用宽度，不能只把二维数组写进文档。

## 表格列宽不是平均分配

普通转换器经常把表格宽度平均分给每一列。这样实现简单，却会让短编号列占据大片空白，让真正需要空间的说明列被挤成许多行。天策把列宽分配看成一个有限空间内的排版优化问题：每增加一点宽度，应该给哪一列，才能最大程度减少整张表的换行、溢出和行高？

### 先测量将要写入 Word 的真实内容

算法先用当前 Word 模板中的字号和字体测量标题及全部单元格。在 Windows 上优先使用 GDI 取得真实字体宽度，并区分中文字体、英文字体、代码字体和数学字体；其他环境才使用 Unicode 字符宽度估算。

测量也不是把 Markdown 源码当作普通字符串。链接按可见文字计算，粗体按粗体字体计算，行内代码使用代码字体，图片保留固定的版面需求，中文标点避免形成不自然的断行。公式则先提取可见符号，并在等号、加减号和关系运算符等位置建立可换行片段。因此复杂公式不仅会被写入 Word，也会实际参与表格列宽决策。

每个单元格最终得到两个关键宽度：

- **最低宽度**：最宽的不可拆分内容所需空间，再窄就会产生横向溢出；
- **理想宽度**：内容保持原有行数、不发生额外换行时所需空间。

### 再模拟“多给这一列一点”能改善多少

页面可用宽度由纸张宽度减去左右页边距得到。算法先为所有列保留结构性底线，能够容纳各列最低宽度时就从最低宽度开始；如果整张表连最低宽度之和都放不下，则从公平的结构底线开始竞争剩余空间。

剩余宽度不是按字符数比例一次算完，而是分小步逐次分配。每一步都会分别模拟：如果把这一小段宽度交给某一列，整张表会发生什么变化。代价计算同时考虑：

- 一行中换行最多的单元格，因为它决定整行高度；
- 全行所有单元格增加的总行数；
- 不可拆分内容超出列宽的程度，并对严重溢出施加更高代价；
- 当前列距离最低宽度还有多远；
- 表头的可读性，表头换行会获得更高权重。

宽度总是交给当前能让总代价下降最多的列。前段使用较大的步长快速接近合理解，最后一小段改用更细步长收口；当所有列都达到理想宽度后，才平均分配剩余空间。结果通常会让编号、状态等短列保持紧凑，把更多页面交给长说明和复杂公式，而相同内容的多列仍能保持均衡。

```mermaid
flowchart LR
    A["读取页面可用宽度"] --> B["按真实字体测量单元格"]
    B --> C["得到最低宽度与理想宽度"]
    C --> D["模拟各列增加宽度后的换行代价"]
    D --> E["把宽度交给边际收益最高的列"]
    E --> F{"还有剩余宽度？"}
    F -- "是" --> D
    F -- "否" --> G["写入固定表格网格与单元格宽度"]
```

### 算法结果要真正落进 DOCX

计算出的比例最终会换算为 Word 使用的 twip，并同时写入表格总宽度、固定布局、表格网格和每个单元格宽度，避免 Word 再用自动适应重新改写结果。表格默认占满页面正文宽度并居中，单元格中的图片上限也跟随最终列宽计算，保证测量阶段和写入阶段使用的是同一套空间约束。

这套设计的价值不在于追求数学上的唯一最优解，而在于把“这张表读起来是否合理”转换成可以测量、比较和测试的排版成本。测试会验证长说明列能获得显著更多空间、同质列仍保持等宽、公式断点参与测量，以及最终 Word XML 中的固定宽度确实生效。

## 包级后处理与验证

DOCX 本质是一个包含多份 XML、关系和媒体资源的 ZIP 包。生成完成后，工具会检查关系引用、包结构和关键内容，执行必要后处理并汇总警告。测试覆盖公式结构、复杂边界、模板、表格布局、远程图片、回归样例和包安全。

## 为什么它也是标准工具示例

`md2docx` 自己拥有 `.tool/tool.json`、输入输出 Schema、案例、程序、资源、依赖和测试。模型调用时由标准工具合同启动它、传入 JSON 并收回结果，不在聊天服务里硬编码“Word 转换”。编辑器中的 Word 按钮则调用后端内置转换服务，以便直接使用当前尚未保存的标签页内容；两条入口保留各自生命周期，但公式、Markdown 和 DOCX 核心必须同步演进。独立 Tool 另外承载模板和外部表格引用能力，不能把这些扩展反向塞进工作台按钮的基础合同。

## 当前边界

- Word 目录字段可能需要在 Word 中刷新后显示最终页码。
- 浏览器渲染的复杂图式不是可编辑 OMML。
- 不能保证任意第三方 LaTeX 宏或任意 HTML/CSS 都能等价转换。
- “生成成功”与“版面符合特定组织标准”是两件事，正式交付仍应打开检查。
